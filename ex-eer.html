Subclasses and specialization

Everything Set 1 left out: subclasses, superclasses and inheritance; the disjointness and completeness constraints and how to read them off a sentence; and where an attribute or a relationship belongs once a hierarchy exists. Nine exercises, eight of them complete diagrams.

The enhanced model adds exactly one idea to the diagrams you drew in Set 1: an entity set can have subclasses. Everything else — the d and o circles, the double line, the little subset arcs — is notation for saying precisely which subclasses, and how they carve up the superclass.

The idea earns its place because of a problem plain ER handles badly. When most of an entity set shares one set of attributes, but a minority carries extra ones that are meaningless for the rest, plain ER gives you two bad options: nullable attributes that nobody can interpret, or a second entity set that duplicates everything the two have in common. A subclass is the third option, and Set 1 deliberately avoided problems that need it.

Where this set comes from

Several of these problems are the parts of the CSCI 331 problem book that Set 1 skipped, precisely because they needed a subclass. If a scenario here feels familiar — the hospital, Rotund Trend, the course schedule, Midnight Candle — it is the same enterprise seen from the angle plain ER could not handle.

2.1Subclasses and inheritance

A subclass is a subset of an entity set, distinguished by its own special attributes and relationships. The entity set it is drawn from is the superclass, and the relationship between them is often written is-a: a physician is a medical professional.

Two consequences follow, and both get used in every exercise below.

  • Inheritance. A subclass entity has every attribute of the superclass and takes part in every relationship the superclass takes part in. You never repeat an inherited attribute on the subclass — writing name on both employee and physician is not extra detail, it is a claim that a physician has two names.
  • Identity. A subclass entity is a superclass entity, not a copy of one. It needs no key of its own: it is identified by the superclass's key. This is what separates a subclass from a weak entity set, which is a different thing with its own partial key.
When a subclass is not the answer

The test is whether the extra attributes are meaningless outside the subclass, not merely unknown or usually empty. A patient's discharge date is unknown while they are still admitted — that is a null, not a subclass. A nurse's certifying agency has no meaning at all for an administrator — that is a subclass. Getting this backwards produces hierarchies three levels deep that model nothing, and is the most common way to over-use the notation.

2.2The two constraints

A specialization carries two constraints, and — exactly like cardinality and participation in Set 1 — they are independent of each other. Read each one off its own sentence in the narrative.

constraintnotationreadingthe question to ask
disjointcircle marked dat most one subclasscan one entity be in two?
overlappingcircle marked oany number of subclasses 
totaldouble line to the circleevery entity is in some subclasscan one entity be in none?
partialsingle line to the circlean entity may be in none 

All four combinations occur. "Employees are either administrators or medical professionals" is disjoint and total. "A university may be strong in the sciences, the arts, both, or neither" is overlapping and partial. Nothing about the first constraint tells you the second.

A specialization has exactly one subclass — stores, of which some are discount stores. Is it disjoint or overlapping?

The question does not arise. Disjointness is a constraint between subclasses, so with only one subclass there is nothing to constrain, and d and o say exactly the same thing. The problem book writes o in this situation (Exercise 2.9); d would be equally correct.

The completeness constraint still matters, though, and is still a real choice: a single line says some stores are not discount stores, a double line would claim they all are.

2.3What attaches where

Once a hierarchy exists, every attribute and every relationship in the specification has to be placed at some level of it. The rule is short: put each one at the highest level where it is meaningful for every entity, and no higher.

  • Meaningful for all employees — salary — goes on the superclass.
  • Meaningful only for nurses — the certifying agency — goes on that subclass.
  • A relationship obeys the same rule. In Exercise 2.8 only graduate students hold prior degrees, so holds attaches to graduate, not to student — and that is the whole content of the exercise.

Attaching too high is the commoner error, because it looks harmless: putting g.p.a. on student rather than on undergraduate does not lose any data, but it silently asserts that a high-school GPA is a meaningful thing to record for a doctoral candidate.

2.4The notation on one page

Everything Set 1's notation page had, plus these four. The small arc on each branch is the subset symbol: it opens towards the subclass and says which end of the line is the subset of which.

Disjoint
at most one subclass each

Overlapping
any number of subclasses

Total
double line: every entity is in one

Partial
single line: an entity may be in none

2.5Exercises

One short warm-up, then eight diagrams. As in Set 1, indicate every applicable constraint: a specialization without its circle and its line into the superclass is not finished. Draw before you click.

Warm-up

State the definition of a subclass of an entity set, give a reasonable example, and explain it briefly.

Definition. A subclass is a subset of an entity set, distinguished by its own special attributes and relationships.

Example. Woman is a subclass of the set of persons, characterised by the attribute number of pregnancies, which has no meaning for persons outside this subclass.

Why the example works. The attribute is not merely usually empty outside the subclass — it is meaningless there, and that is the test for whether a subclass earns its box. If the extra attributes would make sense for everyone and just happen to be unknown, you have a nullable attribute, not a subclass.

One specialization at a time

Give a reasonable example of a specialization into two disjoint subclasses with optional participation. Draw the EER diagram, indicating carefully the cardinality and disjointness constraints.

The example. The class "vehicle" has two subclasses, "auto-bus" and "bicycle". The two are obviously disjoint, unless somebody saw a bus on two wheels. The participation is optional, as there are many vehicles that are neither auto-buses nor bicycles.

The method. Pick the superclass first, then choose subclasses that satisfy the two constraints the question names, and test each one by trying to break it.

  • Disjoint means no entity can be in both. Test it by describing something in the intersection: if the description is absurd — a two-wheeled bus — disjointness holds.
  • Optional (partial) means something in the superclass is in neither. Test it by naming one: a car, a tram, a snowmobile.

If you cannot name the counter-example for the second test, your specialization is total and you have answered a different question.

Give a reasonable example of an entity set that has two disjoint subclasses, with optional participation. Explain your answer briefly, and draw the diagram.

The example. In a department store database, there may be an entity set apparel, intended to include anything and everything that a person can wear. Within this set, we may recognise a subclass footwear and another subclass eye glasses. The two subclasses are clearly disjoint, since one cannot easily conceive of an object that can function as footwear and eye-glasses simultaneously. The participation is optional, since many apparel items — skirts, trousers, shirts, coats, hats, gloves — classify neither as footwear nor as eye-glasses.

What makes this a better answer than "vehicle" again. The two subclasses here would carry genuinely different attributes — shoe size and sole material for one, lens prescription and frame width for the other — and neither set means anything for a hat. That is the justification a marker is looking for: not just that the sets are disjoint, but that they need to exist at all.

Complete diagrams

For each employee, the hospital records the social security number, name and salary. The employees are either administrators or medical professionals. For administrators, the hospital records their highest educational degree and the date it was received. Among medical professionals, the hospital pays special attention to physicians and certified nurses. For physicians, the hospital records their specialization area. For each certified nurse, the hospital stores the name of the agency that issued the certificate.

Step 1 — the superclass. employee, with id # as key, plus name and salary. Everything true of every employee goes here and nowhere else; the subclasses inherit it.

Step 2 — the first specialization. "The employees are either administrators or medical professionals" gives two subclasses. Disjoint (d): the word "either" excludes being both.

Step 3 — the second specialization, nested. "Among medical professionals… physicians and certified nurses" specialises medical, not employee. The nesting is the content of this exercise: a physician is a medical professional is an employee, and hanging all four subclasses off employee in one flat specialization would lose the fact that physicians and nurses are medical and administrators are not.

Step 4 — where each attribute lands. degree and date on administrator; area on physician; agency on nurse. Each sits at the lowest level where it is meaningful — the rule of §2.3, applied four times.

Step 5 — the constraints you must decide. Both specializations are drawn disjoint and partial. The second one is the judgement call: the text says "among medical professionals" the hospital attends to physicians and nurses, which leaves room for medical staff who are neither — a technician, a therapist. If your reading is that the hospital employs nobody else, a double line and a stated assumption is a defensible answer. State the assumption; that is what earns the mark.

Dangerous Professor records data about every instructor. Instructors are identified by social security number and addressed by last name and title. Notably, for those instructors who are employed part-time, the Professor needs to record the maximum number of credit hours that they are willing to lecture. Moreover, part-time instructors are invited to submit all of their contact phone-numbers (if any), while full-time instructors have only one office phone number that the Professor cares to keep.

Step 1 — why a subclass at all. maxHours is the giveaway: a maximum willing teaching load is not merely unknown for a full-timer, it is meaningless. That is the §2.1 test, and it is what rules out modelling this with a nullable attribute.

Step 2 — the shared attributes stay up. socSecNum (key), lastName and title describe every instructor, so they hang off the superclass and are inherited.

Step 3 — the phone numbers, which are the real exercise. Both subclasses have something called a phone number, and they are different attributes. A part-timer submits "all of their contact phone-numbers (if any)" — a set, possibly empty, so a multivalued attribute, double ellipse. A full-timer has "only one office phone number" — a single simple attribute. Putting one phone # on the superclass would collapse two different specifications into one and get both wrong.

Step 4 — the constraints. The problem book draws this one o, overlapping, and partial. Neither is forced by the text, and both are worth arguing about: if the department's contracts make part-time and full-time exclusive and exhaustive, d with a double line is the better model. What is not defensible is leaving the circle unmarked.

The employees of Rotund Trend form a creative and devoted group. Apart from filing their social security number and name, Rotund Trend records at least one phone number for each employee. A special group of employees is in charge of delivery service; the management requires a driver license number from every employee in the delivery group. The management is careful about tracking the years of service — after spending precisely seven years with the company (in any position), an employee is awarded an honorary present from the President, and allowed to append the title "senior" to whatever title(s) they already hold. The values of the honorary gifts, awarded to individual senior employees at the seventh anniversary of their employment date, are archived in the database.

Step 1 — two subclasses, and why they overlap. delivery empl. carries license #; senior empl. carries gift value. The constraint is overlapping, because seniority is earned "in any position" — a driver who stays seven years is in both subclasses at once. Marking this d is the error the problem is built to catch, and the three words that prevent it are easy to read past.

Step 2 — and why it is partial. A two-year cashier is in neither subclass, so a single line into the circle.

Step 3 — "at least one phone number". Not quite a plain multivalued attribute, because "at least one" is a lower bound the notation cannot express on a single symbol. The diagram splits it: a required phone # as a simple attribute, and a multivalued phone # (additional) for the rest, which may be empty. A plain double ellipse plus a note in words is also accepted — but the split says it in the notation.

Step 4 — years of service. Derived from the employment date, so date hired is stored and years served is dashed. Note where it sits: on the superclass, because every employee has a length of service — it is the seven-year threshold, not the quantity, that defines the subclass.

Step 5 — what the gift value is an attribute of. It is awarded to an individual senior employee, one per person, so it is an attribute of senior empl. If the company gave a gift at every seventh anniversary, the model would have to change: value and date together, one pair per award, which means a weak entity set award owned by the employee.

Midnight Candle has many customers, identified by library card number (issued internally), and the library database stores their name and address. The library practises careful profiling of its customers, based on their educational and professional affiliation, with the intention of predicting their taste in books. To this end, the library stores name, address and national rating of virtually any university in the country, and records the degree type, the date the degree was issued, and the university that granted it, for each college-level degree ever received by any of its customers. Universities are classified according to their perceived strength (if any) in one or more of the following foci of study: sciences, arts, humanities, and sport.

Step 1 — the degrees are a relationship, not an attribute. A degree connects a customer to a university, and its type and date are determined by that pair, so they hang off the degree diamond. This is Set 1 material and it is half the diagram.

Step 2 — the ratio. "each college-level degree ever received" — a customer may hold several, and a university grants many: M : N, partial on both sides.

Step 3 — the specialization, and the two words that settle it. "in one or more of the following foci" makes it overlapping: a university may be strong in sciences and in sport at once. "(if any)" makes it partial: a university may be strong in none. Both constraints are stated explicitly in the sentence, which is unusual and worth noticing — most narratives make you infer at least one.

Step 4 — four subclasses with no attributes. Nothing is recorded about a university because it is strong in the sciences, and the problem says so: "the library intends to collect further information about universities, based on this classification, but this database function has not yet been fully specified". The subclasses are placeholders for attributes that do not exist yet.

That is a legitimate thing to draw, and it is worth being honest about the alternative: four subclasses carrying nothing could equally be one multivalued attribute focus on university. The specialization is the better model here only because the specification says those boxes are about to be filled in.

A college department keeps a student database. For each student, the department records his name, student I.D. number, date of birth, and the major field of study. For graduate students, the department stores the following information about each undergraduate degree held: the university that issued the degree, date issued, and the major field of study. For undergraduate students, the department records their high-school GPA.

Step 1 — a total specialization. Every student in a college department is a graduate student or an undergraduate, and there is no third possibility, so the line into the d circle is double. This is the first total specialization in the set, and the first one where the double line is forced rather than chosen.

Step 2 — disjoint. Nobody is both at once.

Step 3 — the easy subclass. g.p.a. on undergraduate: a high-school GPA is meaningless for a doctoral candidate, not merely unknown.

Step 4 — the hard subclass, and the point of the exercise. A graduate student holds prior degrees, and each degree has three facts about it: university, date, major. That is not one attribute — it is a repeating group of related values, which is exactly what a weak entity set is for. So degree is a weak entity set, owned by graduate through the identifying relationship holds, with date as its partial key.

Step 5 — note where holds attaches. To graduate, not to student. A relationship is placed by the same rule as an attribute: at the level where it is meaningful, and no higher. Attaching it to student would say an undergraduate may hold prior college degrees, which the specification does not.

Subclass or weak entity set?

Both appear in this one diagram, which makes it a good place to fix the difference. A subclass is the same entity seen in more detail — a graduate student is a student, and needs no key of its own. A weak entity set is a different entity that cannot be identified alone — a degree is not a student, and it borrows the student's key to complete its own. If you find yourself giving a subclass a partial key, you have confused the two.

The capstone

Draw a complete EER diagram for the Pure Wood database. Pure Wood is a furniture store chain. All employees have their IDs, names and addresses on file, along with the date they were hired and the salary they are paid. Pure Wood keeps a register of its suppliers, identified by name; along with the name, records are kept of the mailing address, fax number, and ordinary contact voice phone number(s), if any. Pure Wood identifies its shops (stores) by name, characterises each shop by address, and assigns to each shop its manager, identified by employee ID. Some Pure Wood stores are operated as discount stores; Pure Wood records the size of the available parking lot of each discount store. Every item sold bears a product code, which identifies a class of all items that are equivalent: two identical chairs off the same assembly line have equal product codes and are two instances of the same product. They are, however, two distinct chairs, and bear distinct instance identifiers, written on a sticker the item bears from acquisition until delivery. For every item instance, at any moment, Pure Wood knows the store where that instance is located, and can determine its product code from its instance identifier. Every product must have a type, weight, height, length, width and colour. Products may be associated with purposes (studying, sleeping, meditating); some products may be suitable for multiple purposes, and some need not have any purpose on file. Whenever a product is found suitable for an individual purpose, a photograph is stored which illustrates this. All instances of the same product are sold at the same price in all stores, and that price is on file, along with the supplier who has supplied the product.

Drawn here as two panels for legibility; it is one diagram, and product appears in both to show where they join.

Step 1 — the distinction the whole problem turns on. A product is a class of equivalent items; a product instance is one physical chair. Two boxes, related 1 : M by of. Collapsing them loses the ability to say where any particular chair is, which the narrative asks for explicitly. Everything shared by identical items — type, dimensions, colour, price, supplier, purposes — belongs to product; everything about one physical object — its label and its current store — belongs to product instance.

Step 2 — instance identifiers are a key, not a partial key. The sticker "identifies the instance" and its product code can be determined from it, so it is unique across the whole company. product instance is therefore a strong entity set with label id as its key — despite being 1 : M under a parent, which is what tempts people to draw it weak. Compare Exercise 2.8's degree, which genuinely is weak.

Step 3 — the single specialization. Out of twelve boxes, exactly one subclass: discount store under store, carrying lot size. Partial, since not every store is a discount store. With one subclass, d and o are equivalent (see Check 2.1); the problem book writes o.

Step 4 — the relationships, one sentence each.

  • manage: "assigns to each shop its manager" — each store has one manager, an employee may manage several, so M : 1 from store to employee, total on the store side.
  • location: "at any moment, Pure Wood knows the store where that instance is located" — M : 1, total on the instance side, since every instance is physically somewhere.
  • from: one supplier per product, so M : 1.
  • serve: "some products may be suitable for multiple purposes, and some need not have any" — M : N, partial on the product side. The photo illustrates one product serving one purpose, so it is an attribute of the relationship.

Step 5 — the price. "All instances of the same product are sold at the same price in all stores" is a sentence written to stop you attaching price to the instance or to the store. It is a fact about the product, and nothing else.

The lesson of the capstone

One subclass in a database this size is normal. EER is a small extension to ER, used sparingly, and a diagram that is mostly specializations is usually a diagram that has mistaken nullable attributes for subclasses. The hard work here was all Set 1 work — deciding what is an entity, what is a value, and what an attribute belongs to.

Going further

Mapping a specialization to tables is where the choice between d and o, total and partial, stops being decoration. A total, disjoint specialization can become one table per subclass with no superclass table at all; a partial one cannot, because the entities in no subclass would have nowhere to live. An overlapping specialization rules out the single-table-with-a-type-column approach, since one entity would need two type values at once. Every combination maps, but each maps differently — which is the real reason the notation insists you decide.
