Exercise set 9 · Lectures 13 to 16 Normalization

Dependencies, keys and decomposition

The theory behind the schemas you have been writing since Set 3: what a functional dependency is, how to compute the closure of an attribute set, how to find every candidate key from it, what the normal forms actually require, and how to split a schema so that the split loses neither information nor dependencies. Twenty-three exercises from the problem book, in the order Lectures 13 to 16 give the material.

Nothing on this page is a query. Everything is a calculation on attribute names, and almost all of it reduces to one routine — the closure algorithm of Lecture 14. Learn that one properly and the rest of the set is bookkeeping.

Notation, as the lectures write it

Attribute sets are written without braces or commas: AB is the set containing A and B. A functional dependency is X → Y. The closure of an attribute set is X+; the closure of a dependency set is F+. They are different objects and the superscript is the only thing that distinguishes them, so read it carefully.

Every answer below is checked the same way. A dependency is in F+ exactly when its right-hand side sits inside the closure of its left-hand side:

[ X → Y ] ∈ F⁺   ⇔   Y ⊆ X⁺

That equivalence is the whole of Lecture 14. Every question on this page about whether something holds, whether something is a key, or whether a schema is in some normal form, is that line applied to a different pair of sets.

9.1Why decompose at all

Lecture 13 starts from the universal schema — one relation holding every attribute in the database. It is a legal relation and it is a terrible table, because you cannot store one fact in it without storing others alongside. Record that a student is enrolled in a course and you have also recorded the course's name, its credits, its teacher and that teacher's rank, every time.

Breaking it into components fixes that only if the components are chosen well. Choose them badly and you get redundancy — the same fact stored in several rows, so that changing it in one place and not another makes the database say two contradictory things. Everything in this set is machinery for choosing well.

Consider the following relational schema from your database: 
Attendance (student_id, student_name, course_name, classroom)
Your data administrator claims that the following functional dependency holds: 
student_name, course_name  →  classroom

(a) List a sample content of the database that, if found, proves his claim, or explain why this is impossible.
(b) List a sample content that, if found, disproves his claim, or explain why this is impossible.

(a) Impossible. A functional dependency is a constraint imposed on the schema from outside — a statement about every state the database may ever be in. No particular content can establish it, because the very next row inserted might break it.

(b) Any two rows that agree on student_name and course_name and disagree on classroom. For instance:

Attendance
student_idstudent_namecourse_nameclassroom
…Oliver TwistDatabase SystemsA103

The asymmetry is the point, and it is worth stating out loud. One counter-example settles a dependency for ever; a million confirming rows settle nothing. This is the same asymmetry you met in Set 3 and again in Set 8: an instance can disprove a key and can never prove one, because both a key and a dependency are claims about all possible content.

So where do dependencies come from? From the people who know what the data means. They are part of the specification, like the cardinality on an ER edge, and the only honest answer to “does this dependency hold?” is “ask whoever defined the database”.

9.2Functional dependencies

The definition

Given a relation schema R and attribute sets X and Y of R, the dependency X → Y holds — read “X functionally determines Y” — if for any two tuples t₁ and t₂ of R with t₁[X] = t₂[X], it must also be that t₁[Y] = t₂[Y].

Read it as a promise about disagreement: agree on the left and you are not allowed to disagree on the right. That reading is what turns several exercises below into one-line answers — “can two tuples agree on CL but disagree on G?” is just “is CL → G in F+?” upside down.

A dependency is trivial when the right side is already contained in the left: AB → A cannot fail. The normal forms all say “for every non-trivial dependency”, because the trivial ones constrain nothing.

How many dependencies a dependency implies

Lecture 13 ends with an observation that is easy to skip and worth keeping: a single dependency X → A₁A₂…An already carries 2n − 2 others with the same left side — one for every non-empty proper subset of the right-hand side. That is why F+ is enormous even when F is small, and why nobody ever computes F+ directly. The closure of an attribute set is the way round it.

9.3Armstrong's rules

Three rules generate every dependency that follows from a set F. Lecture 14 names them Armstrong's inference rules.

#RuleSays
1Reflexiveif A ⊆ X then X → A
2Augmentationif X → Y then XA → YA
3Transitiveif X → Y and Y → Z then X → Z

Three more follow from those, and save a great deal of writing:

#RuleSays
4Decompositionif X → YA then X → Y
5Unionif X → Y and X → Z then X → YZ
6Pseudotransitiveif X → Y and AY → Z then AX → Z
Consider the following set F of functional dependencies: 
(a)  A  → BC
(b)  B  → D
(c)  DE → G
Find six (or as many as you can) additional dependencies that are implied by F. For each one, give a short proof that it belongs to F+, using Armstrong's axioms and the additional rules. 
1.  BC  → CD     from (b), by augmentation (add C to both sides)
2.  A   → CD     from (a) and 1., by transitivity
3.  BE  → DE     from (b), by augmentation (add E to both sides)
4.  BE  → G      from 3. and (c), by transitivity
5.  ABE → BE     by reflexivity
6.  ABE → G      from 5. and 4., by transitivity

The pattern is augment, then chain. Transitivity is the only rule that produces something genuinely new, and it needs the right side of one dependency to match the left side of another exactly. Augmentation is how you make them match: step 1 pads B → D out to BC → CD so that it can be chained onto A → BC.

Reflexivity looks useless and is not. Step 5 produces a dependency that says nothing on its own — of course ABE determines BE. But it is a legal first link, and it lets you attach anything already known about BE to the larger set ABE.

Six is what the question asks for; there are infinitely many, because step 5 works for any superset. A proof is only a proof if each line names the rule and the lines it came from.

The quick way to check any of these. Compute the closure of the left-hand side and look for the right-hand side inside it — BE+ = BDEG, which contains G, so BE → G holds. That is §9.4, and it is how you would check your own answer before handing it in. What it does not give you is the derivation, which is what this question asks for.

9.4The closure of an attribute set

The algorithm, from Lecture 14

Given R, a dependency set F and an attribute set X, the closure X+ is the set of attributes A for which X → A is derivable.

initialize  X⁺ = X
repeat:
    for each dependency  A → B  in F:
        if  A ⊆ X⁺  then  X⁺ = X⁺ ∪ B
stop when no change is possible

It runs in O(|F|2) and it always terminates, because X+ only grows and is bounded by R.

Keep a table as you go — round, which dependency fired, and the set so far. Every answer below is written that way, because it is what “show your work” means here and because it makes a dropped dependency easy to spot.

One practical note: once a dependency has fired it can be crossed off, since its right-hand side is already in. That is the difference between the loop finishing in two passes and grinding through |F| of them.

9.5Finding the candidate keys

The vocabulary, recalled

A superkey is an attribute set S such that no two tuples agree on S — equivalently, S+ = R. A key is a minimal superkey: remove any attribute and it stops being one. If a schema has several, each is a candidate key; one is designated the primary key and the rest are secondary.

An attribute is prime if it belongs to some candidate key, and non-prime otherwise. Three of the four normal forms are stated in terms of that distinction, so you cannot test them until you have found every candidate key — not just one.

The two algorithms, from Lecture 15

One candidate key. Start with K = R, which is trivially a superkey. For each attribute A in K, compute (K − A)+; if it still equals R, drop A. What is left when you have tried every attribute is a key.

Every candidate key. Set K to the attributes that appear on no right-hand side in F. They can never be derived, so every candidate key must contain them. If K+ = R, that single K is the only key and you are finished. Otherwise try K plus one more attribute, then K plus two, and so on; at the first size that yields any keys, collect them all and stop.

The “stop at the first size that works” is what keeps the answer minimal. Going on to larger sets would hand you superkeys that are not keys.

For the schema ABCDEGHJ and dependency set F of Exercise 9.3, is BC a candidate key? Explain your answer.

No. From Exercise 9.3, BC+ = BCDEGHJ, which is missing A. A candidate key must determine every attribute of the schema, and BC does not determine A, so it is not even a superkey — let alone a minimal one.

The actual key is A alone. A is the only attribute that never appears on a right-hand side, so it must be in every candidate key; and A+ = ABCDEGHJ = R, so it is already a superkey by itself. A single-attribute superkey is automatically minimal, so A is the one and only candidate key.

Check the direction of the question. It is easy to compute BC+, see seven of the eight attributes, and read that as success. The test is equality with R, not “nearly R”.

Consider a relational schema R = ABCDEGHJK with the set of functional dependencies F: 
(1)  ADG  → BC
(2)  ABDG → E
(3)  C    → G
(4)  BJ   → HK

(a) Is the schema R in Boyce-Codd Normal Form? Prove your answer.
(b) Is the attribute set ABCD a superkey for R? Prove your answer.
(c) Does the dependency ACDJ → K hold in R under F? Prove your answer.
(d) Is it possible for two tuples of R to agree (simultaneously) on the values of attributes A and C, but to disagree on the value of B? Prove your answer.

(a) No. BCNF demands that the left side of every non-trivial dependency be a superkey. Dependency (3) has C on the left, and C+ = CG, which is nowhere near R. One violation is enough.

(b) No.

ABCD  →(3)  ABCDG  →(1)  ABCDG  →(2)  ABCDEG

ABCD+ = ABCDEG ⊂ R — the attributes H, J and K are missing. Dependency (4) never fires because J is absent, and J appears on no right-hand side, so it can never arrive.

(c) Yes.

ACDJ  →(3)  ACDGJ  →(1)  ABCDGJ  →(2)  ABCDEGJ  →(4)  ABCDEGHJK

K ⊆ ACDJ+, so the dependency is in F+. Notice that ACDJ+ = R, so ACDJ is in fact a superkey — the question only asked about K, but the closure tells you more than you asked for.

(d) Yes, they may disagree, because AC → B does not hold: AC+ = ACG, and B is not in it. Dependency (1) needs D and G as well as A; G arrives from (3) but D never does.

Four questions, four closures, one method. That is the shape of this kind of exam problem: each part is the same calculation on a different starting set.

Consider a relational schema R = ABCDEGHJK with the set of functional dependencies F: 
(1)  ADG  → BC
(2)  ABDG → E
(3)  C    → GJ
(4)  BJ   → HK
(5)  AH   → K

(b) Is ABCD a superkey for R?

(d) Is it possible for two tuples of R to agree on A and B but disagree on C?

(a) No. Dependency (3) has C on the left and C+ = CGJ ≠ R, so C is not a superkey.

(b) Yes, and this is where this schema differs from Exercise 9.8. The extra J on the right of (3) changes everything:

ABCD  →(3)  ABCDGJ  →(1)  ABCDGJ  →(2)  ABCDEGJ  →(4)  ABCDEGHJK = R

Once J arrives, (4) can fire, and H and K follow. In Exercise 9.8 nothing produced J and the closure stalled.

(c) Yes. ACD+ = ABCDEGHJK = R, so ACD determines everything, H included.

(d) Yes, they may disagree. AB+ = AB — no dependency has a left side inside AB, so the closure never grows at all, and C is certainly not in it.

(e) ACD and ADG are both candidate keys. Every candidate key must contain A and D, since neither ever appears on a right-hand side. But AD+ = AD, so at least one more attribute is needed. Adding C works, by part (c); adding G works too:

ADG  →(1)  ABCDG  →(2)  ABCDEG  →(3)  ABCDEGJ  →(4)  ABCDEGHJK = R

Both are minimal, since AD alone is not a superkey and neither C nor G can be dropped. Trying the other candidates one at a time — ADB, ADE, ADH, ADJ, ADK — none reaches R, so those two are the complete answer.

“Find a candidate key” asks for one; the question of whether there are others is a different one. Here there are two, and on the exam that distinction matters, because the prime attributes — and therefore 3NF — depend on having found all of them.

Consider a relational schema R = ABCDEGHJK with the set of functional dependencies F: 
(1)  BC → A     (4)  G → BE
(2)  DB → C     (5)  H → K
(3)  E  → D     (6)  J → H
List all candidate keys for R, stating clearly how many there are altogether. For each one, prove that it is indeed a candidate key, and prove that there are no others.

There is exactly one: GJ.

Every candidate key must contain G and J, because neither appears on the right-hand side of any dependency in F, so nothing can ever derive them. Scan the right sides to confirm: A, C, D, BE, K, H — no G, no J.

GJ is already a superkey, so nothing more is needed and nothing less will do:

GJ  →(4)  BEGJ  →(6)  BEGHJ  →(3)  BDEGHJ
    →(5)  BDEGHJK  →(2)  BCDEGHJK  →(1)  ABCDEGHJK = R

Since GJ+ = R, the algorithm of Lecture 15 stops at once: the forced attributes alone form a key, so there is no larger set to try and no other candidate key exists.

That last step is the proof of uniqueness, and it is easy to leave out. Any other candidate key would have to contain GJ — and any proper superset of a key is a superkey, not a key. So GJ being a key by itself settles that it is the only one.

A second question the same closure answers. Can two tuples agree on G and E but disagree on C? No — GE+ reaches C by the same chain E → D, then DB → C once B has arrived from G → BE.

9.6Equivalence and minimal cover

Two different-looking dependency sets can constrain a schema identically, and one of them is usually shorter. Lecture 15 gives the test for sameness and the algorithm for finding the short one — which is the input every decomposition algorithm in §9.9 expects.

Equivalence, and the lecture's example

F covers G when every dependency of G follows from F; that is, G+ ⊆ F+. Two sets are equivalent, written F ≡ G, when each covers the other.

Nobody builds F+ to check this. For each dependency X → Y of G, compute X+ under F and look for Y inside it. That is the same Y ⊆ X+ test as everywhere else, and it takes one closure per dependency.

Lecture 15 works this schema ABDEH with two dependency sets:

F and G on ABDEH
FG
(1) A → BH(a) B → DEH
(2) B → AH(b) H → A
(3) H → BDE(c) A → B

Step 1 — does F cover G? Take each dependency of G and close its left side under F:

B  →(2)  ABH  →(3)  ABDEH      so  DEH ⊆ B⁺,  (a) holds
H  →(3)  BDEH →(2)  ABDEH      so  A   ⊆ H⁺,  (b) holds
A  →(1)  ABH                   so  B   ⊆ A⁺,  (c) holds

Step 2 — does G cover F? Now close each left side of F under G:

A  →(c)  AB   →(a)  ABDEH      so  BH  ⊆ A⁺,  (1) holds
B  →(a)  BDEH →(b)  ABDEH      so  AH  ⊆ B⁺,  (2) holds
H  →(b)  AH   →(c)  ABH  →(a)  ABDEH   so  BDE ⊆ H⁺,  (3) holds

Both directions hold, so F+ = G+ and the two sets are equivalent — they describe the same schema.

One direction is not enough. Lecture 15's counter-example is F = {A → B, B → C} against G = {A → C}. F covers G, since A → C follows by transitivity. G does not cover F: under G, A+ = AC, which does not contain B.

Minimal cover, and the algorithm

A dependency set F is minimal when all three hold:

#ConditionWhat it rules out
1every right-hand side is a single attributeX → ABC, which is really three dependencies in a trench coat
2no redundant attribute on a left-hand sideXAB → Y where AB → Y already does the job
3no redundant dependencya dependency whose removal leaves an equivalent set

A minimal cover of a set E is a minimal set equivalent to E. Every set has at least one, found by establishing the three conditions in that order — after which no further iteration is needed:

1.  replace each  X → A₁A₂…Aₙ  by  X → A₁, …, X → Aₙ

2.  for each  X → A  in F, for each attribute B in X:
        if  (F − {X → A}) ∪ {(X−B) → A}  is equivalent to F
        then replace  X → A  by  (X−B) → A

3.  for each remaining  X → A  in F:
        if  F − {X → A}  is equivalent to F
        then remove  X → A

Every test inside steps 2 and 3 is an equivalence test, and every equivalence test is a closure. There is nothing else in the algorithm.

Lecture 15's first example. E = {B → A, D → A, AB → D}.

step 1:  nothing to do — all right sides are single already.
step 2:  can  AB → D  lose a left attribute?
             A → D ?  under E, A⁺ = A.  No.
             B → D ?  under E, B⁺ = AB, and with B → D added
                        the set still proves AB → D.  Yes — replace it.
         F is now  {B → A, D → A, B → D}
step 3:  B → A is redundant: B → D → A already gives it.  Drop it.

minimal cover:  { B → D,  D → A }

Lecture 15's second example. G = {A → BCDE, CD → E}.

step 1:  A → B,  A → C,  A → D,  A → E,  CD → E
step 2:  can  CD → E  lose an attribute?
             C → E ?  No.    D → E ?  No.    Keep CD → E.
step 3:  A → E is redundant: A → CD → E.  Drop it.

minimal cover:  { A → B,  A → C,  A → D,  CD → E }

Those four may be written informally as {A → BCD, CD → E}, recombining the common left sides by the union rule. That form is convenient to read but no longer satisfies condition 1, so the split form is what the decomposition algorithm takes as input.

Consider the relational schema R = ABCDEGHJKLMN with the set of functional dependencies F: 
(1)  A → E     (6)   B → A
(2)  H → C     (7)   K → D
(3)  D → K     (8)   C → N
(4)  M → G     (9)   E → M
(5)  L → J     (10)  G → L

(a) Prove that F is a minimal cover.
(b) Find one candidate key of R and prove that it is indeed a candidate key.

(a) Check the three conditions, in order.

Condition 1 — every right-hand side here is a single attribute. By inspection, true of all ten.

Condition 2 — every left-hand side here is a single attribute as well, so there is nothing to remove: dropping the only attribute would delete the dependency rather than weaken it.

Condition 3 — no dependency is redundant. Each one has the shape X → Y where X is a single attribute that appears on no other left-hand side in F. Remove that dependency and X+ collapses to X alone, because nothing else in F can fire on it; before the removal X+ contained Y. So the smaller set is not equivalent, and the argument runs the same way for all ten.

(b) BHD is a candidate key (and so is BHK; either answers the question). Every candidate key must contain B and H, since neither appears on any right-hand side. But those two alone are not enough:

BH  →(2)  BCH  →(6)  ABCH  →(8)  ABCHN  →(1)  ABCEHN
    →(9)  ABCEHMN  →(4)  ABCEGHMN  →(10)  ABCEGHLMN
    →(5)  ABCEGHJLMN = BH⁺

D and K are missing, and they are the only two attributes outside BH+, so exactly one more is needed. Adding either works, since (3) and (7) run in both directions:

BHD  →(above)  ABCEGHJLMN + D  →(3)  ABCDEGHJKLMN = R
BHK  →(above)  ABCEGHJLMN + K  →(7)  ABCDEGHJKLMN = R

Each is minimal, because BH is not a superkey and both B and H are forced.

Why the proof of (a) is so short here. Ten dependencies would normally mean ten equivalence tests in condition 3. They collapse to one argument because every left-hand side is a distinct single attribute: no dependency can help derive another one's left side on its own, so removing any of them strands its right-hand side. Notice the shape before you start grinding.

This schema returns in Exercise 9.13, once the normal forms are defined.

Consider again the schema ABCDEGHJ and the dependency set F of Exercise 9.3: 
(1)  A  → BC     (4)  B  → E
(2)  B  → D      (5)  E  → H
(3)  DE → G      (6)  GH → J
Is the dependency set F a minimal cover? Explain your answer. If it is not, produce one.

No. Condition 1 requires a single attribute on every right side, and dependency (1) A → BC has two. That one observation is the whole answer to the question as asked.

Producing a minimal cover takes one more step and two checks. Split (1) by the decomposition rule:

A → B,   A → C,   B → D,   DE → G,   B → E,   E → H,   GH → J

Condition 2. Only DE → G and GH → J have more than one attribute on the left. Neither can shed one: under F, D+ = D and E+ = EH, so neither D → G nor E → G holds; likewise G+ = G and H+ = H, so neither half of GH determines J alone.

Condition 3. No dependency is redundant — drop any one of the seven and recompute, and the right-hand side is no longer in the closure of the left. A → C is the clearest case: C appears on no other right-hand side at all, so removing it makes C underivable from anything.

The seven dependencies above are therefore a minimal cover of F.

Splitting is almost always step one and almost never the last step. Here it happened to be enough, but only because the checks in conditions 2 and 3 both came back clean. The checks are the work; the splitting is bookkeeping.

9.7The normal forms

The four forms, as Lecture 16 states them

An attribute is prime if it belongs to some candidate key, and non-prime otherwise. Every normal form below is a sentence about non-trivial dependencies and candidate keys, so you cannot test any of them until you have found all the candidate keys — which is why §9.5 comes first.

FormRequires
1NFevery attribute's domain holds only atomic values, and every attribute of a tuple holds a single value from that domain
2NF1NF, and every non-prime attribute is fully functionally dependent on the key — no non-prime attribute is determined by a proper part of it
3NF2NF, and no non-prime attribute is transitively dependent on the key. Equivalently: for every non-trivial X → A, either X is a superkey or A is prime
BCNFfor every non-trivial X → A, X is a superkey. No escape clause

The second 3NF phrasing is the one to use on paper: it is a loop over F, not a hunt for transitive chains. BCNF is the same loop with the words “or A is prime” deleted, which is why every BCNF schema is automatically in 3NF and the converse fails.

Where they bite. A dependency that violates BCNF stores the same fact twice — one row per occurrence of the left side. 3NF tolerates exactly the violations in which the repeated attribute is itself part of a key, and §9.9 explains what is bought by tolerating them.

Consider again the schema R = ABCDEGHJKLMN and the minimal cover F of Exercise 9.11: 
(1)  A → E     (6)   B → A
(2)  H → C     (7)   K → D
(3)  D → K     (8)   C → N
(4)  M → G     (9)   E → M
(5)  L → J     (10)  G → L

(a) List all dependencies that respect BCNF in R, and prove your listing is correct.
(b) List all dependencies that violate BCNF in R, and prove your listing is correct.

(a) There are none. BCNF asks that the left side of every non-trivial dependency be a superkey of R. Every superkey of R contains BH — that was the first step of Exercise 9.11(b), and it follows from B and H appearing on no right-hand side. But every left-hand side in F is a single attribute, so none of them can contain both. The list is empty.

(b) All ten, which is the same observation read the other way round. Not one dependency in F respects BCNF, so the schema sits at 1NF and nothing higher — 3NF fails too, since the right-hand sides are E, C, K, G, J, A, D, N, M, L and the prime attributes are only B, D, H, K (from the two keys BDH and BHK), so A → E alone already fails both clauses.

A schema in which every dependency violates BCNF is not pathological. It is what a schema looks like when the key is wide and the dependencies are narrow, and it is exactly the case the decomposition algorithm of §9.9 is built for — which is why that algorithm produces one small component per dependency, plus one more to hold the key.

Consider the relational schema R = ABCDE with the following set F of functional dependencies: 
AB → D
E  → C
C  → A

(a) Does the dependency E → A hold in F+? Prove your answer.
(b) Determine if EB is a key of the schema R and prove your answer.
(c) Determine if EA is a key of the schema R and prove your answer.
(d) Is the schema R in BCNF? Prove your answer.
(e) Is the schema R in 3NF? Prove your answer.

(a) Yes — by transitivity on E → C and C → A.

(b) Yes, EB is a key. Both E and B must be in every key, since neither appears on a right-hand side, so no key is smaller. And it is a superkey:

EB  →(E→C)  BCE  →(C→A)  ABCE  →(AB→D)  ABCDE = R

(c) No. EA+ = ACE — E → C fires and then nothing else can, since AB → D needs B. B and D are both missing, so EA is not even a superkey.

(d) No. E → C is non-trivial and E is not a superkey — if it were, EA would be one too, and part (c) says it is not.

(e) No, and this is the part worth reading twice. E → C fails 3NF as well, which needs both escape clauses to fail. E is not a superkey, by (d). And C is not prime: BE is the only candidate key, so the prime attributes are exactly B and E.

Why BE is the only key. Every key contains BE, and BE is itself a key by (b); any proper superset of a key is a superkey, not a candidate key. So there is nothing else to check — and the prime set is settled in one line, which is what (e) needs.

Consider a relational schema R = ABCDEGHJK with the set of functional dependencies F: 
(1)  BC → A     (4)  G → BE
(2)  DB → C     (5)  H → K
(3)  E  → D     (6)  J → H

(a) List all candidate keys for R, stating clearly how many there are altogether, and prove there are no others.
(b) Does R satisfy BCNF? Prove your answer.
(c) Does R satisfy 3NF? Prove your answer.

(a) Exactly one: GJ — this is the schema of Exercise 9.10, and the proof is the one given there. Neither G nor J appears on a right-hand side, so both belong to every key; and GJ+ = R, so no key is larger.

GJ  →(4)  BEGJ  →(6)  BEGHJ  →(3)  BDEGHJ
    →(5)  BDEGHJK  →(2)  BCDEGHJK  →(1)  ABCDEGHJK = R

(b) No. BCNF requires every left-hand side to be a superkey, and every superkey contains GJ. Not one dependency in F has both G and J on the left — in fact none has either, except (4), which has G but not J.

(c) No. Since no left-hand side is a superkey, 3NF falls back on its second clause for every dependency: the right-hand side must be prime. The prime attributes are exactly G and J, because GJ is the only candidate key. Scanning the right-hand sides — A, C, D, BE, K, H — not one of them is G or J. Every dependency fails, so R bears no normal form above 1NF.

Two questions, one piece of work. Parts (b) and (c) are answered entirely from the key found in (a). That is the usual shape of a normalization question, and it is why a wrong or incomplete key list poisons everything downstream.

Consider the relational schema ABCD with the dependency set F: 
AC → B
AC → D
D  → C

(a) Is ABCD in 3NF with respect to F? Prove your answer.
(b) Regardless of your conclusion in part (a), remove one dependency from F so that ABCD is in BCNF with respect to the new set of dependencies. Explain your answer. If this is impossible, prove it.

First, the candidate keys — there are two: AC and AD. A is on no right-hand side, so it is in every key, but A+ = A. Adding C: AC+ = ABCD = R. Adding D:

AD  →(D→C)  ACD  →(AC→B)  ABCD = R

AB+ = AB, so AB is not a key, and both of the above are minimal. The prime attributes are therefore A, C and D; only B is non-prime.

(a) Yes, ABCD is in 3NF. Take the dependencies one at a time. AC → B and AC → D have a candidate key on the left, so they pass on the first clause. D → C does not — D+ = CD, not R — but its right-hand side C is prime, so it passes on the second. No dependency fails, and 2NF holds for the same reason (the only non-prime attribute B is not determined by any proper part of either key: A+ = A, C+ = C, D+ = CD).

(b) Remove D → C. It is the only dependency whose left side is not a superkey, so it is the only BCNF violation; and removing it leaves {AC → B, AC → D}, in which AC is now the only candidate key — without D → C, AD+ = AD — and both remaining dependencies have exactly that key on the left. BCNF holds.

Neither other removal works. Drop AC → B and the keys become ABC and ABD, while D → C survives with a non-superkey left side. Drop AC → D and the only key is AD, so now AC → B violates BCNF as well.

A note on the printed answer

The problem book's hint for part (b) reads “AC is the only key”. That is true of the reduced set, after D → C has gone, and it is the reason the removal works. Under the original F it is not true: AD is a second candidate key, as computed above. Read the hint as describing the answer to (b), not the schema in (a) — and in part (a) do not take “AC is the only key” on faith, because if you did, you would conclude that D is non-prime and that the schema fails 3NF. It does not.

Give an example of a relational schema which is not in BCNF, but is in 3NF, and explain your example. You may use abstract attribute names, and you need not have in mind any reasonable interpretation. If such a schema does not exist, prove it.

The smallest one has three attributes. Take R = ABC with

AB → C
C  → B

There are two candidate keys, AB and AC. A is on no right-hand side, so it is in every key, and A+ = A. Then AB+ = ABC directly, and AC+ →(C→B) ABC. So every attribute is prime.

Not in BCNF: C → B is non-trivial and C+ = BC ≠ R, so C is not a superkey.

In 3NF: AB → C has a key on the left. C → B does not, but B is prime — it belongs to the key AB — so the second clause saves it. No dependency fails, so 3NF holds.

This is the whole gap between the two forms, in one schema. 3NF differs from BCNF only in forgiving a dependency whose right-hand side is part of some key. Any example of the kind the question asks for must therefore contain a dependency shaped exactly like C → B: a non-superkey on the left, a prime attribute on the right. §9.9 returns to this and explains why the forgiveness is worth something.

9.8Judging a decomposition

Splitting a schema is easy; splitting it without breaking something is not. Lecture 16 names the two things a decomposition can break, and each has a test that is a closure in disguise.

The join brings back all five original rows and two more besides — (1,3,4) and (2,3,5) — because B = 3 occurs twice on each side and every combination is produced. Rows that were never in R are now indistinguishable from rows that were. That is the failure mode: not lost data, but invented data, and no query can tell the difference afterwards.

Definition. The decomposition has a lossless join if R₁ ⋈ R₂ = R for every legal content of R. Otherwise R ⊂ R₁ ⋈ R₂ and the join is lossy. Note which way the containment runs: the join is always a superset, never a subset.

Theorem (Lecture 16). For a two-way decomposition, the join is lossless if and only if at least one of

R₁ ∩ R₂  →  R₁
    or
R₁ ∩ R₂  →  R₂

belongs to F+. In practice: intersect the two component schemas, close the intersection, and see whether the result swallows either component. One closure, one comparison, done.

Dependency loss

Given R, a minimal cover F and a decomposition {R₁, …, Rn}, a dependency [X → A] ∈ F is lost if no single component contains all of XA.

A lost dependency is not a lost fact — it still holds of the data. It is a lost constraint: the DBMS can no longer enforce it from inside one table, so an insertion that breaks it can only be caught by joining the pieces back together first. Lecture 16's example is the universal schema City, Street, Zip with Z → C and CS → Z; split off ZC and the second dependency has nowhere left to live.

The two properties are independent. A decomposition can be lossless and lose dependencies, can preserve every dependency and be lossy, can fail both, or can manage both. Exercises 9.18 and 9.19 give you one of each of the first two.

Consider a relational schema R = ABCDEGH with the dependency set F: 
(1)  ABCD → H
(2)  CD   → E
(3)  G    → C
R is decomposed into R₁ and R₂ as follows: 
R₁ = ABCDH          R₂ = CDEG

(a) Does this decomposition have a lossless join? Prove your answer.
(b) Does this decomposition preserve dependencies? Prove your answer.
(c) Which — if any — of the highest normal forms (BCNF, 3NF) is attained by the component schema R₁? Prove your answer.
(d) The same question for R₂.

(a) No, the join is lossy. The components overlap in CD, and

CD  →(2)  CDE  =  CD⁺

Neither component fits inside that: ABCDH ⊈ CDE and CDEG ⊈ CDE. Both conditions of the theorem fail, so the join is lossy.

(b) Yes, every dependency survives. (1) ABCD → H has all five attributes inside R₁ = ABCDH; (2) CD → E and (3) G → C both fit inside R₂ = CDEG. Nothing is split.

(c) R₁ is in BCNF, and therefore in 3NF as well. Of the three dependencies only (1) holds inside ABCDH — (2) and (3) mention E and G, which are not there. And the left side of (1) is ABCD, which is the candidate key of this component: ABCD+ = ABCDH = R₁, and no proper subset reaches H. A single dependency whose left side is the key satisfies BCNF by definition.

(d) R₂ attains neither. Inside CDEG the surviving dependencies are (2) CD → E and (3) G → C. The only candidate key is DG: neither D nor G appears on a right-hand side, so both are forced, and DG+ = CDEG = R₂. Now look at (3): its left side G is not a superkey, so BCNF fails; and its right side C is not prime — the only key is DG — so 3NF fails too. The component bears no normal form above 1NF.

This is the lesson of §9.8 in one exercise. The decomposition preserves every dependency and still destroys the data, and one of its two components is worse normalized than you would want. Preservation, losslessness and normal form are three separate questions, and a decomposition has to answer all three before it is worth writing down. §9.9 is the algorithm that answers all three by construction.

9.9Decomposing properly

Everything so far has been a test applied to a decomposition someone else wrote down. Lecture 16 ends with the two constructions that produce one, and with an honest account of what each can and cannot promise.

Decomposition into BCNF

Input: a schema R and a minimal cover F. Output: a decomposition in which every component is in BCNF.

let  X → A  be a dependency that violates BCNF in R
decompose R into   R₁ = XA   and   R₂ = R − A
continue on R₁ and R₂ as needed

Why X → A never troubles you again. In R₁ it cannot: X+ = XA = R₁, so X is a superkey there and BCNF holds. In R₂ it cannot either, because R₂ no longer contains A, so the dependency is not even expressible. Each step removes one violation for good, and the attribute count strictly decreases, so the process stops.

Each split is lossless — the intersection of the two halves is X, and X → A gives X → R₁, which is exactly the theorem's first condition. So the whole construction is lossless, step by step.

What it does not promise is dependency preservation, and Lecture 16's CollegeDB run shows it going wrong. Decomposing SNACEDPFTMKLHYG by the dependencies S → NA, T → MK, DP → F, C → ED, CY → TLH, Y → P, SCY → G in a different order strands DP → F: by the time its turn comes, D, P and F no longer sit together in any component, and the constraint is lost. The order in which you take the violations matters, and the algorithm gives you no rule for choosing it.

The modified algorithm — 3NF by synthesis

The fix is to stop decomposing and start building, one component per dependency.

Input: a schema R and a minimal cover F. Output: a decomposition that is lossless, preserves every dependency, and has every component in at least 3NF — all three, guaranteed.

1.  any attribute appearing in no dependency of F gets a table of its own
2.  for each dependency  X → A  in F, build the component  XA
3.  if some component already contains a candidate key of R, stop;
    otherwise add one more component consisting of a candidate key of R

Step 3 is what buys the lossless join, and it is the step students drop. Without it the pieces need not rejoin: the key component is the spine that every other component can be joined back onto.

Step 2 is what buys dependency preservation, trivially — every dependency of F has a component built to hold exactly its attributes, so none can be lost. This is also why the input must be a minimal cover and not just any equivalent set: condition 1 of minimality keeps the components small, and condition 3 keeps you from building components nobody needs.

The price is 3NF rather than BCNF. A component XA built from X → A is in 3NF but may fail BCNF if some other dependency of F+ happens to hold inside it. That is the trade the next three exercises are about: BCNF buys zero redundancy from functional dependencies but may cost a constraint; 3NF keeps every constraint but may leave some redundancy behind. You cannot always have both.

Consider again the schema R = ABCDEGH and dependency set F of Exercise 9.19: 
(1)  ABCD → H
(2)  CD   → E
(3)  G    → C
Since the decomposition of Exercise 9.19 was found wanting, propose a better one, and prove that it is better. If it is impossible to construct a better decomposition, prove that.

First check the input. F is already a minimal cover: every right side is a single attribute; ABCD → H cannot shed a left attribute (BCD+ = BCDE, ACD+ = ACDE, ABD+ = ABD and ABC+ = ABC, none reaching H), nor can CD → E (C+ = C, D+ = D); and no dependency is redundant, since H, E and C appear on only one right side each.

Now run the algorithm. Step 1: every attribute of R occurs somewhere in F, so nothing is set aside. Step 2 gives one component per dependency:

X₁ = ABCDH          X₂ = CDE          X₃ = GC

Step 3: is a candidate key of R inside one of those? The only candidate key is ABDG — A, B, D and G appear on no right-hand side, so all four are forced, and

ABDG  →(3)  ABCDG  →(1)  ABCDGH  →(2)  ABCDEGH = R

No component contains ABDG, so add a fourth:

X₄ = ABDG

Why this one is better, on all three counts.

Lossless. Guaranteed by step 3, which is exactly what the decomposition of Exercise 9.19 was missing.

Dependency-preserving. Guaranteed by step 2: (1) lives in X₁, (2) in X₂, (3) in X₃.

Normalized. The algorithm promises 3NF, and here it happens to deliver BCNF in all four. In X₁, X₂ and X₃ exactly one dependency holds, and its left side is that component's key. In X₄ = ABDG no dependency holds at all — none of the three has its whole attribute set inside it — so BCNF is satisfied vacuously.

The fourth component looks pointless and is the only reason the first three work. ABDG stores no dependency and enforces no constraint; it exists so that the join has something to hang on. Leave it out and you are back to Exercise 9.19.

Consider the relational schema R = ABCDEGH with the same dependency set F: 
(1)  ABCD → H
(2)  CD   → E
(3)  G    → C
This time R is decomposed into three schemas: 
R₁ = ABCDH          R₂ = CDE          R₃ = GC

(a) For each of the three components, determine whether it is in BCNF, and prove your answer.
(b) For each component you found not to be in BCNF, determine whether it is in 3NF, and prove your answer.
(c) Does this decomposition have a lossless join? Prove your answer.
(d) Does this decomposition preserve dependencies? Prove your answer.
(e) If your answer to either (c) or (d) is no, propose a better decomposition and prove that it is better. If this is impossible, prove it.

(a) All three are in BCNF. Exactly one dependency of F holds inside each component — (1) in R₁, (2) in R₂, (3) in R₃ — and in each case its left side is precisely the key of that component: ABCD+ = ABCDH, CD+ = CDE, G+ = CG.

(b) Nothing to do, since no component failed (a). Every BCNF schema is in 3NF anyway.

(c) No, the join is lossy. Consider the step that produces R₃ = GC. The attribute G appears in no other component, so the intersection of R₃ with any other schema at any stage can only be C. But C+ = C, so C determines neither R₃ nor any other piece, and the theorem's condition fails at that step. One bad step is enough: the join of the three is lossy.

(d) Yes. Dependency (k) is preserved in component Rk, for each of k = 1, 2, 3, by construction — this decomposition is precisely step 2 of the algorithm.

(e) Add the key. F is already a minimal cover and R₁, R₂, R₃ are already what step 2 produces. All that is missing is step 3: no component contains a candidate key of R. The only candidate key is ABDG, the four attributes that never appear on a right-hand side, and ABDG+ = R. So the repaired decomposition is

R₁ = ABCDH     R₂ = CDE     R₃ = GC     R₄ = ABDG

R₁ to R₃ remain in BCNF, and R₄ is vacuously in BCNF since no dependency holds in it. By the theorem the join is now lossless, and dependency preservation was never in question.

Compare this with Exercise 9.20 and notice they end in the same place. There, a two-way split was thrown away and the algorithm run from scratch; here, three quarters of the algorithm's output was handed to you and only the last step was missing. The repair is the same component either way, which is a good sign you have understood what step 3 is for.

A subtlety in part (c)

The answer above judges R₁ by the dependencies of F that syntactically fit inside it, which is the standard reading and gives ACHJ as the only key. If instead you project the whole of F+ onto R₁ — keeping every dependency that holds among R₁'s attributes, including ones proved through attributes outside it — then ABHJ is a second key of R₁, since ABHJ → E → C by (3) and (2). The conclusion in (c) is unaffected: dependency (1) still violates 3NF, because under either reading AC is not a superkey and B is not prime. But if an exam question asks for “all candidate keys of the component”, say which reading you are using.

(a) Explain the advantages of decompositions into 3NF, compared to decompositions into BCNF. If such advantages do not exist, explain why.
(b) Explain the disadvantages of decompositions into 3NF, compared to decompositions into BCNF. If such disadvantages do not exist, explain why.

(a) 3NF decompositions keep every constraint; BCNF ones may not. A correct decomposition into BCNF is guaranteed to have a lossless join — that falls out of the construction, as the box above shows — but it carries no guarantee of dependency preservation, and Lecture 16's CollegeDB run is a worked case of it losing one. The 3NF algorithm guarantees both: lossless join from step 3, dependency preservation from step 2. That is the advantage, and it is the only one.

(b) 3NF schemas may still carry redundancy; BCNF ones do not. BCNF eliminates every redundancy that arises from a functional dependency, because no non-superkey is ever allowed to determine anything. 3NF forgives exactly the dependencies whose right-hand side is prime, and each one forgiven is a fact that will be stored more than once. (Neither form says anything about redundancy arising from multi-valued dependencies, which is a separate machinery.)

The trade, in one sentence. BCNF buys a cleaner table at the risk of a constraint the DBMS can no longer check from inside one relation; 3NF keeps every constraint checkable at the price of some repetition. Which is worse depends on the database, which is why both algorithms are in the lecture and neither is called the right one.

Where to look for the forgiven dependency. It is the shape of Exercise 9.17: a non-superkey on the left, a prime attribute on the right. If a 3NF schema contains no dependency of that shape, it is in BCNF too, and the question does not arise.
