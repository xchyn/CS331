Index files and B-trees

Set 11 ended with a file that answers a lookup in six days unless it happens to be sorted on the field you are looking up. This set is the way out: a small second file, sorted on whatever field you like, with a pointer back into the first. Ten exercises from the problem book, every one of them the same six lines of arithmetic applied to a different index.

Nothing here is new machinery. An index is a file, with records, occupying blocks, searched the same way any file is searched — so every formula of Set 11 applies to it unchanged. What is new is that the file is small, and that you get to choose what it is sorted on.

12.1Why an index, and what one is

The problem, and the wrong fix

When a file is sorted on one of its fields, the other fields are not sorted. So how do you search when the field you are searching on is unsorted?

The obvious answer is to keep several copies of the data, each sorted on a different field. It is wrong on three counts: it is expensive in time, expensive in space, and — the one that actually disqualifies it — the copies are hard to keep consistent with one another. That is redundancy, which Sets 9 and 10 spent their time removing, and it leads to the same place: a database that says two contradictory things.

The right answer is an indexing structure. An index is used to speed up the retrieval of records in response to certain search conditions — except when the file is very small, in which case it can simply be read into memory. The guarantee it gives is worth stating precisely:

An index guarantees that no data block is fetched unless it is relevant.

Not “fetches fewer blocks” — fetches no irrelevant block at all. Sequential search reads 228 blocks to find one record and 228 − 1 of them are irrelevant; that is the waste the index removes.

An index is a file with two fields

An index is a file that has exactly two fields: the index field and a block pointer. The pointer holds the logical address of the data block that contains the index field of a given value.

How long is a pointer? k bits distinguish 2k things, so addressing B blocks needs

⌈lg B⌉ bits

and nothing more. Lecture 20's example: a file of 228 blocks with an 8-byte index field. lg B = 28 bits, which is under 4 bytes, so

ℓP  =  8 + 4  =  12 B

Round the pointer up to a whole number of bytes, then round the record up to a power of two if the arithmetic wants it. The problem book does both and says so; 12 bytes becomes 16 = 24 in most of the exercises below, and stays 12 in none of them. Where a record length is not a power of two — Exercise 12.5 has one — the formulas are unchanged and only the arithmetic gets uglier.

12.2The three kinds, and sparse against dense

Which index you are allowed to build
#KindBuilt on
1primary indexthe ordering key field of an ordered file of records
2clustering indexthe ordering field, when several records in the file can share one value of it
3secondary indexany nonordering field of a file

Two questions settle which one you are looking at, and they are independent: is the file sorted on this field? and is this field a key?

field is a keyfield is not a key
file sorted on itprimaryclustering
file not sorted on itsecondarysecondary, through a bucket

A file has at most one ordering field, so it has at most one primary or clustering index and any number of secondary ones. That asymmetry is the whole reason the secondary index exists, and it is where the cost lies.

Sparse and dense — and the two counting rules
Index isWhen it holds
sparseone index record for each data block
denseone index record for each data record

A primary index can be sparse and a secondary index cannot. The reason is the sorting. If the data file is sorted on the index field, the first value in each block tells you everything about that block, so one pointer per block suffices. If it is not sorted, a value could be anywhere, and every record needs its own pointer.

That gives the two rules Lecture 21 states, and they decide every exercise on this page before any arithmetic starts:

primary index:    one pointer per block    →   TP  =  BF
secondary index:  one pointer per record   →   TS  =  TF

Since a block holds many records, TS is larger than TP by that factor — often a hundred or a thousand. A secondary index is bigger than a primary one on the same file, even when its index field is shorter, and that extra size is what makes its B-tree a level or two deeper.

When the index field is not a key

A secondary index on a field that is not a key cannot have one pointer per index value, because one value may occur in many records. Lecture 21's answer is an intermediate block: the index record points at a block of pointers, and that block points at the data records. A clustering index does the same thing more cheaply, because the file is sorted on the field, so all the matching records sit together and one pointer to the first of them is enough.

Every index in the exercises below is on a key, so the intermediate block never appears in the arithmetic. Know that it exists, and know why: a question that says “assume that this field is an alternate key” — as Exercises 12.8 and 12.9 do — is saying it so that you may leave the bucket out.

(a) In estimates of the cost of database accesses, which operations are counted, and why?
(b) Explain the difference between a dense index and a sparse index.
(c) Explain the difference between a primary index and a secondary index.
(d) What is a bit map index?
(e) What is a secondary index?

(a) Block accesses to the secondary storage are counted, as their duration exceeds by several orders of magnitude the time required to perform any in-memory operation. That is the ratio of §11.1 — about 105 — and it is why everything on this page is measured in tb and nothing in instructions.

(b) A dense index has an index entry for each record in the data file. A sparse index normally has one index entry for each block of the data file, which may contain several data records.

(c) An index is primary if its index field is the ordering field of the data file; otherwise it is secondary.

(d) A bit-map index is an array indexed by a row id, which contains a short bit-string encoding of the value of the indexing field for that row.

(e) A secondary index is an index on a non-ordering field.

The two definitions that get confused are (b) and (c), and they are not the same distinction. Dense/sparse is about how many entries the index has; primary/secondary is about which field it is on. They are linked in one direction only: a sparse index has to be primary or clustering, because only a sorted field lets one entry speak for a whole block. The converse fails — a primary index may be dense, with one entry per record, and §12.4 will show that costs a level of B-tree for nothing.

12.3From the binary search tree to the B-tree

Why the obvious tree is the wrong one

A binary search tree has one property, stated twice:

  • the value at any node is greater than any value in the subtree rooted at its left child;
  • the value at any node is smaller than any value in the subtree rooted at its right child.

Search time is the height of the tree, which is lg n at best — a balanced tree — and n at worst, when the values arrive already sorted and the tree degenerates into a list. The classical fix is to rebalance as you go, which gives the AVL tree.

And it is still the wrong structure here, for the reason §11.2 gave: the unit of transfer is a block. A binary node holds one value and two pointers — a few dozen bytes — so a tree of 222 values costs 22 block accesses, each of which fetches a 4-kilobyte block in order to read twelve bytes of it. The structure wastes 99.7% of every transfer it makes.

The B-tree

A B-tree is a balanced search tree whose nodes fit into a data block. Two properties:

#Property
1all leaves are at the same level
2every internal node is at least half full

Each node holds n values and n + 1 pointers, laid out alternately, with the subtrees interleaved between the values:

T₀  <  V₁  <  T₁  <  V₂  <  T₂  <  V₃  <  T₃  <  …  <  Tₙ₋₁  <  Vₙ  <  Tₙ

Property 1 is what makes the depth a single number — every search costs exactly the height, never less and never more. Property 2 is what bounds that height: a node that is at least half full has at least half the maximum number of children, so the tree cannot be made tall by sparse nodes. Together they are the whole of §12.4's formula.

The tree grows at the root, not at the leaves, and that is how property 1 survives. When a leaf overflows it splits into two leaves at the same level and pushes one value up; the only way the height ever increases is when that push reaches a full root and splits it. So the leaves all stay level by construction, for free.

Notice that the keys arrive in sorted order — A, then B, then C — the case that degenerates a binary search tree into a list. The B-tree is three levels deep after nine of them, and would be three levels deep after nine million.

12.4How deep, and how long

Six lines, in this order

Everything in §12.5 is this, with different numbers. BF and TF are the data file's blocks and records, from Set 11; b is the block size.

ℓi  =  index field  +  block pointer           round up

Ti  =  BF   for a primary index
     =  TF   for a secondary index

Bi  =  Ti · ℓi / b                           the index in blocks

Δmax  =  b / ℓi                            pointers per full node
Δmin  =  Δmax / 2                           at least half full

hmax  =  ⌈ lg Bi / lg Δmin ⌉                 the depth of the B-tree

t    =  (hmax + 1) · t​b                    descend, then one data access

The + 1 is the data block. The B-tree delivers a pointer, not a record; one more access turns the pointer into the row. Leave it out and every answer is short by one block access.

The depth formula is the multiway-merge formula of §11.5 wearing a different hat. There, R = ⌈lg B / lg M⌉ counted how many times you can multiply a run by M before it covers the file; here, h = ⌈lg Bi / lg Δmin⌉ counts how many times you can multiply a subtree by Δ before it covers the index. Both are “how many factors of x fit into y”, and both are tiny — 2, 3 or 5 in every exercise below.

Lecture 21's worked example, four ways

The file of §11.5: four fields of 8, 8, 16 and 32 bytes, 64 billion records, 4-kilobyte blocks, block access time 1/256 s.

ℓ   =  8 + 8 + 16 + 32  =  64  =  2⁶ B
T   =  64 billion  =  2³⁶ records
b   =  4 KB  =  2¹² B                 t​b  =  2⁻⁸ s

BF  =  Tℓ / b  =  2³⁶⁺⁶⁻¹²  =  2³⁰ blocks

Without an index, if the file happens to be sorted on the field you want:

binary search on F:   (lg BF + 1) · t​b  =  31 · 2⁻⁸  <  2⁵ · 2⁻⁸  =  1/8 s

With a primary B-tree index P on the ordering key A — 8 bytes, plus a pointer that must address 230 blocks and so needs 30 bits, under 4 bytes:

ℓP    =  8 + 4  =  12  ≤  16  =  2⁴ B
TP    =  BF  =  2³⁰                    one index record per data block
BP    =  TP · ℓP / b  =  2³⁰⁺⁴⁻¹²  =  2²² blocks

Δmax  =  b / ℓP  =  2¹² / 2⁴  =  2⁸         Δmin  =  2⁷
hmax  =  ⌈ 22 / 7 ⌉  =  4

t     =  (4 + 1) · t​b  =  5 · 2⁻⁸  ≈  20 ms

The index is a twohundredandfiftysixth of the file — 222 blocks against 230 — because each index record stands for a whole data block and is a quarter the length of a data record. That ratio is where all the speed comes from, and it is why the formula starts at TP = BF.

And the index can be sorted on a field the data file is not. Lecture 21 makes the point by costing what it takes to sort an index on B, the second field, which is unordered in the data file. The index has one record per data record — it is secondary, so Ti = TF = 236 — and with ℓi = 24 that is 228 blocks. With 4 gigabytes of memory, M = 220 blocks and R = ⌈28/20⌉ = 2, so

t  =  2 · R · Bi · t​b  =  2 · 2 · 2²⁸ · 2⁻⁸  =  2²² s  ≈  48 days

which is Set 11's arithmetic, applied to the index instead of the file — and it is 48 days instead of the 192 the data file itself would cost, because the index is four times smaller.

The four procedures, ranked

Every search question on this page has one of these four answers, and the job is to say which case you are in before computing anything:

ProcedureAllowed whenCost
sequential searchalwaysBF · tb
binary search on Fthe file is sorted on the field(lg BF + 1) · tb
binary search on the indexthere is an index on the field, stored as a sequential file(lg Bi + 1) · tb
descend the B-treethere is an index on the field, implemented as a B-tree(hmax + 1) · tb

Rows three and four are the same index, stored two ways, and Lecture 21 costs both on its second example: (17 + 1) · 2−6 ≈ 280 ms against (3 + 1) · 2−6 ≈ 63 ms. The B-tree is not faster because it is a tree; it is faster because its fan-out is 28 and binary search's is 2. Halving 217 blocks takes 17 steps; dividing them by 28 takes 3.

12.5Exercises

Nine exercises on three databases. Each of the last six gives you a data file and an index and asks for the same six lines; the differences between them are worth more attention than the arithmetic, because they are what the questions are really testing.

(a) A file occupies K blocks of the secondary storage and has a B-tree index on field F with p pointers per index record. Give an estimate of the cost of locating a record by its index field F. Explain your answer briefly.
(b) A talented administrator has invented a way to pack 2p pointers in an index record. Give an estimate of the resulting relative speedup in the cost of locating a record by its index field F. Explain your answer briefly.

(a) It is safe to assume that an individual record of the index file occupies an entire block. Hence there cannot be more than p data records per block — in fact this is probably a considerable over-estimate, as a data record is probably much longer than an index entry. We arrive at a total of no more than Kp data records, yielding an index depth of logp Kp. Allowing one access for the data record itself, we obtain an upper bound:

1 + logP Kp  =  1 + logP p + logP K  =  2 + logP K

(b) By the answer to (a), the ratio of the old and the new access times is

 2 + logP Kp        logP Kp
---------------  ≈  -------------  =  logP 2p  =  logP p + logP 2  =  1 + 1/lg p  ≈  1
2 + log₂P Kp       log₂P Kp

Even for modest values of p — say p = 128 = 27 — the estimated decrease in access time is less than 15%.

This is the same answer as Exercise 11.9, and for the same reason. There, doubling the memory bought almost nothing because memory enters the sorting cost only as the base of a logarithm. Here, doubling the fan-out buys almost nothing because fan-out enters the search cost only as the base of a logarithm. In both cases the quantity you are improving is already raised to a power that has made it enormous, and doubling it adds one to the exponent.

What this does not say is that fan-out does not matter. Going from p = 2 — a binary tree — to p = 256 divides the depth by 8, which is the whole of §12.3's argument. Going from 256 to 512 divides it by 9/8. The first doubling is free and the eighth is worthless; the formula 1 + 1/lg p says exactly where the curve flattens.

Continue with the Research Lab database and the index P of Exercise 12.3.

(a) Estimate the maximum number of pointers per node of the B-tree that implements the index P.
(b) Estimate the minimum number of pointers per node of that B-tree.
(c) Calculate the maximum depth of the B-tree that implements P.
(d) Describe an adequate procedure to search the file project for all records where the value of the field projId is equal to 99887766554433, and estimate the worst-case running time of the procedure that you propose.

(a) A node fills one block, and each pointer comes with its index record:

Δmax  =  b / ℓP  =  2¹⁶ / 2⁴  =  2¹²

(b) By property 2 of §12.3, every internal node is at least half full:

Δmin  =  ½ · Δmax  =  2¹²⁻¹  =  2¹¹

(c) The worst case is the tree in which every node is only half full, so the depth is taken against Δmin:

hmax  =  ⌈ lg BP / lg Δmin ⌉  =  ⌈ 13 / 11 ⌉  =  2

(d) Descend the B-tree of the primary index P, followed by one data access.

t  =  (hmax + 1) · t​b  =  (2 + 1) · 2⁻⁸  =  12 · 2⁻¹⁰  <  12 ms

Two levels for two terabytes. A node holds 211 pointers even when half empty, so two levels reach 222 blocks and the index is only 213. The tree is nowhere near full, and that is normal: the depth jumps in whole steps and almost every real index sits well inside a step.

Compare the three ways of answering (d). Sequential search would cost B · tb = 225 · 2−8 = 217 s, about a day and a half. Binary search on the sorted data file would cost (25 + 1) · 2−8 ≈ 102 ms. The B-tree costs 12. Each step down that list costs a structure that has to be built and maintained, and buys about an order of magnitude.

Refer to the Mail-Order Bookstore database, whose customer table is declared

Assume that every character occupies a single byte on disk, while every decimal or date occupies 11 bytes. Block size is equal to 2 kilobytes, and block access time is equal to 1/512 seconds. The Bookstore has reached its goal and has 8 billion customers, so that the table customer occupies B = 228 blocks (Exercise 11.6).

(a) Explain the record structure and find the record size of the primary index for the table customer.
(b) Calculate the number of blocks occupied by that primary index.
(c) Assuming the index is implemented as a B-tree, calculate the depth of this B-tree.
(d) Calculate the worst-case time to look up a customer by email address.

(a) Every primary-index record consists of an index field emailC and a block pointer. The block pointer must address 228 blocks, so it needs at least 28 bits, which rounds up to 4 bytes. The emailC field is 36 bytes long. Hence

ℓP  =  36 + 4  =  40 B

(b) One index record per data block:

TP  =  B  =  2²⁸

BP  =  TP ℓP / b  =  2²⁸ · 5 · 2³ / 2¹¹  =  5 · 2²⁰ blocks

(c) The worst-case depth corresponds to all nodes being only half full, so the number of index records per block is

Δ  =  ⌈ ½ · b / ℓP ⌉  =  ⌈ ½ · 2¹¹ / (5 · 2³) ⌉  =  ⌈ 2⁷ / 5 ⌉  =  26

h  =  ⌈ lg BP / lg Δ ⌉  =  ⌈ 22.32 / 4.70 ⌉  =  ⌈ 4.75 ⌉  =  5

(d) h block accesses to navigate the index, plus one access to the data file, at tb = 2−9 seconds:

t  =  (h + 1) · t​b  =  6 · 2⁻⁹  =  6/512 s  <  12 ms
A note on the printed answer

Neither ℓP nor BP is a power of two here, so the exponents cannot simply be added and the book brackets the logarithms instead of evaluating them. It bounds lg BP between 22 and 23 and lg Δ between 4 and 5, which gives

h  ≤  ⌈ 23 / 4 ⌉  =  6        h  ≥  ⌈ 22 / 5 ⌉  =  5

and takes the conservative end, h = 6, for a lookup time of 7 · 2−9 < 14 ms. The exact ceiling is 5, as computed above, so the two answers differ by one block access — under 2 ms. Either is creditable if the working is shown; what is not creditable is an answer that quietly treats 40 as 32 or 64 and reports a power of two.

This is the one exercise on the page where the numbers are ugly, and it is worth doing for that reason. The six lines of §12.4 do not assume anything is a power of two; the powers of two are a convenience of the other questions, not a property of the method.

This index is half the size of the table it indexes, where the primary index of Exercise 12.5 was a fiftieth. Both facts come from the same rule: TP = B but TS = T, and there are 32 customer records to a block. A secondary index is never cheap.

Two notes on the printed answer

Lecture 21's formula is hmax = logΔmin Bindex, which is what is used above and which the book itself uses in Problems 52, 58, 59 and 60. The difference is one block access, and it is the same one: the record count overcounts by exactly the records-per-block factor.

The book's DDL also reads on customer (name), but Appendix B.20 declares the column nameC. The statement above uses the declared name, so it will actually run.

(f) Describe an adequate procedure to search the file professor for all records where wizardID is equal to 98765432, and estimate the worst-case running time.
(g) The same, for all records where socSecNum is equal to 23456789.

(a) socSecNum, the primary key, which is the field the data file is ordered on.

(b) First the data file:

ℓ  =  16 + 16 + 16 + 4 + 4 + 8  =  64  =  2⁶ B
T  =  1 billion  ≈  2³⁰ records
b  =  32 KB  =  2⁵ · 2¹⁰  =  2¹⁵ B

B  =  Tℓ / b  =  2³⁰⁺⁶⁻¹⁵  =  2²¹ blocks

and then the index, one record per data block:

TP  =  B  =  2²¹

(c) The record length is the sum of the lengths of the key socSecNum and a block pointer. Since there are 221 blocks, 3 bytes (24 bits) are sufficient for the block pointer:

ℓP  =  16 + 3  =  19        rounded up to a power of 2,   ℓP  =  32  =  2⁵ B

(d)

BP  =  TP ℓP / b  =  2²¹⁺⁵⁻¹⁵  =  2¹¹ blocks

(e)

Δmax  =  b / ℓP  =  2¹⁵⁻⁵  =  2¹⁰        Δmin  =  2⁹

hmax  =  ⌈ lg BP / lg Δmin ⌉  =  ⌈ 11 / 9 ⌉  =  2

(f) Sequential search of the data file, since there is no index on wizardID and the file is not ordered on it:

t  =  B · t​b  =  2²¹ · 2⁻⁷  =  2¹⁴ s  >  4 hours

(g) Descend the B-tree of the primary index P, followed by one data access:

t  =  (hmax + 1) · t​b  =  (2 + 1) · 2⁻⁷  =  24 · 2⁻¹⁰  <  24 ms

Parts (f) and (g) are the same file, the same size, the same hardware, and the same question about one record. Four hours against 24 milliseconds, and the only difference is which field is named. An index makes exactly one field fast; every other field is as slow as it ever was, and that is why a schema ends up with several indexes and why each of them has to be paid for.

The pointer is 3 bytes here and 4 in Exercise 12.3, because this file has 221 blocks and that one had 225. Size the pointer from ⌈lg B⌉ every time; it is the one quantity in the six lines that depends on the answer to an earlier line.

Refer again to the Professor Payroll database, with the field lengths of Exercise 12.7. Assume now that the maximum capacity of this database allows about 4 billion professors, and that it is filled to capacity. Block size is equal to 16 kilobytes, block transfer time is equal to 1/256 seconds, and 16 gigabytes of primary memory are available. In this problem only, assume that wizardID is an alternate key of table professor, and that a B-tree index W is built for table professor on the field wizardID.

(a) Is the index W primary or secondary?
(b) Estimate the number of records, the record length, and the number of blocks of the file W.
(c) Estimate the maximum and minimum number of pointers per node of the B-tree that implements W, and calculate its maximum depth.
(d) Describe an adequate procedure to search the file professor for all records where wizardID is equal to 98765432, and estimate the worst-case running time.
(e) The same, for all records where salary is equal to 123456.

(a) Secondary, and not clustering, since table professor is ordered on its primary key socSecNum, hence not on wizardID.

(b)

TW  =  T  =  4 · 2³⁰  =  2³²              one index record per data record

ℓW  =  8 + 8  =  16  =  2⁴ B                wizardID is an alternate key

b   =  16 KB  =  2⁴ · 2¹⁰  =  2¹⁴ B

BW  =  TW ℓW / b  =  2³²⁺⁴⁻¹⁴  =  2²² blocks

(c)

Δmax  =  b / ℓW  =  2¹⁴⁻⁴  =  2¹⁰        Δmin  =  2⁹

hmax  =  ⌈ lg BW / lg Δmin ⌉  =  ⌈ 22 / 9 ⌉  =  3

(d) Descend the B-tree of the secondary index W, followed by one data access:

t  =  (3 + 1) · t​b  =  4 · 2⁻⁸  =  16 · 2⁻¹⁰  <  16 ms

(e) Sequential search, since there is no index on salary:

B  =  Tℓ / b  =  2³²⁺⁶⁻¹⁴  =  2²⁴ blocks

t  =  B · t​b  =  2²⁴ · 2⁻⁸  =  2¹⁶ s  ≈  18 hours

Three levels here, two in Exercise 12.7, and the index is on the same field of the same table. The file is 32 times bigger (232 records against 227) and the blocks are half the size, so BW is 222 against 216 while Δmin falls from 210 to 29. Depth grows like the logarithm of the file divided by the logarithm of the fan-out, so a thirty-twofold file costs one extra level, and a billionfold file would cost three.

Smaller blocks make the tree deeper, twice over. Halving b doubles BW and halves Δmax, so it adds 1 to the numerator and subtracts 1 from the denominator of the depth formula. It is the only quantity in the six lines that pushes in both directions at once.

Consider a stored file F, which consists of fixed-length records. The block size is equal to 4 kilobytes, and the block access time is approximately 1/64 seconds. File F occupies 256 gigabytes of storage space but is expected to grow. Two gigabytes of core memory are available. The record structure of the file is: the primary-key field K whose length is equal to 6 bytes, and two additional fields: field A whose length is equal to 122 bytes, and field B whose length is equal to 128 bytes. The file F has a primary index P.

Describe an adequate procedure to sort the file F according to the field A, estimate the running time of the procedure that you propose, and explain your analysis.

Multiway merge sort — the primary index P is on K and is of no use for ordering by A. The file size is given directly, so the block count comes straight from it:

b   =  4 KB  =  2² · 2¹⁰  =  2¹² B
t​b  =  1/64 s  =  2⁻⁶ s

BF  =  256 GB / b  =  2⁸ · 2³⁰ / 2¹²  =  2²⁶ blocks

M   =  2 GB / b  =  2³¹ / 2¹²  =  2¹⁹ blocks
R   =  ⌈ lg BF / lg M ⌉  =  ⌈ 26 / 19 ⌉  =  2 rounds

t   =  2 · R · BF · t​b  =  4 · 2²⁶ · 2⁻⁶  =  2²² s

which is between 40 and 50 days. Each of the two rounds reads and writes the entire file once, which is the 4 · BF · tb the book writes.

The record structure is given and is not used. 6 + 122 + 128 = 256 bytes per record would let you compute T, which the question never asks for — the size of F arrives in gigabytes, so BF is a division and nothing else. Reaching for ℓ and T out of habit is how a four-line answer becomes an eight-line one with a rounding error in it.

And the index is given and is not used either. That is the point of mentioning it: a primary index on K says the file is sorted on K, which tells you nothing whatever about A. The only thing it rules out is the cheap answer — the file is already sorted, so there is nothing to do — and it rules it out for the wrong field.

This is Set 11's exercise with Set 12's furniture around it, and it is here as the reminder that an index does not make a sort cheaper. It makes one kind of lookup cheaper. Sorting still costs 2 · R scans, every time.

What this set has not asked: what an insertion costs once all those indexes exist, or how the B-tree is kept balanced when records are deleted rather than added. Every index that makes a read faster makes a write slower, and §12.3's split was only half the story.
