Queries as logical rules

A third query language, after the algebra of Set 5 and the SQL of Sets 6 to 8, and the shortest of the three to learn: a query is a rule, a rule has a head and a body, and the body is a list of table names with variables in their columns. Sixteen exercises from the problem book on five databases, four of which you have already queried in SQL.

Nothing here is new information about databases. Every query on this page could be written in the algebra or in SQL, and many of them already were, in earlier sets. What changes is how you say it — and the saying turns out to be shorter than either.

10.1Predicates and rules

What Datalog is

Datalog is a declarative logic programming language designed for databases. Logic programming is the paradigm built on symbolic logic — predicate calculus: the programmer states logical rules describing the relationships between objects, and the machine uses those rules to deduce answers.

The word that matters is declarative:

StyleYou specifyOn this site
declarativewhat has to be accomplishedSQL, Datalog
proceduralhow to perform every stepthe relational algebra

Set 5's algebra tells the machine to take this product, then select these rows, then project these columns, in that order. SQL and Datalog describe the answer and leave the order to the system. That is the same distinction Lecture 10 drew between the algebra and SQL, and Datalog sits on the SQL side of it.

Predicates are tables

The two building blocks of logic programming are predicates and rules.

A predicate is a statement expressing a relationship between one or more objects. In a database the correspondence is exact:

the name of the predicatethe name of the table
the variables of the predicatethe columns of the table
R(x, y, z) is truethe row [x, y, z] is in R

A rule is a logical statement defining a relationship between predicates. It is written head ← body: the head names the predicate being derived, the body states the conditions that must hold for it to be true. Taking the lecture's rule against the table above:

P(x)  ←  R(x, y, 6)  and  y < 5

Read it left to right as a definition and right to left as a search: a row x belongs to P whenever R holds some row whose first column is x, whose third column is 6, and whose second column is below 5. Two rows of R end in 6; of those, [4,5,6] fails y < 5 and [2,4,6] passes. So P holds one row:

P
x
2

Three things that take practice. A constant written in an argument position, like the 6 above, is a condition, not a name. The same variable written twice means the two positions must be equal — which is how Datalog does everything the algebra does with a product and a selection. And the number of arguments must match the number of columns, every time, which is why the schema sits beside you while you write.

Notation, as Lecture 17 writes it

The arrow is ←, written :- in some systems and <-- in the problem book. Conditions in the body are separated by and. Comparison is =, !=, <, >, ≤, ≥. A string constant is written in single quotes.

The head predicate is usually called R or Result; both appear in the problem book and the two are interchangeable. This page uses Result wherever a program has more than one rule, so that the auxiliary predicates of §10.5 are easy to tell apart from the answer.

Variable scope is local to one rule — head and body together. The y in one rule has nothing to do with the y in the next, which is what makes the union of §10.2 work.

10.2The algebra, in Datalog

Lecture 17 introduces Datalog by walking the five operations of Lecture 8 through it, on a schema close to the CollegeDB of Set 5:

Person      (id, name, address, yearborn)
Teacher     (tid, rank, salary)
Student     (sid, yearenroll)
Department  (code, name, chair)
Course      (dcode, number, name, credit)
Section     (regNum, dcode, cnum, year)
GradeSheet  (sid, regNum, year, grade)
The five correspondences

1. No operation at all. “Find all people.”

RA:       R = Person
SQL:      SELECT * FROM Person;
datalog:  R(i, n, a, y)  ←  Person(i, n, a, y)

2. Projection. “Find all people's id and name.” Drop the unwanted variables from the head:

RA:       R = Π[id, name] Person
SQL:      SELECT id, name FROM Person;
datalog:  R(i, n)  ←  Person(i, n, a, y)
          R(i, n)  ←  Person(i, n, _, _)

Both rules say the same thing. The second uses unnamed variables — the underscore stands for “some value, I do not care which, and I will not refer to it again”. Prefer it: a named variable that occurs once is a reader's false alarm, because every other repeated name in the rule is doing work.

3. Selection. “Find all 3-credit courses.”

RA:       R = σ[credit = 3] Course
SQL:      SELECT * FROM Course WHERE credit = 3;
datalog:  R(d, n, c, k)  ←  Course(d, n, c, k) and k = 3

And the two combined — names of all 3-credit courses:

R(c)  ←  Course(_, _, c, k) and k = 3

4. Union. “Find all years in the database in which people were born or are taking classes.” Write two rules with the same head; both add rows to the same answer:

RA:       R = (Π[yearborn] Person) ∪ (Π[year] Section)
datalog:  R(y)  ←  Person(_, _, _, y)
          R(t)  ←  Section(_, _, _, t)

The variable is named y in one and t in the other to make the point: scope is local to a rule, so the names need not agree and agreeing would mean nothing.

5. Subtraction. “Find the id of students who never failed a course.” Put not in front of a predicate:

RA:       R = (Π[sid] Student) \ (Π[sid] σ[grade = 'F'] GradeSheet)
datalog:  R(i)  ←  Student(i, _) and
                   not GradeSheet(i, _, _, g) and g = 'F'

And if the names are wanted rather than the ids, bring in the table that has them, matching on i:

R(n)  ←  Student(i, _) and Person(i, n, _, _) and
          not GradeSheet(i, _, _, g) and g = 'F'
Where are product and join?

They have no symbol in Datalog because they need none. Listing two predicates in a body is already the product; repeating a variable across them is already the matching condition. The rule

R(n)  ←  Student(i, _) and Person(i, n, _, _)

is the product of Student and Person, selected where the two ids agree, projected on the name — three algebra operations, one line, no operator written at all. The i appearing twice is the whole of it.

That is also the answer to a question Set 5 raised and Set 6 repeated: the join is a convenience, not a necessity. Datalog gets along without it, and so do all the answers on this site.

10.3The Employee database

Eleven of the sixteen exercises are set against one small schema, Appendix B.6 of the problem book. It is worth the page it takes, because its four tables produce every shape of query this set has to teach — matching, self-matching, negation and the auxiliary predicate — without a single column you have to look up twice.

employee (employee_name, street, city)
works    (employee_name, company_name, salary)
company  (company_name, city)
manages  (employee_name, manager_name, company_name)

The book's narrative: an employee may be unemployed or work for one or more companies, and has exactly one address. A company must be located in one or more cities. works gives the salary an employee earns at an individual company. An employee need not have a manager, or may have one or more, in an individual company.

Where the content comes from

The schemas above are the book's. The book prints no content for this database, so the rows below are ours — small, and chosen so that every one of the eleven queries returns something worth reading and so that the careless version of a query returns something visibly different. Three features are deliberate and several exercises turn on them: Ida Frost is unemployed and appears in no table but employee; Anna Karenina and Rose Purple each work for two companies and everybody else who works at all works for exactly one; and First Bank and Quiet Motors are each located in two cities, so “the city of the company” is never a single value.

One spelling note. The book writes the city two ways across these problems — 'NY' in Problems 482 and 483, 'New York' in Problems 485 to 492. This page writes 'New York' in both places, so that one database serves all eleven.

Turning a rule into SQL, to check it

There is no Datalog engine on this page, and you will not be asked to run one. But every answer here was checked, and the recipe is worth knowing because it is also the fastest way to convince yourself a rule is right:

In the ruleIn the SQL
each body predicateone table in the FROM list, with an alias
a variable appearing twicean equality in the WHERE clause
a constant in an argument positionan equality against that constant
an unnamed variable _nothing at all
not P(…)NOT IN against a subquery over P
the head variablesthe SELECT list, with DISTINCT

DISTINCT is not optional. Datalog has set semantics — a row is either in the answer or it is not — and SQL has bag semantics, so the translation needs it wherever a rule could match twice. Exercise 10.13 is built on exactly that difference.

The file sql/verify_set10.sql holds the translation of every rule on this page.

The first three exercises give you the algebra and ask only for the Datalog, which is the direction Lecture 17 teaches in. After that you are on your own with the English.

In the Employee database, write a set of safe datalog rules for the query given by the following relational algebra expression: 
R = Π[employee_name] σ[F] (employee)

where  F ≡ [ city = 'New York' ]
 
Result(n)  ←  employee(n, s, c) and c = 'New York'

Or, since s is never used again:

Result(n)  ←  employee(n, _, c) and c = 'New York'

Either is correct, and the second is the one to write. A one-line query needs one rule; the selection became a condition and the projection became the choice of head variables.

The rows it returns:

Jim Wild
John Boss

The constant could also go inside the predicate. employee(n, _, 'New York') says the same thing in fewer symbols. The lecture writes the condition out, and so does the problem book, so this page does too — but recognise the short form when you meet it.

In the Employee database, write a set of safe datalog rules for the query given by the following relational algebra expression: 
R = Π[employee_name] σ[F] (employee)

where  F ≡ [ city ≠ 'New York' ]
 
Result(n)  ←  employee(n, _, c) and not c = 'New York'

which may equally be written c != 'New York'.

The rows it returns — the other eight employees:

Anna Karenina   Luna Lovegood   Oliver Twist
Hugo Vance      Mina Grey       Paul Stone
Ida Frost       Rose Purple

This not is not the not of §10.5. Here it negates a comparison, which is a test on values already bound by employee(n, _, c). In §10.5 it negates a predicate, which is a different and more delicate thing. The symbol is the same; the question of what the rule is safe to range over is not.

Ida Frost appears here and did not in Exercise 10.1, and will keep reappearing. She is in employee and in nothing else, so any query that starts from employee sees her and any query that starts from works does not.

In the Employee database, write a set of safe datalog rules for the query given by the following relational algebra expression: 
R = Π[employee_name₁, salary₂] σ[F] (employee₁ × works₂)

where  F ≡ [ employee_name₁ = employee_name₂ ∧
                 salary₂ ≤ 20,000 ]
 
Result(n, r)  ←  employee(n, _, _) and works(n, _, r) and r ≤ 20000

The two predicates share the variable n, which is the whole of the matching condition; the comparison is a condition like any other.

The rows it returns:

Luna Lovegood   18000
Oliver Twist    19000

The employee predicate is doing nothing here and the rule is just as correct without it:

Result(n, r)  ←  works(n, _, r) and r ≤ 20000

Every name in works is already a name in employee, by the foreign key, so dropping the table cannot change the answer. Keeping it mirrors the algebra expression you were given, which is why it is written above — but a body predicate that constrains nothing is worth noticing, because in a query with a not in it the same predicate may be the only thing keeping the rule safe.

On the join

The problem book prints this expression with the join: Π[employee_name, salary] σ[salary ≤ 20,000] (employee ⋈ works). It is written above as a product with the matching condition spelled out, which is how Set 5 writes every algebra expression on this site. The two are the same query. Datalog needs neither form, as §10.2 said: the repeated n is the join.

10.4Writing a query from scratch

No algebra is given from here on. The method is always the same three steps, and it is worth doing them in order until they stop needing to be:

The three steps
  1. Name the tables the answer needs, including any you need only to get from one to another. Write one predicate per table, with a distinct variable in every column.
  2. Join them by renaming. Wherever two columns must hold the same value, give both positions the same variable. This is the step people get wrong, and the schema is how you check it: two columns can only be matched if one of them refers to the other.
  3. Fill in the constants and the head. Conditions from the English become comparisons; the attributes the question asks for become the head variables; everything else becomes an underscore.

Step 3 last, not first. Writing the head before you know which variables exist is how you end up with a head variable that appears nowhere in the body — a rule that is not safe, and that no system will run, because the variable ranges over every value in the universe rather than over the database.

In the Employee database, find the city and street of every manager of Jim Wild.

(a) in the relational algebra, using only σ, Π, ×, ∪, \.
(b) as a set of safe datalog rules.

(a)

R = Π[city₁, street₁] σ[F] (employee₁ × manages₂)

where  F ≡ [ employee_name₁ = manager_name₂ ∧
                 employee_name₂ = 'Jim Wild' ]

(b)

Result(c, s)  ←  employee(n, s, c) and manages(j, n, _) and j = 'Jim Wild'

The rows it returns:

Boston     5 Oak Avenue
New York   2 Pine Road

Anna Karenina and John Boss, who both manage Jim Wild at First Bank.

Which column of manages is which. The schema is manages(employee_name, manager_name, company_name), so Jim Wild belongs in the first position and the person whose address we want belongs in the second. Put them the other way round and the query runs, returns rows, and answers a different question — the addresses of everyone Jim Wild manages, which is nobody. A rule that returns the empty set is at least loud about it; a rule that returns plausible wrong rows is not.

The address comes from employee, not from manages, which is why the rule needs two predicates at all. manages knows only names.

In the Employee database, find all the cities in which the companies for which Anna Karenina works are located.

(a) in the relational algebra, using only σ, Π, ×, ∪, \.
(b) as a set of safe datalog rules.

(a)

R = Π[city₂] σ[F] (works₁ × company₂)

where  F ≡ [ company_name₁ = company_name₂ ∧
                 employee_name₁ = 'Anna Karenina' ]

(b)

Result(c)  ←  works(n, p, _) and company(p, c) and n = 'Anna Karenina'

The rows it returns:

Boston
New York

Two companies, three rows of company, two cities in the answer. Anna Karenina works for First Bank, which is located in New York and in Boston, and for Red Press, which is located in New York. The matching produces New York twice, and the answer holds it once, because Datalog is a set. Translate this to SQL without DISTINCT and you will see the duplicate.

“The city of a company” is a trap in this schema, and the narrative warned about it: a company must be located in one or more cities. Any query that assumes one city per company is reading a different database.

In the Employee database, find the cities of location of those companies in which John Boss manages some employee who lives in New York.

(a) in the relational algebra, using only σ, Π, ×, ∪, \.
(b) as a set of safe datalog rules.

(a) Let P hold the names of those companies in which John Boss manages some employee who lives in New York:

P = Π[company_name₂] σ[G] (employee₁ × manages₂)

where  G ≡ [ employee_name₁ = employee_name₂ ∧
                 city₁ = 'New York' ∧
                 manager_name₂ = 'John Boss' ]

R = Π[city₂] σ[company_name₁ = company_name₂] (P₁ × company₂)

(b) Two rules, following the algebra exactly — the first defines the intermediate predicate, the second uses it:

P(p)       ←  employee(n, _, c) and manages(n, m, p) and
               c = 'New York' and m = 'John Boss'
Result(c)  ←  P(p) and company(p, c)

What each rule returns:

P       =  First Bank
Result  =  Boston, New York

It can also be written as one rule, by substituting the body of the first into the second:

Result(c)  ←  employee(n, _, k) and manages(n, m, p) and company(p, c) and
               k = 'New York' and m = 'John Boss'

Both are correct and the one-rule version is shorter. The two-rule version is better, and not only because it matches the algebra: it gives the intermediate result a name, which is the only documentation a rule ever gets, and it is the pattern §10.5 cannot do without.

Notice that the answer leaves New York. The query asks for employees who live in New York, and returns Boston among the cities, because First Bank is located in both. Reading the answer and expecting only New York is a misreading of the question, not a bug in the rule — which is the kind of thing worth checking against real rows before handing an answer in.

10.5Negation and auxiliary predicates

Three things not needs

Putting not in front of a predicate is how Datalog subtracts, and §10.2 showed the simple case. Three rules govern it.

1. A negated predicate cannot be the only thing in the body. A rule is safe when every variable in it also appears in some positive predicate. Write

Result(n)  ←  not works(n, _, _)                 ← not safe

and you have asked for every value in the universe that is not an employee name in works, which is infinite. The fix is always the same: range over a table first.

Result(n)  ←  employee(n, _, _) and not works(n, _, _)

2. Which table you range over decides the answer. The rule above finds the unemployed, because it ranges over employee. Range over works instead and the unemployed cannot appear at all, since they have no row there. The problem book makes the same point about Problem 488 and prefers the former; Exercise 10.7 is where it bites.

3. When the thing to be subtracted takes more than one rule, give it a name. This is the auxiliary predicate, and it is the pattern the rest of this section is built on:

Fail(x)    ←  … one way of failing …
Fail(x)    ←  … another way of failing …
Result(x)  ←  … range over a table … and not Fail(x)

Several rules with the head Fail are a union, by §10.2; not Fail then subtracts the union in one go. Without the name you would have to negate each way of failing separately, which is a different and usually wrong query.

In the Employee database, find names of all employees who are not managers and do not earn a salary of more than $30,000 in any company for which they work.

(a) in the relational algebra, using only σ, Π, ×, ∪, \.
(b) as a set of safe datalog rules.

(a) First the employees that fail the test, because they are managers or because their salary is too high:

Ψ = Π[employee_name₁] σ[F] (employee₁ × works₂ × manages₃)

where  F ≡ [ employee_name₁ = manager_name₃
                 ∨
                 ( employee_name₁ = employee_name₂ ∧ salary₂ > 30,000 ) ]

R = Π[employee_name] (employee) \ Ψ

(b)

Fail(n)    ←  employee(n, _, _) and manages(_, n, _)
Fail(n)    ←  employee(n, _, _) and works(n, _, r) and r > 30000
Result(n)  ←  employee(n, _, _) and not Fail(n)

What each predicate holds:

Fail    =  Anna Karenina, Hugo Vance, Jim Wild,
           John Boss, Paul Stone, Rose Purple
Result  =  Ida Frost, Luna Lovegood, Mina Grey, Oliver Twist

Ida Frost is in the answer, and that is the whole exercise. She is unemployed: she is not a manager, and there is no company in which she earns more than $30,000 because there is no company in which she earns anything. The book makes the point explicitly — taking the complement in works rather than in employee would look for suitable employees among those who are actually employed, leaving out the unemployed, and the book believes the former interpretation is preferable. Whichever you choose, choose it deliberately and say which you chose.

Two rules for Fail, not one. “Is a manager” and “earns too much somewhere” are two independent ways of failing, joined by or, and a Datalog body has no or — it has only and. Two rules with the same head is how you write a disjunction, which is exactly the union of §10.2 doing a job you would not have guessed it was for.

In the Employee database, find names of all employees who work for exactly one company.

(a) in the relational algebra, using only σ, Π, ×, ∪, \.
(b) as a set of safe datalog rules.

(a) The employees that work for at least one company:

ξ = Π[employee_name] (works)

The employees found to work for at least two different companies:

Ψ = Π[employee_name₁] σ[F] (works₁ × works₂)

where  F ≡ [ employee_name₁ = employee_name₂ ∧
                 company_name₁ ≠ company_name₂ ]

R = ξ \ Ψ

(b)

Fail(n)    ←  works(n, p, _) and works(n, q, _) and not p = q
Result(n)  ←  works(n, _, _) and not Fail(n)

What each predicate holds:

Fail    =  Anna Karenina, Rose Purple
Result  =  Hugo Vance, Jim Wild, John Boss, Luna Lovegood,
           Mina Grey, Oliver Twist, Paul Stone

“Exactly one” is “at least one” minus “at least two”, and Datalog can count no higher than that. There is no counting in the language — no COUNT, no HAVING. What there is instead is the same predicate written twice in one body with different variables, which says “two rows”, plus a != to say they are different rows. Everything you can express about cardinality is built from that.

Ida Frost is not in this answer, where she was in the last one, and the difference is one word: this rule ranges over works and Exercise 10.7 ranged over employee. Here that is right — somebody who works for no company does not work for exactly one.

Leaving out not p = q would make Fail hold everyone who works anywhere, since the two works predicates would happily match the same row twice, and Result would be empty. If a negated rule returns nothing at all, this is the first thing to look for.

In the Employee database, find names of all companies in which Rose Purple is employed, but not as a manager.

(a) in the relational algebra, using only σ, Π, ×, ∪, \.
(b) as a set of safe datalog rules.

(a) The companies where Rose Purple works, and the companies where she manages somebody:

ξ = Π[company_name] σ[employee_name = 'Rose Purple'] (works)

Ψ = Π[company_name] σ[manager_name = 'Rose Purple'] (manages)

R = ξ \ Ψ

(b)

Fail(p)    ←  manages(_, m, p) and m = 'Rose Purple'
Result(p)  ←  works(n, p, _) and n = 'Rose Purple' and not Fail(p)

What each predicate holds:

Fail    =  Red Press
Result  =  Blue Press

Rose Purple works for Red Press and Blue Press, and manages somebody at Red Press only.

The constant is needed in both rules, and forgetting it in the first is the usual error. Write Fail(p) ← manages(_, _, p) and Fail becomes every company in which anybody manages anybody, which here is four companies and would make the answer empty. The two rules are about the same person, but nothing in the language says so except the constant appearing in each.

Why Fail needs a name here at all, when it has only one rule: because not may only be applied to a predicate, and the thing being subtracted is a derived set, not a stored table. You could inline it — not manages(_, 'Rose Purple', p) — and many systems would accept that; the book's style, and the style that keeps working when the subtracted set needs two rules, is to name it.

In the Employee database, find the names and cities of residence of those employees who don't live in New York, and don't work for a company located in New York, and don't have a manager who lives in New York.

(a) in the relational algebra, using only σ, Π, ×, ∪, \.
(b) as a set of safe datalog rules.

(a) There are three ways to fail, and failing any one of them is enough, so the set to subtract is their union:

Ψ = Ψ₁ ∪ Ψ₂ ∪ Ψ₃

Employees living in New York:

Ψ₁ = Π[employee_name] σ[city = 'New York'] (employee)

Employees working for a company located in New York:

Ψ₂ = Π[employee_name₁] σ[G] (works₁ × company₂)

where  G ≡ [ company_name₁ = company_name₂ ∧ city₂ = 'New York' ]

Employees with a manager who lives in New York:

Ψ₃ = Π[employee_name₂] σ[J] (Ψ₁₁ × manages₂)

where  J ≡ [ manager_name₂ = employee_name₁ ]

R = Π[employee_name₁, city₁] σ[K] ( ((Π[employee_name] employee) \ Ψ)₂ × employee₁ )

where  K ≡ [ employee_name₁ = employee_name₂ ]

(b) Each Ψ becomes an auxiliary predicate, and the three are negated separately in the one result rule:

Live(e)       ←  employee(e, _, c) and c = 'New York'
Located(e)    ←  works(e, p, _) and company(p, c) and c = 'New York'
Boss(e)       ←  Live(b) and manages(e, b, _)
Result(e, c)  ←  employee(e, _, c) and
                  not Live(e) and not Located(e) and not Boss(e)

What each predicate holds:

Live     =  Jim Wild, John Boss
Located  =  Anna Karenina, Jim Wild, John Boss, Rose Purple
Boss     =  Anna Karenina, Jim Wild

Result   =  Hugo Vance      Detroit
            Ida Frost       Chicago
            Luna Lovegood   Detroit
            Mina Grey       Flushing
            Oliver Twist    Boston
            Paul Stone      Boston

Boss is defined in terms of Live, not in terms of employee all over again. A derived predicate may be used in a body exactly like a stored one, and that is what makes the auxiliary-predicate style pay: the condition “lives in New York” is written once and used twice.

Three separate nots, not one Fail. The English says and — all three must be avoided — so the three negations sit side by side in one body. Exercise 10.11 asks the same question with or and the shape changes completely. Read those two answers next to each other; the pair is the point of both.

In the Employee database, find the names and cities of residence of those employees who don't live in New York, or don't work for a company located in New York, or don't have a manager who lives in New York.

(a) in the relational algebra, using only σ, Π, ×, ∪, \.
(b) as a set of safe datalog rules.

(a) Now there is only one way to fail — by being caught by all three at once — so the union of Exercise 10.10 becomes an intersection, with Ψ₁, Ψ₂ and Ψ₃ exactly as computed there:

Ψ = Ψ₁ ∩ Ψ₂ ∩ Ψ₃

R = Π[employee_name₁, city₁] σ[K] ( ((Π[employee_name] employee) \ Ψ)₂ × employee₁ )

where  K ≡ [ employee_name₁ = employee_name₂ ]

(b) The three auxiliary predicates are unchanged; what changes is that they are now combined into one Fail before being negated:

Live(e)       ←  employee(e, _, c) and c = 'New York'
Located(e)    ←  works(e, p, _) and company(p, c) and c = 'New York'
Boss(e)       ←  Live(b) and manages(e, b, _)
Fail(e)       ←  Live(e) and Located(e) and Boss(e)
Result(e, c)  ←  employee(e, _, c) and not Fail(e)

What it returns:

Fail    =  Jim Wild

Result  =  Anna Karenina   Boston      Luna Lovegood   Detroit
           Hugo Vance      Detroit     Mina Grey       Flushing
           Ida Frost       Chicago     Oliver Twist    Boston
           John Boss       New York    Paul Stone      Boston
                                       Rose Purple     Chicago

Nine of the ten employees. Jim Wild lives in New York, works for First Bank which is located there, and is managed by John Boss who lives there, so he is the only one all three catch.

This is De Morgan, and it is worth saying out loud. “Not A and not B and not C” is “not (A or B or C)” — three negations beside each other, as in Exercise 10.10. “Not A or not B or not C” is “not (A and B and C)” — one negation of a conjunction, which is why this version needs the extra Fail rule and the previous one did not. A Datalog body can only say and, so an or has to be pushed outward into separate rules or inward past a not; recognising which of the two a question wants is most of the work in these.

John Boss is in this answer and not in the previous one. He lives in New York and works for a company located there, so Exercise 10.10 excludes him twice over — but nobody manages him, so the third condition does not catch him, and here that is enough to let him through.

10.6Four databases you already know

The last five exercises are the problem book's Datalog questions on four schemas from earlier sets. Nothing new is introduced; what changes is that you have to find your way around a schema you last used in SQL, which is most of the difficulty in a real query and none of the difficulty in a textbook one.

A note on the names in the data

Two of these questions name a person or a company: the book asks about a mechanic called Adjuster Crack Hide and a designer called Crocodile Garment. The book prints no content for either database, so the rows on this site are ours and use different names. The exercises below name somebody who is actually in the data — a mechanic called Constructor Break Fixer and a designer called Smart Dresser — so that the answers can be run and shown. Nothing else about either question is changed.

Refer to the Car Repair Shop database of Set 8: 
mechanic     (socSecNum, name)
manufacturer (name, address)
car          (manufacturerId, model, price)
carInstance  (VIN, manufacturerId, modelCode, dateMade)
repairJob    (workOrderID, carID, officer, dateBrought)
Write a set of safe datalog rules for: find manufacturer name, manufacturer address, and car price of those cars that have been brought in for a repair job where the officer in charge was a mechanic by name of Constructor Break Fixer. 
Result(k, a, p)  ←  manufacturer(k, a) and
                     car(k, m, p) and
                     carInstance(v, k, m, _) and
                     repairJob(_, v, f, _) and
                     mechanic(f, e) and
                     e = 'Constructor Break Fixer'

The rows it returns:

HappyForgerWorks   1 Anvil Road     21000
GreatConjurer      9 Spell Street   25000

Five predicates and not one of them is optional. Read the chain of repeated variables, because that is the query:

VariableLinks
kmanufacturer.name to car.manufacturerId to carInstance.manufacturerId
mcar.model to carInstance.modelCode
vcarInstance.VIN to repairJob.carID
frepairJob.officer to mechanic.socSecNum

Five tables, four links, and the whole query is in the choice of letters. Compare the SQL you wrote for this database in Set 8: the same query there is a FROM list of five tables and a WHERE clause of four equalities, which is the same information with more punctuation.

k and m together are what link car to carInstance, because the key of car is the pair. Matching on k alone would ask for cars of the right make and any model, which is the half-a-composite-key error Set 8 ends on — and in Datalog it is easier to spot, because the unmatched variable just sits there with nothing to pair with.

The question asks about cars, and the answer is about models. Two instances of the same model repaired by the same mechanic give one row, not two, because v does not appear in the head and Datalog is a set. That is almost certainly what was wanted; it is worth being sure.

Refer to the Professor Payroll database of Sets 5 and 7: 
professor  (socSecNum, firstName, lastName, salary, rank, wizardID)
department (name, office, phone, chairId)
Write a set of safe datalog rules for: find full name (first and last) of those professors who serve as department chairs. 
Result(fn, ln)  ←  professor(d, fn, ln, _, _, _) and
                    department(_, _, _, d)

The rows it returns:

Minerva   McGonagall
Severus   Snape
Pomona    Sprout
Dolores   Umbridge

Five departments, four professors. Dolores Umbridge chairs both Divination and Muggle Studies, so the matching produces her row twice and the answer holds it once. Translate this rule to SQL and leave out DISTINCT and you get five rows — the single clearest example on this page of what “Datalog is a set” buys you. SQL made you ask for duplicate removal; Datalog makes you ask for duplicates, and there is no way to ask.

The whole query is the variable d appearing in two places: the social security number of a professor, and the chairId of a department. Everything else in the rule is an underscore. When a rule comes out looking like this, you have found the foreign key the question was really about.

Naming the shared variable d is a small lie worth avoiding. It holds a social security number, not a department — the name was picked because it is the department's column that it is being matched against. The book writes it this way; a letter closer to s would read better. Names in a rule are documentation and nothing else, so choose them for the reader.

Refer to the Cool Cotton database of Set 8: 
shirt     (styleCode, salesPrice)
shirtSize (basicStyle, sizeOption)
Write a set of safe datalog rules to select styles and sales prices of all shirts that are available in sizes greater than 10. 
Result(s, p)  ←  shirt(s, p) and shirtSize(s, t) and t > 10

The rows it returns — all six styles:

S-1001    6.50
S-1002   12.00
S-1003   24.99
S-1004    9.75
S-1005   null
S-1006   24.99

A condition that excludes nothing is still worth writing. Every size in this content is 16 or more, so t > 10 passes every row and the answer is every shirt that has a size at all. That is the right answer to the question asked, and it is also a warning: an answer that looks like “the whole table” is the one case where you cannot tell a working query from a broken one by reading the output. Check it by changing the constant — at t > 20 the answer drops to two styles, S-1002 and S-1003.

S-1005 has no sales price and is in the answer anyway. The variable p binds to the null and carries it into the head; nothing in the rule looks at p, so nothing can object. Had the question asked for shirts priced above something, that row would have vanished without comment — which is the null behaviour Set 8 spends four exercises on, and it is no different here.

Every shirt in shirtSize is also in shirt, so shirt(s, p) is not acting as a filter. It is in the body because the head needs p, and shirtSize does not have it.

Refer again to the Cool Cotton database: 
designer       (designerId, designerName)
originalDesign (theStyle, theDesigner, adoptedWhen, designPlan)
factory        (factoryId, factoryName)
purchaseDeal   (item, producedBy, productName,
                purchasePrice, quantity, orderDue)
Write a set of safe datalog rules to find names of all factories that have produced some shirt style(s) designed by Smart Dresser designers. 
Result(fn)  ←  designer(di, dn) and
                originalDesign(s, di, _, _) and
                purchaseDeal(s, fi, _, _, _, _) and
                factory(fi, fn) and
                dn = 'Smart Dresser'

The rows it returns:

Superb Seamstress Star
Tiny Thread
Rapid Stitch

Two designer ids share the name Smart Dresser, and the question says designers, plural. D-01 designed S-1002 and S-1003; D-03 designed S-1004. Match on the name, as above, and all three factories appear. Match on one id instead —

Result(fn)  ←  originalDesign(s, 'D-01', _, _) and
                purchaseDeal(s, fi, _, _, _, _) and
                factory(fi, fn)          ← answers a different question

— and the answer silently drops to two:

Superb Seamstress Star
Tiny Thread

This is the reason the designer predicate is in the body at all. The link from a style to a factory never passes through it; it is there only so that the name can be matched rather than the id. When a question names somebody in English, it is naming a value in some column, and finding which column — and whether that column is unique — is the first thing to settle.

purchaseDeal takes six arguments, four of them underscores. Count the columns in the schema before you write the predicate, every time; a predicate written with the wrong number of arguments is the one error Datalog cannot interpret charitably.

Refer to the Hotel database of Set 8: 
hotel   (hnumber, name, address)
guest   (gnumber, name, address)
room    (rnumber, hnumber, type, price_night)
booking (hnumber, gnumber, arrived, left, rnumber)
Write a set of safe datalog rules to find names of all guests that have never stayed in the New Hotel. 
Discard(g)  ←  guest(g, _, _) and hotel(h, n, _) and
                booking(h, g, _, _, _) and n = 'New Hotel'
Result(n)   ←  guest(g, n, _) and not Discard(g)

What each predicate holds:

Discard  =  1212, 3456, 7171

Result   =  Nice Guy        Any Guy
            Mary Clever     Former Student
            Smart Student   Poor Student
            Fine Lady       Nasty Professor

Eight of the eleven guests.

“Never” is the word that tells you a negation is coming, along with “no”, “not any” and “only”. And as always, the thing to negate is a derived set, so it needs a rule and a name of its own: Discard holds the guests who have stayed there, and the answer is everybody else.

Discard holds numbers and Result holds names. The negation must be on the key, not on the name — guest.name is not declared unique in this schema, so two guests could share one and negating the name would throw away the innocent one along with the guilty. It is a small thing and it is the kind of small thing that makes a query wrong on real data and right on the ten rows you tested it with.

The rule is safe because g and n both appear in guest(g, n, _), which is positive. Drop that predicate and keep only not Discard(g) and the rule asks for every value in the universe that is not one of three guest numbers, which no system will run and none should.

Where this set ends up

Three query languages now, and every one of these sixteen queries could have been written in any of them. What Datalog contributes is not power but clarity about where the power comes from:

AlgebraSQLDatalog
× then σ on equalityFROM two tables, WHERE they matchthe same variable written twice
σ on a constantWHERE a comparisona comparison in the body
Πthe SELECT listthe head variables
∪UNIONtwo rules with the same head
\NOT INnot before a predicate
a named intermediate resulta subqueryan auxiliary predicate
sets throughoutbags, unless DISTINCTsets throughout

Read the bottom two rows together. The auxiliary predicate is the one piece of Datalog with no single counterpart in the other two — it is a subquery you can reuse, a view you do not have to create, and a name for the intermediate step that the algebra lets you write but SQL mostly does not. Every hard query on this page is hard only until it is given one.

What this set has not asked: anything that counts, averages or orders. There is no aggregation in the Datalog of Lecture 17, and no recursion either — the feature that makes Datalog more than a notation for the algebra. Both are real and neither is in this course.
