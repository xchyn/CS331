Queries on three databases

Forty-one more exercises at the level of Set 7, on three schemas you have not met: a chain of hotels, a car repair shop, and a shirt company. Nothing new is introduced — the same SELECT, WHERE, ORDER BY, aggregate functions, GROUP BY, HAVING and subqueries of Lectures 11 and 12. What changes is the schema, which is the part that actually takes practice. Still no JOIN keyword.

8.1The three databases

Each section below gives a schema, the rows it holds, and then the exercises written against it. Load all three and you can run anything on this page:

-- from the sql/ directory
mysql -u root < sql/hotel.sql           # the exercises in 8.3
mysql -u root < sql/carshop.sql         # the exercises in 8.5
mysql -u root < sql/coolcotton.sql      # the exercises in 8.7
mysql -u root -t < sql/set8.sql         # every answer, in page order
The same restriction as Set 7

All three of these sections of the problem book carry the same sentence at the top: your code must not contain union, intersection, except, or any of the join operators. So the rule you have been working under is the book's rule here, not an extra one of ours. Relations go in the FROM clause separated by commas; every link between them is written out in the WHERE clause.

The answers go a little further and stay inside the vocabulary of Lectures 11 and 12 as well. Where the book reaches for EXISTS, NOT EXISTS or >= ALL, the answer here is written with IN or NOT IN against a subquery, which is the form the lectures use. The shape is always the same: build the set, then ask whether a value is in it.

Oracle and MariaDB

The book is written for Oracle, and four of its habits do not survive the move to MariaDB. They appear often enough on this page to be worth knowing before you start.

sysdate is CURDATE(). Several questions say “today, where you do not know what date it is” — the point being that the query must ask the server rather than have a date typed into it.

trunc(x) disappears. Oracle's DATE carries a time of day, so the book wraps dates in trunc to throw the time away before comparing. MariaDB's DATE has no time to throw away, so the comparisons are written directly.

to_date('20-MAY-2000') is just '2000-05-20'. MariaDB reads the ISO form natively.

Reserved words need backticks. The Hotel schema has a column called left and the Car Repair Shop has one called rank; both are reserved in recent MySQL and MariaDB. Written plainly, left gives you

ERROR 1064 (42000): You have an error in your SQL syntax; check the manual
that corresponds to your MariaDB server version for the right syntax to use
near 'FROM booking' at line 1

which blames the wrong word. Write `left` and it works. The book, on Oracle, needs none of this.

Where the rows come from

The Hotel rows are the book's own, printed in Appendix A.8. The Car Repair Shop and Cool Cotton rows are ours: the book gives those two schemas but no sample content, so rows were written for them — small, and chosen so that every exercise returns something worth looking at. Each file says so in its header comment. The questions are the book's throughout.

8.2The Hotel Database

Four hotels, their rooms, the guests, and who stayed where. It is the smallest schema on this page and the only one whose rows are printed in the book — Appendix A.7 gives the CREATE TABLE statements and Appendix A.8 the INSERTs.

hotel   (hnumber, name, address)
room    (rnumber, hnumber, type, price_night)
guest   (gnumber, name, address)
booking (hnumber, gnumber, rnumber, arrived, left)

Two things about this schema are worth reading off before any query is written. room's key is the pair — room 2 exists in three different hotels, so a room number alone identifies nothing, and every query that reaches a room has to match both columns. And booking's left may be NULL, which here means the guest has not checked out: that is what makes “occupied today” a question about two conditions rather than one.

One booking moves with the calendar

The book's last booking is written sysdate, so that the “arriving today” questions always find something. Ours keeps that: Busy Traveler's arrival is CURDATE() and the departure the day after. 8.3Exercises: the Hotel Database

Problems 751–778 of Section 9.15. They run from a one-table SELECT to a NOT IN over two copies of one relation, roughly in that order.

List numbers and prices of all rooms in the hotel number 2222. 
SELECT rnumber, price_night FROM room WHERE (hnumber = 2222);
+---------+-------------+
| rnumber | price_night |
+---------+-------------+
|       1 |      104.00 |
|       2 |      105.00 |
|       3 |      106.00 |
|       4 |      107.00 |
+---------+-------------+

One table, one condition. Note that the question gives you the hotel's number and not its name, which is why no second relation is needed — room already carries hnumber.

What is the average price of a room? 
SELECT AVG (price_night) FROM room;
+------------------+
| AVG(price_night) |
+------------------+
|       109.125000 |
+------------------+

An aggregate with no GROUP BY collapses the whole table to one row. The average is over rooms, not over hotels: the Old Hotel's four expensive singles pull it up more than the Big Hotel's four cheap rooms pull it down, because each room counts once regardless of which hotel it is in.

List full locations (hotel name and room number) of all rooms that cost at least $100 and no more than $120. 
SELECT room.rnumber, hotel.name
FROM   room, hotel
WHERE  (hotel.hnumber = room.hnumber AND price_night BETWEEN 100 AND 120);
+---------+-------------+
| rnumber | name        |
+---------+-------------+
|       1 | Big Hotel   |
|       2 | Big Hotel   |
|       3 | Big Hotel   |
|       4 | Big Hotel   |
|       1 | Small Hotel |
|       2 | Small Hotel |
|       3 | Small Hotel |
|       4 | Small Hotel |
|       2 | Old Hotel   |
|      10 | Old Hotel   |
|      32 | Old Hotel   |
|      43 | Old Hotel   |
|       4 | New Hotel   |
|       5 | New Hotel   |
|       6 | New Hotel   |
|       7 | New Hotel   |
+---------+-------------+

“Full location” is why there are two relations. A room number on its own does not locate a room, so the hotel's name has to be fetched, and fetching it means putting hotel in the FROM clause and writing hotel.hnumber = room.hnumber.

Every room qualifies, because every price in this database happens to fall between 100 and 119. That is worth noticing rather than glossing over: a condition that excludes nothing is not a wrong condition, and you cannot tell a query is right by looking at the size of its answer. Change the bound to 110 and eight rows drop out.

BETWEEN 100 AND 120 is inclusive at both ends, and is exactly price_night >= 100 AND price_night <= 120.

List full locations and prices of all the rooms of type double or family that cost more than $105 per night, in ascending order of price. 
SELECT rnumber, room.hnumber, name, address, price_night
FROM   hotel, room
WHERE  (room.hnumber = hotel.hnumber AND
        type IN ('family','double') AND
        price_night > 105)
ORDER BY price_night ASC;
+---------+---------+-----------+--------------+-------------+
| rnumber | hnumber | name      | address      | price_night |
+---------+---------+-----------+--------------+-------------+
|       7 |    4444 | New Hotel | Green Forest |      111.00 |
|       6 |    4444 | New Hotel | Green Forest |      112.00 |
|       5 |    4444 | New Hotel | Green Forest |      114.00 |
|       4 |    4444 | New Hotel | Green Forest |      119.00 |
+---------+---------+-----------+--------------+-------------+

type IN ('family','double') is shorthand for type = 'family' OR type = 'double'. The parentheses matter: written without them, AND binds tighter than OR and the price condition would attach to only one of the two types.

Only the New Hotel survives — the rooms above $105 elsewhere are all singles. ASC is the default and could be left off; writing it costs nothing and says you meant it.

List the names and full room locations of all guests that have booked a room that costs at least $100 and no more than $110. 
SELECT guest.name, room.rnumber, hotel.name
FROM   room, hotel, booking, guest
WHERE  (hotel.hnumber = room.hnumber AND
        hotel.hnumber = booking.hnumber AND
        room.rnumber  = booking.rnumber AND
        guest.gnumber = booking.gnumber AND
        price_night BETWEEN 100 AND 110);
+-----------------+---------+-------------+
| name            | rnumber | name        |
+-----------------+---------+-------------+
| Fine Lady       |       1 | Big Hotel   |
| Any Guy         |       2 | Big Hotel   |
| Mary Clever     |       3 | Big Hotel   |
| Former Student  |       1 | Small Hotel |
| Poor Student    |       3 | Small Hotel |
| Nasty Professor |       4 | Small Hotel |
+-----------------+---------+-------------+

Four relations, three links. That is the usual arithmetic: n relations in a FROM clause need n−1 equalities to tie them into one chain, and if you write fewer the missing one turns into a silent cross product. Count them before you run anything.

Two of the links are needed for one relationship. A booking points at a room by both hnumber and rnumber, because that is room's key. Drop room.rnumber = booking.rnumber and the query still runs, still looks reasonable, and quietly prices each guest against every room in their hotel.

Both output columns are called name. SQL allows it; the reader has to work out which is which from the order. SELECT guest.name AS guest, hotel.name AS hotel is kinder.

What is the average price of a room in the New Hotel? 
SELECT AVG (price_night)
FROM   room, hotel
WHERE  (room.hnumber = hotel.hnumber AND hotel.name = 'New Hotel');
+------------------+
| AVG(price_night) |
+------------------+
|       114.000000 |
+------------------+

Compare with Exercise 8.2. The aggregate is unchanged; what changed is the set of rows reaching it. The WHERE clause runs first and the aggregate sees only what survives — which is the whole mental model you need for WHERE against HAVING later.

How many guests have booked a room in the Old Hotel? 
SELECT COUNT (gnumber)
FROM   booking, hotel
WHERE  (booking.hnumber = hotel.hnumber AND hotel.name = 'Old Hotel');
+----------------+
| COUNT(gnumber) |
+----------------+
|              2 |
+----------------+

COUNT(gnumber) counts bookings, not guests. They agree here because no guest has booked the Old Hotel twice. If one had, this would say 3 and the honest answer would still be 2 — COUNT(DISTINCT gnumber) is the query that cannot be caught out. The book writes it without DISTINCT; both are worth being able to defend.

COUNT(gnumber) and COUNT(*) differ only when the column can be null, since COUNT of a column skips nulls. gnumber is in booking's primary key, so it never is.

What is the price difference between the cheapest and the most expensive room in the Big Hotel? 
SELECT MAX (price_night) - MIN (price_night)
FROM   room, hotel
WHERE  (room.hnumber = hotel.hnumber AND hotel.name = 'Big Hotel');
+-------------------------------------+
| MAX(price_night) - MIN(price_night) |
+-------------------------------------+
|                                3.00 |
+-------------------------------------+

Two aggregates in one expression, over the same filtered rows. Nothing says the result of an aggregate cannot be arithmetic on — and this is much easier than it looks if you remember that both MAX and MIN see the same four rows.

List names and room numbers of all guests who have resided in the Big Hotel but do not live in New York. 
SELECT guest.name, booking.rnumber
FROM   guest, booking, hotel
WHERE  (guest.gnumber = booking.gnumber AND
        hotel.hnumber = booking.hnumber AND
        NOT (guest.address LIKE '%New York%') AND
        hotel.name = 'Big Hotel');
+-------------+---------+
| name        | rnumber |
+-------------+---------+
| Mary Clever |       3 |
| Fine Lady   |       1 |
| Any Guy     |       2 |
+-------------+---------+

The address is free text, so LIKE is the only tool available. % matches any run of characters including none, so '%New York%' finds the phrase anywhere in the field.

It is a crude test and the question deserves a warning: this would also exclude a guest living in New York, Nebraska, and it does exclude Big Boss, whose address is “New York other”. A schema that stored city and state in their own columns would not need LIKE at all. That is a design observation, not a SQL one, and it is the right one to make.

Find names of all guests that have stayed in the New Hotel. 
SELECT guest.name
FROM   guest, hotel, booking
WHERE  booking.hnumber = hotel.hnumber AND
       booking.gnumber = guest.gnumber AND
       hotel.name = 'New Hotel';
+---------------+
| name          |
+---------------+
| John Strong   |
| Big Boss      |
| Busy Traveler |
+---------------+

The positive half of the pair. Three relations, two links, one condition — and the whole of it is reachable by asking “which tables hold the words in the question?” The question mentions guests (names), a hotel (by name), and staying (which is booking).

Find names of all guests that have never stayed in the New Hotel. 
SELECT name
FROM   guest
WHERE  gnumber NOT IN
       (SELECT booking.gnumber
        FROM   booking, hotel
        WHERE  booking.hnumber = hotel.hnumber AND
               hotel.name = 'New Hotel');
+-----------------+
| name            |
+-----------------+
| Nice Guy        |
| Mary Clever     |
| Smart Student   |
| Fine Lady       |
| Any Guy         |
| Former Student  |
| Poor Student    |
| Nasty Professor |
+-----------------+

“Never” cannot be written by negating the condition in Exercise 8.10. hotel.name != 'New Hotel' finds guests with some booking elsewhere, which is a different set and includes John Strong, who has stayed in both. The question is about a guest having no row at all, and no condition on a single row can say that.

Build the set first, then exclude. The subquery is the set of guest numbers that have stayed there — it is Exercise 8.10 with gnumber in place of the name. The outer query then keeps the guests not in that set. Eight of the eleven qualify.

The subquery mentions nothing from the outer query, so it is computed once and the whole answer is one pass over guest. That is the shape Lecture 11 uses for the highest salary and Lecture 12 for deleting Blue, and it is worth reaching for first.

One warning about NOT IN. If the inner query ever returned a NULL, x NOT IN (...) would be unknown for every x and the answer would be empty. It is safe here because booking.gnumber is part of a primary key and so is never null — but it is worth checking rather than assuming.

List the room numbers of all the rooms in the Small Hotel whose guests left on May 20, 2000, ordered by room number. 
SELECT booking.rnumber
FROM   booking, hotel
WHERE  (booking.hnumber = hotel.hnumber AND
        hotel.name = 'Small Hotel' AND
        `left` = '2000-05-20')
ORDER BY booking.rnumber ASC;
Empty set

Nobody left the Small Hotel that day, so the correct answer is no rows. Resist the urge to treat an empty result as a bug — check it against the data instead. The Small Hotel's departures are on 24 April and 15 May, and one guest has not left at all.

Ask for the 15th and the query proves itself:

+---------+
| rnumber |
+---------+
|       1 |
+---------+
Two kinds of quote on one line

The condition `left` = '2000-05-20' has a backtick mark on the left and a single-quote mark on the right, and they are not the same thing.

Backticks mark a name. `left` says “this is the column called left”, not the reserved word LEFT that MariaDB would otherwise try to read as the start of a function. They are MariaDB's spelling of what standard SQL writes with double quotes, and they are needed only when a name collides with a keyword.

Single quotes mark a value. '2000-05-20' is a literal — the thing being compared against, rather than something in the database.

Swap the two and nothing works. 'left' is the five-letter word, so 'left' = '2000-05-20' compares two strings, finds them different, and quietly returns no rows at all. And `2000-05-20` would be read as a column name, which does not exist.

But why is a date in quotes at all? Because MariaDB has no separate syntax for writing one down. You write the date as a string in 'YYYY-MM-DD' form, and the server converts it to a DATE on the spot — it knows to, because the other side of the = is a DATE column. The quotes are about how the value is typed, not about what type it ends up being.

Which is why the three conditions in this query are punctuated three different ways:

conditionthe value isquoted?
booking.hnumber = hotel.hnumberanother columnno — it is a name, not a value
hotel.name = 'Small Hotel'a stringsingle quotes
`left` = '2000-05-20'a datesingle quotes, same as a string

A number takes no quotes at all: Exercise 8.1 writes hnumber = 2222. Quoting it would still work, since MariaDB would convert '2222' back to a number, but it says the wrong thing about what the column holds.

The book, on Oracle, writes left plain, with no backticks — Oracle does not reserve the word. This is the exercise where you first meet the difference.

The book also wraps the column in trunc, because an Oracle DATE carries a time and '2000-05-20' would mean midnight exactly. Here the column holds no time, so the comparison is direct — but the habit is a good one to understand, because the moment a column becomes a DATETIME an equality test on it starts failing for reasons that are invisible in the output.

List full locations (room number and hotel name) of all the rooms to which guests are arriving today, where you do not know what date it is. 
SELECT rnumber, hotel.name
FROM   hotel, booking
WHERE  (hotel.hnumber = booking.hnumber AND CURDATE() = arrived);
+---------+-----------+
| rnumber | name      |
+---------+-----------+
|       7 | New Hotel |
+---------+-----------+

“Where you do not know what date it is” is the whole instruction. It forbids typing a date into the query and requires asking the server — CURDATE() in MariaDB, sysdate in the book's Oracle. A query with a literal date in it is wrong tomorrow; this one is right every day.

The row you get is Busy Traveler's, which is stored as CURDATE() precisely so that this question has an answer whenever the file is loaded.

List the names of all guests that are leaving the day after tomorrow, where you do not know which date is today. 
SELECT guest.name
FROM   guest, booking
WHERE  (guest.gnumber = booking.gnumber AND `left` = CURDATE() + INTERVAL 2 DAY);
Empty set

Empty, correctly: the only booking anchored to today ends tomorrow, not the day after. Ask for tomorrow and it appears:

SELECT guest.name
FROM   guest, booking
WHERE  (guest.gnumber = booking.gnumber AND `left` = CURDATE() + INTERVAL 1 DAY);
+---------------+
| name          |
+---------------+
| Busy Traveler |
+---------------+

Date arithmetic is not addition. The book writes sysdate+2, which works in Oracle because a DATE there is a number of days. MariaDB wants the unit named: CURDATE() + INTERVAL 2 DAY. Writing CURDATE() + 2 does something else entirely — it converts the date to the number 20261009 and adds two.

Guests who have not checked out have left set to NULL, and NULL = anything is unknown, never true. They are excluded here, which is what the question wants.

List the name of the guest who was the first to arrive in the year 2000. 
SELECT name
FROM   guest, booking
WHERE  guest.gnumber = booking.gnumber AND
       arrived >= '2000-01-01' AND
       arrived NOT IN
         (SELECT b1.arrived
          FROM   booking b1, booking b2
          WHERE  b1.arrived >= '2000-01-01' AND
                 b2.arrived >= '2000-01-01' AND
                 b1.arrived > b2.arrived);
+---------+
| name    |
+---------+
| Any Guy |
+---------+

“First” written without MIN. This is the notMax pattern of Lecture 11, upside down. The subquery pairs every in-range arrival with every other and keeps the later one of each pair — so it is the set of arrivals that something beats. The earliest is the one date not in that set.

Two copies of booking, and the comparison between them. Exactly as in Lecture 11's notMax: a superlative needs the relation compared against itself, which means naming it twice.

The year condition appears three times on purpose. It is in the outer query and on both copies inside. Leave it off b2 and the four 1999 arrivals start beating things, so every year-2000 arrival lands in the excluded set and the answer is empty.

With MIN it is shorter:

SELECT name
FROM   guest, booking
WHERE  guest.gnumber = booking.gnumber
  AND  arrived = (SELECT MIN(arrived) FROM booking WHERE arrived >= '2000-01-01');

Both return one row here. If two guests had arrived the same morning, both would return two — “the guest who” in a question is not a promise that the answer is unique.

What is the total income from bookings for double rooms at the Big Hotel today? 
SELECT SUM (price_night)
FROM   room, hotel
WHERE  room.hnumber = hotel.hnumber AND
       hotel.name = 'Big Hotel' AND
       room.type  = 'double' AND
       room.rnumber IN
         (SELECT booking.rnumber
          FROM   booking, hotel h2
          WHERE  booking.hnumber = h2.hnumber AND
                 h2.name = 'Big Hotel' AND
                 booking.arrived <= CURDATE() AND
                 (booking.`left` >= CURDATE() OR booking.`left` IS NULL));
+------------------+
| SUM(price_night) |
+------------------+
|             NULL |
+------------------+

SUM of nothing is NULL, not zero. No double room at the Big Hotel is occupied today, so no row reaches the aggregate, and SQL answers with a null rather than a 0. If the figure is going into a report, that difference matters — a null is not a zero and most things that read the answer will not treat it as one.

Standing today's date in for a day when the hotel had guests shows the query working:

  -- with '2000-05-13' in place of CURDATE()
+------------------+
| SUM(price_night) |
+------------------+
|           100.00 |
+------------------+

“Occupied today” is two conditions, and the second has a null case. Arrived on or before today, and either left on or after today or not left at all. Drop the IS NULL half and every guest still in residence silently stops counting — which is the single most common way to get this kind of query wrong.

Why the subquery can match on rnumber alone. A room is identified by the pair, so matching half a key is usually the error of Exercise 8.5. It is safe here only because both the outer query and the subquery have already been pinned to the Big Hotel — which is why hotel appears twice, once outside and once as h2 inside. Drop h2 and the set becomes every room number booked anywhere, and the Big Hotel's room 1 starts counting because somebody is in room 1 of the Small Hotel.

List the room numbers, along with hotel numbers, of all the rooms of type double at the Big Hotel that are today unoccupied, where you do not know what date it is today. 
SELECT room.hnumber, room.rnumber
FROM   room, hotel
WHERE  hotel.hnumber = room.hnumber AND
       hotel.name = 'Big Hotel' AND
       room.type = 'double' AND
       room.rnumber NOT IN
         (SELECT booking.rnumber
          FROM   booking, hotel h2
          WHERE  booking.hnumber = h2.hnumber AND
                 h2.name = 'Big Hotel' AND
                 booking.arrived <= CURDATE() AND
                 booking.`left` >= CURDATE());
+---------+---------+
| hnumber | rnumber |
+---------+---------+
|    1111 |       1 |
|    1111 |       2 |
+---------+---------+

Exercise 8.16 with NOT IN in place of IN, and the same “build the set, then exclude” shape as Exercise 8.11. Both of the Big Hotel's doubles are free, because the only bookings in that hotel are from the year 2000.

The book's version here omits the IS NULL case that its own Problem 772 includes one page earlier. On this data it makes no difference, since the Big Hotel has no open stay. On data where somebody had checked in and not out, this query would call their room unoccupied. Worth writing both and deciding which you believe.

Note that omitting it is also what keeps the NOT IN safe. Had the subquery selected booking.`left` rather than the room number, a single open stay would have put a NULL in the set and emptied the whole answer.

Increase the price of every room by 10% plus an additional dollar. 
UPDATE room SET price_night = price_night * 1.1 + 1;
+---------+---------+--------+-------------+
| rnumber | hnumber | type   | price_night |
+---------+---------+--------+-------------+
|       1 |    1111 | double |      111.00 |
|       2 |    1111 | double |      112.10 |
|       3 |    1111 | family |      113.20 |
|       4 |    1111 | family |      114.30 |
|       1 |    2222 | double |      115.40 |
|       2 |    2222 | double |      116.50 |
...
|       7 |    4444 | family |      123.10 |
+---------+---------+--------+-------------+

Order of operations decides the answer. price_night * 1.1 + 1 is ten percent and then a dollar; (price_night + 1) * 1.1 is a dollar and then ten percent, and gives a different number. The English “10% plus an additional dollar” settles it, barely — this is the sort of sentence worth reading twice before you write arithmetic from it.

The right-hand side reads the old value of the column for every row, so there is no danger of an update compounding on itself as it goes.

Add ten dollars to the price of all rooms in the New Hotel that are cheaper than sixty dollars per night. 
UPDATE room
SET    price_night = price_night + 10
WHERE  price_night < 60 AND
       hnumber IN (SELECT hnumber FROM hotel WHERE name = 'New Hotel');
Query OK, 0 rows affected

Nothing changes, because the New Hotel's cheapest room is $111. Run the same statement with 115 in place of 60 and three of its four rooms move:

+---------+---------+--------+-------------+
| rnumber | hnumber | type   | price_night |
+---------+---------+--------+-------------+
|       4 |    4444 | double |      119.00 |
|       5 |    4444 | family |      124.00 |
|       6 |    4444 | double |      122.00 |
|       7 |    4444 | family |      121.00 |
+---------+---------+--------+-------------+

Why a subquery at all? UPDATE names one relation and has no FROM clause, so there is nowhere to put hotel — and the hotel's name is what the question gives you. The subquery turns that name into the set of matching hotel numbers, and IN tests the row being updated against it. This is the shape Lecture 12 uses four times over to delete Blue.

The price condition stays outside. It is about the row being changed, so it belongs in the UPDATE's own WHERE clause; only the part that needs another relation goes into the subquery. The split is worth making deliberately — put the price test inside and you are asking a different question.

Increase by ten dollars the price of all those rooms for which guests are booked to arrive not earlier than the next month, where you do not know what the current month is. 
UPDATE room SET price_night = price_night + 10
WHERE  hnumber IN (SELECT booking.hnumber
                   FROM   booking
                   WHERE  booking.rnumber = room.rnumber AND
                          booking.arrived > LAST_DAY(CURDATE()));
Query OK, 0 rows affected

LAST_DAY is the whole trick. “Not earlier than next month” means “after the last day of this month”, and LAST_DAY(CURDATE()) gives that date without your needing to know whether this month has 28, 30 or 31 days. The book writes last_day(sysdate); the name happens to be the same.

No row changes, because every booking in the data is either from the year 2000 or is today's. Standing 30 April 2000 in for the end of the month shows the shape — four rooms have a guest arriving after that date, and all four go up by ten:

+---------+---------+--------+-------------+
| hnumber | rnumber | type   | price_night |
+---------+---------+--------+-------------+
|    1111 |       1 | double |      110.00 |
|    2222 |       1 | double |      114.00 |
|    3333 |      10 | single |      124.00 |
|    4444 |       7 | family |      121.00 |
+---------+---------+--------+-------------+

They are in four different hotels: the condition is about the booking's date, not about where the room is. Room 2 of the Old Hotel is not in the list, because its guest arrives on 30 April exactly and the comparison is strictly greater.

This subquery does mention the row being updated, and here there is no way round it. A room is a pair, so the set has to be built for this room number and then the room's own hotel tested against it. Compare Exercise 8.20, where one IN against a fixed set was enough because the question named a single hotel.

Delete all the rooms located in the Horrible Hotel. 
DELETE FROM room
WHERE  hnumber IN (SELECT hnumber FROM hotel WHERE name = 'Horrible Hotel');
Query OK, 0 rows affected

There is no Horrible Hotel, so the subquery returns nothing, hnumber IN () is false for every row, and nothing is deleted. No error: asking SQL to delete rows that do not exist is a perfectly ordinary thing to do, and it reports zero rather than complaining.

Had the hotel existed, this would have failed the moment one of its rooms was booked — booking has a foreign key into room, and deleting a parent whose children remain is refused. Compare Exercise 8.30, where the shop's supplier has to be dismantled from the bottom up.

Delete all the bookings of those guests who are booked to arrive on January 1, 2000. 
DELETE FROM booking WHERE arrived = '2000-01-01';
Query OK, 0 rows affected

Nobody arrives on that date, though two guests leave then. Reading arrived where the data says left is the mistake this question is built to catch, and the only defence is to look at the table.

The book's own answer has the wrong year. It prints

DELETE FROM booking
WHERE trunc(arrived) = '01-JAN-1999';

for a question that says January 1, 2000. Deleting nothing either way here, so the slip is invisible unless you check — which is the argument for running an answer key rather than reading it.

The date that does remove something is 31 December 1999, Mary Clever's arrival:

Query OK, 1 row affected

Deleting from booking is always safe here. Nothing references it, so it is the leaf of this schema and has no children to orphan.

Assume the database is empty. Write a complete piece of SQL that stores the following. Our New Hotel, numbered 4445, is located at Green Forest. Mr Magnus Famous-Rich is booking room 331 (of type single) in this hotel, at two hundred dollars per night, starting today (whenever that is). Mr Famous-Rich is our guest number 1. He lives at One Big Castle Drive. 
INSERT INTO hotel VALUES (4445, 'New Hotel', 'Green Forest');

INSERT INTO room VALUES (331, 4445, 'single', 200);

INSERT INTO guest VALUES (1, 'Magnus Famous-Rich', 'One Big Castle Drive');

INSERT INTO booking (hnumber, rnumber, gnumber, arrived)
VALUES (4445, 331, 1, CURDATE());
+---------+---------+------------+------+---------+
| hnumber | gnumber | arrived    | left | rnumber |
+---------+---------+------------+------+---------+
|    4445 |       1 | 2026-10-09 | NULL |     331 |
+---------+---------+------------+------+---------+

The order is forced, and it is the referential order. A row carrying a foreign key can only go in after the row it points at. booking points at guest and at room, and room points at hotel, so the booking is necessarily last. Put it first and the server says:

ERROR 1452 (23000): Cannot add or update a child row: a foreign key
constraint fails (`hotel`.`booking`, CONSTRAINT `booking_ibfk_1`
FOREIGN KEY (`gnumber`) REFERENCES `guest` (`gnumber`))

The last insert names its columns; the others do not. That is not decoration — left is unknown, and the only way to leave a column out of an INSERT is to list the ones you are supplying. It comes out NULL, which is the correct reading of “has not checked out”.

Today is CURDATE() again, for the same reason as Exercise 8.13: the question says “whenever that is”.

Note that the number 4445 is ours: the narrative says 4444, but the Hotel database already has a New Hotel at 4444, and inserting a second row with that key is refused by the primary key. On a genuinely empty database, use 4444 as the question says.

Read the following query. (a) Describe in one sentence, for a non-specialist, what it does. (b) Write the equivalent relational algebra, using only σ, Π, ×, ∪ and −. 
SELECT name, rnumber, price_night
FROM   hotel, room
WHERE  (room.hnumber = hotel.hnumber AND price_night <= 110);

(a) It lists every room costing no more than $110 a night, giving the room's number, its price, and the name of the hotel it is in.

+-------------+---------+-------------+
| name        | rnumber | price_night |
+-------------+---------+-------------+
| Big Hotel   |       1 |      100.00 |
| Big Hotel   |       2 |      101.00 |
| Big Hotel   |       3 |      102.00 |
| Big Hotel   |       4 |      103.00 |
| Small Hotel |       1 |      104.00 |
| Small Hotel |       2 |      105.00 |
| Small Hotel |       3 |      106.00 |
| Small Hotel |       4 |      107.00 |
+-------------+---------+-------------+

(b) The product, then the condition, then the columns — which is the order Lecture 10 reads a SELECT in:

R = Π[name, rnumber, price_night] σ[F] (hotel₁ × room₂)

F ≡ [ hnumber₁ = hnumber₂ ∧ price_night ≤ 110 ]

The subscripts are not optional. Both relations have a column called hnumber, so the product has two of them and the condition has to say which is which. In SQL the same job is done by room.hnumber and hotel.hnumber — the dot is renaming, written differently.

Going the other way is the habit this exercise is for. Reading a query you did not write, in a schema you half remember, is most of what the job turns out to be.

R = Π[workOrderID₁, carID₁] σ[F] (repairJob₁ × mechanic₂)

Find social security number and name of those mechanics that have never been officers in charge of a car repair job. 
SELECT socSecNum, name

The “never” shape of Exercise 8.11 again, and the shortest version of it on this page: the subquery is one column of one table, with no condition at all. Every officer who has ever run a job is in that set, and the mechanics left over are the answer.

One warning about NOT IN. If the inner query ever returned a NULL, x NOT IN (...) would be unknown for every x and the whole query would return nothing — not an error, just an empty answer. It is safe here because repairJob.officer is a foreign key that is never null. Check that before trusting the shape; it is the one way NOT IN can lie to you.

Find name and rank of those suppliers whose parts fit cars made by at least two different manufacturers. (It is not required that one part fit multiple cars — it is required that at least two different car manufacturers find some parts that fit their cars among the parts supplied by the supplier.) 
SELECT DISTINCT s.name, s.`rank`
FROM   supplier s, supplierLine L1, supplierLine L2, fit F1, fit F2
WHERE
    s.name = L1.supplierName AND s.name = L2.supplierName AND
    L1.partManufacturerId = F1.partManufacturerId AND L1.partNumber = F1.partNumber AND

The parenthetical in the question is the hard part. It rules out the reading “one part that fits two makes”. Ignore cars made before the year 2000, and do not report manufacturers that had fewer than 10 cars repaired in the shop. 
SELECT  m.name, m.address,
        COUNT (DISTINCT c.VIN),
        COUNT (DISTINCT c.modelCode),
        COUNT (DISTINCT r.officer),
        COUNT (*),
        MIN (r.dateBrought), MAX (r.dateBrought)
FROM    manufacturer m, carInstance c, repairJob r
WHERE   m.name = c.manufacturerId AND
        c.VIN  = r.carID AND
        YEAR (c.dateMade) >= 2000
GROUP BY m.name, m.address
HAVING   COUNT (DISTINCT c.VIN) >= 10;
Empty set

Nothing qualifies, because no manufacturer in this little database has ten repaired cars — the largest has two. That is deliberate: you can watch the HAVING clause do its work by lowering the threshold to 2, with the six aggregate headings shortened here to fit the page:

+------------------+--------------+------+-------+---------+----------+------------+------------+
| name             | address      | cars | modls | offcrs  | COUNT(*) | earliest   | latest     |
+------------------+--------------+------+-------+---------+----------+------------+------------+
| HappyForgerWorks | 1 Anvil Road |    2 |     2 |       2 |        2 | 2024-04-02 | 2024-05-18 |
+------------------+--------------+------+-------+---------+----------+------------+------------+

The server's own headings are the expressions themselves — COUNT(DISTINCT c.VIN), MIN(r.dateBrought) and so on — which is why an aggregate column is usually given a name with AS before anybody has to read the result.

and again with the year condition and the HAVING both removed:

+------------------+-----------------------+----------+
| name             | COUNT(DISTINCT c.VIN) | COUNT(*) |
+------------------+-----------------------+----------+
| GreatConjurer    |                     2 |        2 |
| HappyForgerWorks |                     3 |        3 |
| SolidWheel       |                     1 |        1 |
+------------------+-----------------------+----------+

Six aggregates over one grouping. Everything in the SELECT list is either grouped on or aggregated — that is the rule, and it is why m.address has to appear in the GROUP BY even though it adds nothing (the name is already a key).

COUNT(DISTINCT c.VIN) and COUNT(*) are different questions. The first is how many vehicles; the second is how many repair jobs. A car brought in three times contributes 1 and 3. The question asks for both, which is the point of the exercise: once rows have been multiplied by a product, a plain count stops meaning what you assumed.

Where the conditions go. “Made before 2000” tests a single row, so it belongs in WHERE and happens before grouping. “Fewer than 10 cars repaired” tests a whole group, so it belongs in HAVING and happens after. They are not interchangeable and the server will tell you so if you try.

The book writes the year test as to_number(to_char(c.dateMade, 'YYYY')) >= 2000, which is Oracle's way of pulling the year out of a date. MariaDB has YEAR().

Find year, month, and page number of every catalog page that contains a picture of some shirt with sales price less than 7 dollars.

Find styles and names of original designers of all shirts produced by Superb Seamstress Star factory. 
SELECT theStyle, designerName

       shirtColor.style = originalDesign.theStyle AND
       shirtSize.sizeOption > 20 AND
       originalDesign.theDesigner = designer.designerId AND
       designer.designerName = 'Smart Dresser';
+-----------+
| colorCode |
+-----------+
| BK        |
| GR        |
| WH        |
+-----------+

Two conditions on the same style, reached by two different routes. shirtColor.style is matched against shirtSize.basicStyle and against originalDesign.theStyle; all three name the same style, under three different column names. Writing them out is what the no-join rule costs, and what it buys is that nothing is matched by accident.

DISTINCT is in the book's own answer here, and it is needed: S-1003 exists in sizes 22 and 24, so without it every color of that style would be listed twice.

The query says “Smart Dresser designers”, plural, and means it. D-01 and D-03 both carry that name, so both are matched. D-03's style S-1004 then drops out anyway, for a different reason — its only size is 18.

Find the name of each factory that has, at any point in time, produced the same shirt style under different product names. 
SELECT DISTINCT factoryName
FROM   factory, purchaseDeal p1, purchaseDeal p2
WHERE  p1.item = p2.item AND
       p1.producedBy = p2.producedBy AND
       p1.productName != p2.productName AND
       factoryId = p1.producedBy;
+-------------+
| factoryName |
+-------------+
| Tiny Thread |
+-------------+

Two copies of one relation, and the third line is the whole query. Same style, same factory, different product name. Drop p1.productName != p2.productName and every deal pairs with itself, so every factory qualifies — the inequality is not a refinement, it is the question.

Tiny Thread makes S-1003 as both Premium and Elite. Superb Seamstress Star uses the product name Classic for two different styles, which is a different thing and correctly not matched.

Each qualifying pair is found twice, once as (Premium, Elite) and once as (Elite, Premium), so DISTINCT is doing real work even though only one factory qualifies. The usual way to avoid that is p1.productName < p2.productName, which picks one ordering of each pair.

Find styles and sales prices of those shirts that have outstanding purchase orders — orders not yet due as of today, not knowing what date it is today. 
SELECT styleCode, salesPrice
FROM   shirt, purchaseDeal
WHERE  (styleCode = item AND
        (orderDue >= CURDATE() + INTERVAL 1 DAY OR orderDue IS NULL));
+-----------+------------+
| styleCode | salesPrice |
+-----------+------------+
| S-1002    |      12.00 |
| S-1002    |      12.00 |
| S-1003    |      24.99 |
| S-1003    |      24.99 |
+-----------+------------+

“Not yet due” is tomorrow or later, not today or later — an order due today is due. Hence the + INTERVAL 1 DAY, which the book writes trunc(sysdate + 1).

And a null due date counts as outstanding. That is a judgement about what the data means: no due date recorded, so the order has not come due. The alternative reading — that the null means something else entirely — is equally defensible, and the lesson is that nothing in SQL decides it for you. What SQL does decide is that orderDue >= anything is unknown for a null, so the IS NULL test has to be written separately or the row vanishes silently.

Both styles come out twice, because each has two outstanding deals. DISTINCT would fix it; whether it should depends on whether “shirts” or “orders” is what is being asked for.

Find style and sales price of the most expensive shirt(s). Then write the same query without using MAX, and account for the difference.

With MAX:

SELECT styleCode, salesPrice
FROM   shirt s
WHERE  s.salesPrice = (SELECT MAX (salesPrice) FROM shirt);
+-----------+------------+
| styleCode | salesPrice |
+-----------+------------+
| S-1003    |      24.99 |
| S-1006    |      24.99 |
+-----------+------------+

Two rows, because two shirts tie. The (s) in the question is a warning that a superlative need not be unique.

Without MAX: this is the notMax pattern of Lecture 11. Pair every shirt with every other, keep the cheaper one of each pair, and the answer is whatever is left out of that set.

SELECT styleCode, salesPrice
FROM   shirt
WHERE  styleCode NOT IN (SELECT s1.styleCode
                         FROM   shirt s1, shirt s2
                         WHERE  s1.salesPrice < s2.salesPrice);
+-----------+------------+
| styleCode | salesPrice |
+-----------+------------+
| S-1003    |      24.99 |
| S-1005    |       NULL |
| S-1006    |      24.99 |
+-----------+------------+

Three rows, and one of them has no price at all. The subquery is the set of shirts that something beats, and S-1005 never lands in it: NULL < 24.99 is unknown, not true, so the pair that should have knocked it out never matched. Nothing beat it, so it comes back as one of the dearest shirts in the catalog.

The fix is to say so explicitly:

SELECT styleCode, salesPrice
FROM   shirt
WHERE  salesPrice IS NOT NULL
  AND  styleCode NOT IN (SELECT s1.styleCode
                         FROM   shirt s1, shirt s2
                         WHERE  s1.salesPrice < s2.salesPrice);
+-----------+------------+
| styleCode | salesPrice |
+-----------+------------+
| S-1003    |      24.99 |
| S-1006    |      24.99 |
+-----------+------------+

This is the whole argument for the aggregate functions. MAX ignores nulls by definition, so the one-line version was right the first time and stayed right without your having to think about it. Hand-rolling the same idea out of comparisons means noticing the null yourself — and the failure is silent, because a shirt with no price looks exactly like a shirt nothing beats.

Worth running both against the data with S-1005 removed. They agree perfectly, which is the point: the pattern is not wrong, it is only incomplete, and incomplete in a way no amount of staring at the output of a smaller example would reveal.

Find the sales price(s) of the shirt style(s) with the largest purchased price that has ever been ordered. 
SELECT salesPrice
FROM   shirt, purchaseDeal
WHERE  (styleCode = item AND
        purchasePrice = (SELECT MAX (purchasePrice) FROM purchaseDeal));
+------------+
| salesPrice |
+------------+
|      24.99 |
+------------+

Two prices, and the query must not confuse them. purchasePrice is what the factory charges Cool Cotton; salesPrice is what the customer pays. The MAX is taken over the first and the answer reported from the second.

The dearest deal is Tiny Thread's Elite at 15.50, which is style S-1003, selling at 24.99. Note that the query says nothing about which style it is — add styleCode to the SELECT list if the answer should be readable.

A subquery on the right of = has to return exactly one value, and MAX guarantees that it does. This is the form Lecture 12 uses for the highest salary. Had the subquery returned two rows the server would have refused it, and IN would be the operator to reach for instead — which is the difference between the two: = compares against a value, IN against a set.

Shirt factory Tiny Thread has changed its name into Reliable Rope. Record the change in the database. 
UPDATE factory
SET    factoryName = 'Reliable Rope'
WHERE  factoryName = 'Tiny Thread';
+-----------+------------------------+
| factoryId | factoryName            |
+-----------+------------------------+
| F-01      | Superb Seamstress Star |
| F-02      | Reliable Rope          |
| F-03      | Rapid Stitch           |
+-----------+------------------------+

One row, one table, nothing else to do — and that is the exercise. purchaseDeal refers to the factory by factoryId, not by name, so the five deals Tiny Thread had are untouched and still correct. The name was stored in exactly one place.

Compare the Car Repair Shop, where supplierLine references a supplier by name. Renaming a supplier there means changing the parent and every child, and the foreign key will refuse to let you do the first without the second. Same operation, different schema, wholly different amount of work — which is the practical argument for keys that never have to change.

Going further

Three themes recur across all three databases on this page, and they are worth collecting.

A duplicate in the output is usually a question about what you were counting. Exercises 8.28, 8.30, 8.35, 8.37 and 8.38 all produce repeated rows, and in only one of them is the repetition what the question wanted. DISTINCT is the fix; knowing whether you need it is the skill.

A null is not a value and does not behave like one. It removed a shirt from Exercise 8.34, smuggled a priceless one into the answer in 8.39, had to be tested for separately in 8.16 and 8.38, and is the correct way to record “has not checked out” in Exercise 8.24. Three-valued logic is the one part of SQL that cannot be learned by analogy with anything else.

Every answer here is written in the vocabulary of Lectures 11 and 12 — nothing beyond SELECT, FROM, WHERE, DISTINCT, the comma product, the five aggregate functions, GROUP BY, HAVING, ORDER BY, and IN and NOT IN against a subquery. SQL has more than this: EXISTS and NOT EXISTS for asking whether a subquery found anything at all, ALL and ANY for comparing against every or some member of a set, and the outer join for keeping rows that match nothing. Each would shorten two or three of these answers. None is needed for any of them, which is worth knowing before you reach for one.

The key you have to match is the key the schema declares. A room is a pair, a purchase deal is a triple, a part is a pair. Matching on half a key is the error that runs cleanly and answers wrongly, and no amount of reading the output will reveal it — only reading the schema will.

What this set still has not asked: whether any of these three schemas stores the same fact in two places. That is normalization, and the problem book has a long section on exactly these databases when you get there.
