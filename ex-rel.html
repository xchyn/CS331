Exercise set 3 · after the relational-model lectures Relational model

From diagram to tables

Relations, keys and the three integrity constraints; the rules that turn an ER or EER diagram into a set of relational schemas, and the two places where those rules leave you a real choice. Twelve exercises — four abstract mapping drills, one in reverse, four on a live database, and three that map diagrams you drew in Sets 1 and 2.

Sets 1 and 2 were about deciding what is true of the enterprise. This set is about carrying those decisions across into a structure a DBMS can actually enforce. Most of the mapping is mechanical — which is exactly why the two steps that are not mechanical are where the marks are.

The payoff is that constraints stop being notation. A double line in Set 1 was a claim about the world; here it becomes a NOT NULL, or the difference between one table and two. If you have ever wondered why the participation constraint mattered, this is the answer.

Every schema on this page was run

All the answers below were created as real tables in MariaDB, with their primary keys and foreign keys declared, before they went into the page. Where a solution claims a constraint is enforced, the constraint was tested by trying to insert a row that violates it and watching the server refuse. Two of those tests are quoted in the solutions, because their outcome is the point of the exercise.

3.1What a relational schema is

A relation schema is a name and a list of attributes, each over some domain. The notation used throughout this set — and in the problem book — puts the primary key underlined in the attribute list:

professor (socSecNum, firstName, lastName, salary, rank, wizardID)
department (name, office, phone, chairId)
member (deptName, profId)

Foreign keys do not fit in that notation, so they are listed separately. This is not a stylistic choice: a foreign key is a statement about a pair of schemas, and it cannot be written inside either one.

fieldin schemareferences schema
chairIddepartmentprofessor
profIdmemberprofessor
deptNamememberdepartment

A super-key is any set of attributes that is unique across the relation; a candidate key is a minimal one; the primary key is the candidate key you chose. The distinctions matter in Exercise 3.1 and then mostly stop mattering until normalization.

3.2The integrity constraints

Three constraints hold in every relational database, whatever it is about. Learn them as sentences — they are worth full marks on an exam and take fifteen seconds to write.

constraintstatement
primary keyNo two tuples in a relation may agree on the values of the primary key.
entity integrityNo attribute that belongs to the primary key can assume a null value.
referential integrityThe value of any foreign key either occurs in a tuple of the referenced relation, or is null.

The third one has a consequence that catches people out: a foreign key is allowed to be null unless something else forbids it. So "every car must be assigned to a facility" — a double line in Set 1 — is not expressed by the foreign key at all. It needs NOT NULL on top.

3.4The two judgement calls

A 1 : M relationship, and what participation does to it. The default is to put a foreign key on the M side. That is correct whenever participation on that side is total: every entity has a partner, so the column is never null and you have lost nothing.

When participation is partial, the foreign key is null for every unrelated entity — and if that is most of them, the column is mostly holes. Giving the relationship its own relation stores only the pairs that exist. Both designs are correct; the diagram tells you which one the enterprise deserves, and Exercises 3.2 and 3.3 are the same diagram with that one line changed.

A specialization. Three options, and which are legal depends on the d/o and total/partial constraints you drew in Set 2. Exercise 3.12 works all three and shows what each one can and cannot enforce.

The rule that is never a judgement call

An M : N relationship always becomes its own relation. There is no foreign-key version of it — a column holds one value, and the whole point of M : N is that there are many. Students who "simplify" by putting a foreign key on one side have not simplified the design, they have changed it into a different one.

3.5Exercises

For every schema you write, underline the primary key and list the foreign keys separately — an answer without its foreign keys is half an answer. Draw or write before you click.

Warm-up

(a) State the entity integrity constraint. (b) State the referential integrity constraint. (c) State the primary key constraint. (d) What is a foreign key? (e) Explain briefly which attributes of a super-key in a relation, if any, may be null.

(a) Entity integrity. No attribute that belongs to the primary key can assume a null value.

(b) Referential integrity. The value of any foreign key either occurs in a tuple of the referenced relation or is null. In other words: if a relational schema R has a foreign key K which references schema S, then in each tuple of R the value of K must be equal to the value of K in some tuple of S, unless the entire K is null.

(c) Primary key constraint. No two tuples in a relation may agree on the values of the primary key.

(d) Foreign key. A foreign key of a schema R which references schema S is a set of fields of R that forms the primary key of S.

(e) Super-key attributes and nulls. Since no attribute of a primary key may be null, exactly those attributes of the given super-key that do not belong to the actual primary key may be null. This may mean all such attributes, or some of them, or none, depending on the relationship of this super-key and the primary key.

Why (e) is the interesting one. It is the only part that requires you to hold both definitions at once. A super-key is any unique set; the primary key is one particular minimal unique set. The attributes in the difference are under no entity-integrity obligation at all — and a super-key containing a nullable attribute is still a super-key, which is one reason we bother to pick a primary key rather than using any old unique set.

Each of the next three gives an ER diagram in letters rather than nouns. That is deliberate: with no story to lean on, the only thing left to read is the notation.

Step 1 — the entity sets. E, F and H are strong, so each becomes a relation keyed by its own key attribute: E(K, …), F(L, …), H(J, …).

Step 2 — the multivalued attribute. V is a double ellipse, so it cannot be a column of F — a column holds one value. It becomes Fv(L, V) with both attributes in the primary key: the same F may have many V values, and the same V value may belong to many F’s. Forgetting to put V in the key is the usual slip; it would allow only one V per F, which is what you were trying to escape.

Step 3 — the weak entity set. W’s key is its owner’s key plus its own partial key: W(J, P, D) with (J, P) primary and J a foreign key to H. The double line into G is what makes J non-null here, and it is non-null by construction, since it is part of the primary key.

Step 4 — the two relationships, which go differently. S is M : N, so it must become its own relation S(J, L) keyed by both. R is M : 1 from E to F, so the default would be a column L inside E — but E’s participation in R is partial (a single line), so that column would be null for every E with no F. The book gives R its own relation R(K, L), keyed by K alone: at most one row per E, so the cardinality is still enforced, and E’s with no partner simply have no row.

Keep that last paragraph in mind for the next exercise, where exactly one line in the diagram changes.

Four things changed from Figure 55, and each one changes the schema.

1. V is now composite, not multivalued. It is a plain ellipse with Y and X hanging off it. A composite attribute flattens: its leaves become columns of the owner and the composite itself vanishes, giving F(L, B, X, Y). No extra relation. Compare Fv in Exercise 3.2 — one ellipse drawn differently is the whole difference between four columns and a second table.

2. E now participates totally in R. The line from E to R is doubled. Every E has an F, so the foreign key L can live inside E and be NOT NULL — there are no holes to avoid, and the separate R relation of Exercise 3.2 would now be an extra join for nothing. Hence E(K, A, L).

3. E has a specialization. N and T become relations keyed by the superclass’s key, each carrying only its own extra attribute and a foreign key up to E. This is option (a) of Exercise 3.12, and it is the only one available here: the specialization is partial, so some E is in neither subclass and a design without an E table would have nowhere to put it.

4. O is derived. Dashed ellipse, so it is computed, not stored. It contributes no column at all — the one mapping rule whose output is nothing.

A discrepancy in the printed answer

The problem book’s foreign-key table for this problem lists "L in R references L in F", but its own schema list for Figure 56 contains no relation called R — L now lives in E. The schema list is the part that matches the diagram, so the row above reads "L in E". Worth knowing in case you are comparing against the book and think you have lost a table.

Step 1 — F folds, K does not. Both are functional, and the difference is participation, exactly as in the previous two exercises. S participates totally in F (double line), so F’s attributes A and P and the foreign key D all fold into S. H participates partially in K (single line), so K keeps its own relation, keyed by C alone.

Step 2 — where a relationship’s attributes go. When a relationship folds, its attributes fold with it: that is why S carries A and P, which belong to F and not to S. When it does not fold, they stay with it: K carries Z. Losing these is the commonest way to drop information in this exercise.

Step 3 — the multivalued G. Its own relation Sg(L, G), both columns in the key. Same rule as Fv in Exercise 3.2.

Step 4 — the specialization. Y and E become relations keyed by H’s key C, each with its own attribute.

A sanity check worth doing. Every underlined key in the diagram appears as a primary key somewhere, and every line in the diagram is accounted for by either a foreign key or a whole relation. If a line has vanished, information has vanished with it.

The conceptual schema for the next exercise:

T1 (A, B, C)
T2 (G, H, J)
T3 (A, G, L)
T4 (A, P, M)

with foreign keys: A in T3 references T1; G in T3 references T2; A in T4 references T1.

Draw a complete ER diagram, indicating carefully all the applicable constraints, for the database whose conceptual schema is the one given just above. Your diagram has to be equivalent to that conceptual schema.

This is the previous three exercises run backwards, and the reasoning is the same rules read right to left.

Step 1 — which relations are entity sets? A relation whose primary key is a single attribute that is not a foreign key is a strong entity set. T1 (key A) and T2 (key G) qualify. Their non-key columns become attributes: B and C on T1, H and J on T2.

Step 2 — T4 is a weak entity set. Its primary key is (A, P) where A alone is a foreign key to T1. That is the signature of a weak entity set: a borrowed key extended by a partial key. So T4 is drawn with a double rectangle, P dash-underlined, and an identifying double diamond to T1 with a double line on the T4 side. M is an ordinary attribute of it.

Step 3 — T3 is a relationship. Its key is A alone, and it holds foreign keys to both T1 and T2. Key on one side only means at most one row per T1: the relationship is M : 1 from T1 to T2. Its extra column L is an attribute of the relationship. And because T3 was given its own relation rather than folded into T1, participation on the T1 side is partial — a single line.

Step 4 — what you cannot recover. A schema does not record whether the designer folded a total 1:M relationship or kept a partial one separate, so more than one diagram maps to the same tables. The diagram above is the natural reading; a diagram with total participation and T3 kept separate anyway would produce identical tables. Say which reading you took — that is what "equivalent to the given schema" asks for.

The Professor Payroll database

The next three work on one live database. Its Part I conceptual schema is the one quoted in §3.1: professor, department and member, with chairId in department referencing professor, and profId and deptName in member referencing professor and department.

An inexperienced programmer has converted the conceptual schema of the Professor Payroll database into the ER diagram given in Figure 59 above, and made two significant, independent mistakes. Find them, draw the correct diagram, and for each mistake write two explanations: one for the programmer, in technical terms, and one for the data administrator, saying how the business will suffer if the design is adopted uncorrected.

Both mistakes are cardinality marks, and both are found the same way: read what the tables say, then check whether the diagram says it too.

Mistake 1 — chair points the wrong way.

For the programmer: relation chair was programmed to be M : 1 from professor to department, but it must be M : 1 from department to professor, since chairId is a non-key attribute in table department. Furthermore, participation in relation chair must be mandatory on the side of department, since chairId is assumed to be non-null.

For the data administrator: if this is not corrected, the design will allow departments to have any number — zero or more — of professors as chair.

Mistake 2 — member is not functional at all.

For the programmer: relation member was programmed to be M : 1 from department to professor, but it must be M : M, since an instance of membership (in table member) is identified by a pair of identifiers, deptName and profId.

For the data administrator: if this is not corrected, the original design will prevent departments from having more than one member.

The technique, which generalises. The primary key of a table tells you the cardinality, and nothing else does.

  • A foreign key sitting in a table whose primary key is something else — chairId inside department — means "one per row of this table": the relationship is functional from this table.
  • A table whose primary key is both foreign keys — member(deptName, profId) — is M : N. It can hold the same department many times and the same professor many times.
  • A foreign key declared NOT NULL means total participation on that side.

Read those three off the tables before you look at the diagram, and a wrong diagram cannot hide.

The enterprise will start recording individual paychecks paid to professors. Paychecks are issued by departments: each department identifies its own paychecks by serial number, and each department has its own paycheck numbering, independent of other departments. In addition to the serial number and issuing department, a paycheck specifies the amount to be paid, and the professor to whom it is to be paid. A professor may receive a paycheck only from a department in which the professor is a member. Write a set of relational schemas to implement this upgrade. You may not modify any existing table, only introduce new ones.
paycheck (dpt, serNum, amount, prof)
fieldin schemareferences schema
dpt, profpaycheckmember

Step 1 — a paycheck is a weak entity. "Each department identifies its own paychecks by serial number… independent of other departments" is the definition of a partial key. So the primary key is (dpt, serNum), and dpt is inherited from the owner.

Step 2 — the sentence that makes this exercise interesting. "A professor may receive a paycheck only from a department in which the professor is a member." The obvious design gives paycheck two separate foreign keys, one to department and one to professor — and that design cannot enforce this rule at all. It would happily record a paycheck from a department the professor has nothing to do with.

The rule is about a pair, and there is already a table whose rows are exactly the legal pairs: member. So the foreign key is composite: (dpt, prof) together reference member(deptName, profId). One constraint, and the illegal paycheck becomes unrepresentable.

Verified. With one professor who is a member of CSCI only, the server accepts a CSCI paycheck and refuses a MATH one:

INSERT INTO paycheck VALUES ('MATH', 1, 5000, '111111111');
ERROR 1452 (23000): Cannot add or update a child row: a foreign key
constraint fails (`paycheck`, CONSTRAINT `paycheck_ibfk_1`
FOREIGN KEY (`dpt`, `prof`) REFERENCES `member` (`deptName`, `profId`))

That is the whole argument for the composite foreign key, and it is worth running yourself rather than taking on trust.

The enterprise will start recording subjects that individual professors teach. Subjects are identified by subject code and further characterised by name, extended textual description, and numeric difficulty rating. When a professor declares their willingness to teach a subject, the enterprise records this fact along with the professor's numeric preference rating of this subject. Additionally, the enterprise assigns its own numeric rating of the professor's appropriateness for the subject. Write a set of relational schemas to implement this upgrade, introducing new tables only.
subject    (code, name, description, difficulty)
wouldTeach (subjectCode, profCode, preference, fit)
fieldin schemareferences schema
subjectCodewouldTeachsubject
profCodewouldTeachprofessor

Step 1 — one new entity set. subject is strong: it has its own identifier and exists whether or not anyone teaches it.

Step 2 — the willingness is a relationship, and it is M : N. A professor may declare several subjects and a subject may attract several professors, so it becomes its own relation keyed by both foreign keys. No judgement call here — see the warning in §3.4.

Step 3 — where the two ratings go, which is the exercise. preference is the professor’s rating of that subject, and fit is the enterprise’s rating of that professor for that subject. Both are determined by the pair, so both are columns of wouldTeach. Putting difficulty there too would be the mirror-image error: a subject’s difficulty is a fact about the subject alone, and it belongs in subject.

This is the same test as Set 1’s "what is an attribute an attribute of?", now with tables instead of diamonds. The question has not changed; only the notation has.

A whole database

Dangerous Professor keeps a database with information about students who took her courses. The ER diagram is given in Figure 61 above. (a) Construct the relational schemas for this database, with an adequate level of normalization. (b) For each schema, state the primary key and the foreign keys, if any.
student  (id_number, name)
offering (year, semester, 4_digit_code, classroom_number)
course   (name, description)
given    (year, semester, 4_digit_code, course_name)
enroll   (year, semester, 4_digit_code, student_id_number, grade)

The foreign keys:

  • Fields year, semester, 4_digit_code in schema given form a foreign key that references fields year, semester, 4_digit_code in schema offering.
  • Field course_name in schema given is a foreign key that references field name in schema course.
  • Fields year, semester, 4_digit_code in schema enroll form a foreign key that references the same three fields in schema offering.
  • Field student_id_number in schema enroll is a foreign key that references field id_number in schema student.

Step 1 — the three-part key, and why everything downstream is wide. An offering is identified by year, semester and 4-digit code together: the code is reused every term. All three are underlined in the diagram, so all three are in the primary key — and every table that references an offering must carry all three columns. Half the work in this exercise is bookkeeping that follows from one decision in the diagram.

Step 2 — given keeps its own relation. It is 1 : M from course to offering, so course_name could have folded into offering. The book keeps it separate, and the key is the offering’s three fields alone — at most one course per offering, so the cardinality still holds. Folding it in is equally defensible; say which you did.

Step 3 — enroll is the M : N one. Its key is the offering’s three fields plus the student’s, four columns in all, and grade — an attribute of the relationship, not of either side — rides along. A student’s grade is not a fact about the student, and not a fact about the offering.

Why not give offering a surrogate key?

In practice you often would: one offering_id column, and enroll becomes two columns instead of four. That is a legitimate implementation decision and a real one — but it is not the mapping, and doing it silently in an exam answer loses the marks for the composite key. Map first, then say you would add a surrogate key and why.

Mapping what you already drew

The last three take diagrams from Sets 1 and 2 and finish the job. If you still have your own answers to those exercises, map yours rather than mine — the mapping is mechanical, so a disagreement means a disagreement about the diagram, which is the more interesting thing to find.

The multivalued attribute becomes the second table. "Contact phone numbers", plural, was a double ellipse in Set 1; here it is supplier_phone, with both columns in the key. This is the same rule as Fv in Exercise 3.2, now with a noun attached.

The relationship attributes land where the diagram said they would. price and brand name hung off the offer diamond because they are determined by the (supplier, medication) pair. In the schema they are ordinary columns of offer — and the reason they could not go on supplier or medication is now mechanical rather than conceptual: neither of those tables has a row per pair to put them in.

A one-column table is fine. medication has nothing but its key, because the Set 1 problem gave medications no attribute other than the generic name. Do not be tempted to delete it and use the name directly in offer: the table is what asserts that the medication exists, and the foreign key is what stops a typo inventing one.

The weak entity set. A copy is identified by its book plus its copy number, so the primary key is (isbn, copy_no) and isbn is also a foreign key. Three tables, not four: the identifying relationship of does not become a relation of its own — it is already represented by the isbn column that the weak entity had to borrow.

The M : 1 relationship folds, and takes its attribute with it. Every copy is in exactly one branch — total participation, drawn as a double line — so branch_name is a column of copy, declared NOT NULL, and date (here received) folds in beside it. This is the total case of §3.4, and it is why copy has five columns instead of a separate in table.

What the schema quietly confirms. Set 1 noted that this design records where a copy is now and forgets where it has been. Look at copy: one branch_name, one received, one row per copy. Moving a copy overwrites both. The limitation was arguable in the diagram; in the table it is plainly visible, which is a good reason to map a design before committing to it.

Map your answer to Exercise 2.8 — students, specialized totally and disjointly into graduates and undergraduates, with prior degrees hanging off the graduate subclass — into relational schemas. Give all three standard options for the specialization and say what each can enforce.

Option (a) — superclass plus one relation per subclass. Always legal, whatever the constraints.

student       (id, name, dob, major)
graduate      (id)
undergraduate (id, gpa)
degree        (id, issued, univers, major)

with id in graduate and undergraduate referencing student, and id in degree referencing graduate. Note where degree points: at graduate, not at student. That is the relationship attaching to the subclass, carried across intact — and it is what makes an undergraduate with a prior degree unrepresentable, which is what Set 2 said the diagram meant.

Option (b) — subclass relations only, no superclass. Legal only because this specialization is total: every student is in one of the two tables, so nothing is homeless.

graduate      (id, name, dob, major)
undergraduate (id, name, dob, major, gpa)

The shared attributes are repeated in both. It saves a join, and it cannot enforce disjointness: nothing stops the same id appearing in both tables. Tested, and it does not stop it — both inserts succeed:

INSERT INTO graduate      VALUES ('S1', 'x', '2000-01-01', 'CS');
INSERT INTO undergraduate VALUES ('S1', 'x', '2000-01-01', 'CS', 3.9);
-- both accepted: option (b) cannot enforce the d constraint

It also has nowhere natural to put a query over all students, and degree would now reference graduate directly.

Option (c) — one relation with a type column. Legal only because the specialization is disjoint — a single kind column holds one value, so an overlapping specialization could not use it.

student (id, name, dob, major, kind, gpa)

with kind in {graduate, undergraduate}. One table, no joins, and gpa is null for every graduate — harmless with two subclasses and one extra attribute, unpleasant with five subclasses and twenty.

The honest summary. None of the three enforces everything the EER diagram states. Option (a) enforces neither constraint, (b) enforces totality but not disjointness, (c) enforces both but pays in nulls. Whichever you choose, some constraint you drew in Set 2 survives only as a note to the implementer or a CHECK written by hand — which is the real reason the choice is worth thinking about rather than defaulting.

Going further

Every schema on this page was written by rule, and none of them was checked for redundancy. That is the next question: a set of tables can satisfy every integrity constraint and still store the same fact in two places, so that an update can make the database contradict itself. Deciding when that has happened, and splitting the tables until it cannot, is normalization — and the functional dependencies it works from are exactly the "what determines what" questions you have been answering since Set 1.
