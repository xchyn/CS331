Exercise set 6 · Lecture 10 Algebra to SQL

The same queries, in a language a server will run

Twenty-one of the Set 5 queries, each given with its algebra, translated into SQL, and run. Every solution shows the rows the server actually printed, so you can check your own answer against the data rather than against a claim.

The relational algebra was designed to be reasoned about; SQL was designed to be typed. They express the same queries, and the translation in one direction is almost mechanical — which is the useful news, because it means the hard thinking you did in Set 5 transfers intact. What does not transfer is the set semantics, and that is where the surprises are.

The questions are the lectures' and the book's; the instruction is ours

Every query below appears in Set 5: the first seven are the examples worked in Lectures 8 and 9, the rest are Problems 252–282 of the problem book. Asking for the SQL as well, and showing what it returns, is this page's addition.

6.1The correspondence

This is the whole of Set 6 in four lines. A query in the relational algebra and the SQL statement that runs it:

query in relational algebraSQL
Π[A1, ..., An]SELECT A1, ..., An
σ[F] ( R1 × ... × Rk )FROM R1, ..., Rk
F ≡ [ condition(s) ]WHERE condition(s);

Read bottom-up it is the algebra inside-out: the product first, then the selection, then the projection. SQL writes them in the opposite order from the one in which they happen, which is the single most confusing thing about the language and stops being confusing the moment you notice it.

The set operations go across just as directly:

algebraSQLnote
R ∪ SUNIONalready removes duplicates; UNION ALL does not
R ∩ SINTERSECTMariaDB 10.3+, PostgreSQL, Oracle
R − SEXCEPTOracle spells it MINUS; see §6.3 for the portable form
R1 × R2 (copies of one relation)FROM R r1, R r2the numbered copies become table aliases, one per copy

Two more details. A condition crosses unchanged except that ∧ is AND, ∨ is OR and ≠ is <>. And string literals take single quotes: double quotes mean an identifier in standard SQL, and MySQL's willingness to accept them for strings is a local dialect not worth relying on.

Finally, two forms worth knowing from the start:

SELECT * FROM table_name;                    -- selects the whole table
SELECT DISTINCT ... FROM ... WHERE ...;      -- selects distinct data

6.2Three things SQL adds

Bags, not sets. A relation is a set; a SQL table is a bag, and SELECT returns a bag. So Π translates to SELECT DISTINCT, not SELECT. Leave out the DISTINCT and a professor with four qualifying paychecks is listed four times — the answer is not merely untidy, it is a different relation. Exercise 6.13 shows exactly this.

The habit to build now

When translating an algebra expression, write DISTINCT every time you see a Π, mechanically, before thinking about whether it is needed. It is never wrong, it is occasionally essential, and deciding case by case is how the one that mattered gets missed. (In production code the calculus is different — a needless DISTINCT costs a sort — but correctness first.)

Three-valued logic. The algebra as taught here has no nulls. SQL does, and a comparison with NULL is neither true nor false but unknown, which WHERE discards. The consequence that bites: x <> 'Potions' is not satisfied by a row whose x is null, so a “not in Potions” query written with <> silently drops those rows. Both schemas here keep their relevant columns non-null, so nothing on this page is affected — but almost every real schema has nullable columns, and this is where the NOT EXISTS form of §6.3 earns its keep.

Everything the algebra cannot do. COUNT, SUM, AVG, MIN, MAX, GROUP BY, HAVING, ORDER BY, LIMIT. None of these has an algebraic counterpart, which is why Exercise 6.7 goes the long way round to find a maximum: the algebra it is translating had no MAX to translate. Doing it the SQL way is a fair answer to a different question, and both are worth being able to write.

The other three statements of Lecture 10 need no algebra at all, because the algebra has no way to change a database:

INSERT INTO table_name VALUES (value1, value2, ...);
INSERT INTO table_name (column1, column2, ...) VALUES (value1, value2, ...);

UPDATE table_name SET column = new_data WHERE condition(s);

DELETE FROM table_name WHERE condition(s);

Those are the three update operations of Set 4, now written in SQL — and the constraints of §4.2 are exactly what decides whether each one succeeds.

6.3Writing a set difference

The losers-and-winners pattern of Set 5 is the one construct with more than one reasonable translation. Three of them:

-- 1. EXCEPT — closest to the algebra, reads like the expression
SELECT name FROM department
EXCEPT
SELECT deptName FROM member;

-- 2. NOT IN — portable to every version of everything
SELECT name FROM department
 WHERE name NOT IN (SELECT deptName FROM member);

-- 3. NOT EXISTS — correlated, and the only one safe against nulls
SELECT d.name FROM department d
 WHERE NOT EXISTS (SELECT 1 FROM member m WHERE m.deptName = d.name);

The solutions below use EXCEPT where the algebra uses −, because the aim is to show the correspondence. For your own code the ranking is roughly the reverse: NOT EXISTS first, because it is the only one of the three that behaves sanely when the subquery can produce a null; NOT IN second for portability; and EXCEPT when the query really is a difference of two whole result sets rather than a membership test.

Why NOT IN can go wrong

x NOT IN (1, 2, NULL) is never true. If x is 3, SQL must decide whether 3 equals the null, and “unknown” propagates through the AND to make the whole condition unknown — so the row is dropped, and a query that should have returned everything returns nothing. A single null in a subquery's output silently empties the result. NOT EXISTS has no such behaviour, because it asks about the existence of rows rather than the equality of values.

Where the final step of the pattern puts the winners back against the full relation, the SQL is usually shorter than the algebra: the difference goes in a subquery inside the WHERE, and the outer query does both the product and the projection in one statement. Several solutions below do that, and the algebra beside them shows what was folded together.

6.5Exercises: the College database

Each exercise gives the English and the algebra from Set 5. Write the SQL, run it, and compare your rows with the ones in the solution. Where your SQL differs from the one shown but your rows agree, you are probably right — but read the commentary, because two of these agree on this data and would diverge on other data.

(a) Find Person born after 2005. (b) Find id of teachers where their salary is greater than $100,000. 
(a)  σ[yearborn > 2005] Person

(b)  Π[tid] σ[F] Teacher
         where   F  ≡  [ salary > 100000 ]
SELECT * FROM Person WHERE yearborn > 2005;

SELECT DISTINCT tid FROM Teacher WHERE salary > 100000;
+-----+-------------+-------------------+----------+     +-----+
| id  | name        | address           | yearborn |     | tid |
+-----+-------------+-------------------+----------+     +-----+
| S12 | Maria Lopez | 12 Main St        |     2006 |     | T01 |
| S13 | John Chen   | 13 Union St       |     2007 |     | T02 |
| S14 | Wei Zhang   | 14 Parsons Blvd   |     2006 |     | T04 |
| S15 | Aisha Khan  | 15 Jewel Ave      |     2008 |     +-----+
| S17 | Omar Haddad | 17 Horace Harding |     2007 |
+-----+-------------+-------------------+----------+

(a) A bare selection is SELECT *: no projection in the algebra, so no column list in the SQL. The schema of the result is the whole of Person, and the four columns come out in the order the table declares them.

(b) Selection becomes WHERE, projection becomes the select list, and the order reverses on the page while staying the same in the machine. The DISTINCT changes nothing here, because tid is the primary key of Teacher and cannot repeat — which is the general rule: a projection that keeps a key never needs it, and one that drops part of a key always might. Write it anyway.

Find the id and name of students who enroll after 2025. 
Π[id2, name2] σ[F] ( Student1 × Person2 )
    where   F  ≡  [ sid1 = id2  ∧  yearenroll1 ≥ 2025 ]
SELECT DISTINCT p2.id, p2.name
  FROM Student s1, Person p2
 WHERE s1.sid = p2.id
   AND s1.yearenroll >= 2025;
+-----+-------------+
| id  | name        |
+-----+-------------+
| S13 | John Chen   |
| S14 | Wei Zhang   |
| S15 | Aisha Khan  |
| S17 | Omar Haddad |
+-----+-------------+

The first translated product, and the template for everything that follows. Student1 × Person2 becomes FROM Student s1, Person p2; the numbered copies become the aliases s1 and p2; the two conjuncts become two lines of the WHERE, one the link and one the real condition.

Written as a modern join it is the same query:

SELECT DISTINCT p.id, p.name
  FROM Student s JOIN Person p ON s.sid = p.id
 WHERE s.yearenroll >= 2025;

which separates the link from the filter and is better style in anything long. The comma form is used throughout this page because it matches the algebra line for line, and that correspondence is the thing being taught.

Qualify every column in a multi-table query. Unqualified, name would work here, since only one table has it — and would break the first time someone added a name to Student. Three characters remove a whole class of silent breakage.

Find the name and salary of those teacher(s) that chair more than one department. 
Π[name2, salary1] σ[F] ( Teacher1 × Person2 × Department3 × Department4 )
    where   F  ≡  [ tid1 = id2  ∧  tid1 = chair3  ∧  tid1 = chair4  ∧  code3 ≠ code4 ]
SELECT DISTINCT p2.name, t1.salary
  FROM Teacher t1, Person p2, Department d3, Department d4
 WHERE t1.tid = p2.id
   AND t1.tid = d3.chair
   AND t1.tid = d4.chair
   AND d3.code <> d4.code;
+-------------+-----------+
| name        | salary    |
+-------------+-----------+
| Alan Turing | 132000.00 |
+-------------+-----------+

Two copies of Department in the FROM, which is what the numbered copies Department3 and Department4 mean. Without the aliases the query is a syntax error; with them it is exactly the algebra, conjunct for conjunct.

This is a DISTINCT exercise. Turing chairs CS and MATH, so the pair qualifies in both orders — (CS, MATH) and (MATH, CS) — and without DISTINCT he appears twice. Had he chaired three departments it would be six times. The algebra's Π deduplicates silently; SQL does not.

The idiomatic SQL is shorter and has no algebraic counterpart at all:

SELECT p.name, t.salary
  FROM Teacher t JOIN Person p ON t.tid = p.id
                 JOIN Department d ON d.chair = t.tid
 GROUP BY p.name, t.salary
HAVING COUNT(*) >= 2;

There is no COUNT in the algebra, which is why the long way round exists — and why “at least k” for a k larger than two or three is painful in algebra and trivial in SQL.

Find the names of chairs of those departments in whose classes at least one student failed in year 2026. 
Π[name1] σ[F] ( Person1 × Department2 × GradeSheet3 × Section4 )
    where   F  ≡  [ id1 = chair2  ∧  code2 = dcode4  ∧
                    reqNum3 = reqNum4  ∧  year3 = year4  ∧
                    grade3 = 'F'  ∧  year4 = 2026 ]
SELECT DISTINCT p1.name
  FROM Person p1, Department d2, GradeSheet g3, Section s4
 WHERE p1.id      = d2.chair
   AND d2.code    = s4.dcode
   AND g3.reqNum  = s4.reqNum
   AND g3.year    = s4.year
   AND g3.grade   = 'F'
   AND s4.year    = 2026;
+--------------+
| name         |
+--------------+
| Alan Turing  |
| Grace Hopper |
+--------------+

Four tables, four links, two filters — and the longest WHERE on the page is still just the filter formula written out one conjunct per line. Laying it out that way, with the equals signs aligned, makes a missing link visible; crammed onto one line it is not.

The composite foreign key is two lines, not one. GradeSheet references Section on (reqNum, year), so both g3.reqNum = s4.reqNum and g3.year = s4.year are needed. Drop the second and a 2026 grade sheet matches a 2025 section with the same registration number — our reqNum 1004 and 1006 are both PHYS 121, in different years, so this is not hypothetical.

Turing chairs CS (S12 failed section 1001) and MATH (S13 failed 1003); Hopper chairs PHYS (S15 failed 1006). Knuth chairs ART, which has no courses and so no sections and so no failures. The DISTINCT is what stops Turing appearing twice.

Find name of all students whose name is also the name of another student. 
Π[name1] σ[F] ( Person1 × Student2 × Person3 × Student4 )
    where   F  ≡  [ id1 = sid2  ∧  id3 = sid4  ∧  id1 ≠ id3  ∧  name1 = name3 ]
SELECT DISTINCT p1.name
  FROM Person p1, Student s2, Person p3, Student s4
 WHERE p1.id   = s2.sid
   AND p3.id   = s4.sid
   AND p1.id  <> p3.id
   AND p1.name = p3.name;
+-------------+
| name        |
+-------------+
| John Chen   |
| Maria Lopez |
+-------------+

Four tables for what the English describes as one comparison, and two of them — s2 and s4 — contribute no column to the select list and no value to any comparison except through their sid. They are there purely to assert that both people are students. A table in the FROM as a membership test is an ordinary thing to need, and it is worth being comfortable with it.

The two conditions do opposite jobs. p1.id <> p3.id says they are different people; p1.name = p3.name says they have the same name. Drop either and the answer becomes every student's name, for two different reasons.

The answer is a set of names, so it cannot tell you which students they belonged to, and if three students shared a name it would still appear once. SELECT DISTINCT p1.id, p1.name is the more useful query and a fair thing to offer alongside.

Find names of students that never failed a course. 
Fail       ←  Π[sid] σ[grade = 'F'] GradeSheet
NeverFail  ←  Π[sid] Student  −  Fail
Result     ←  Π[name1] σ[id1 = sid2] ( Person1 × NeverFail2 )
SELECT DISTINCT p1.name
  FROM Person p1
 WHERE p1.id IN ( SELECT sid FROM Student            -- everyone who could qualify
                  EXCEPT
                  SELECT sid FROM GradeSheet         -- minus the losers
                   WHERE grade = 'F' );
+-------------+
| name        |
+-------------+
| John Chen   |
| Maria Lopez |
| Omar Haddad |
+-------------+

The losers-and-winners pattern, with two of its three steps folded together: the EXCEPT is Fail and NeverFail, and the enclosing WHERE ... IN is step 3, putting the winners back against Person to recover the names.

The attempt that does not work, and what it returns:

SELECT DISTINCT p1.name
  FROM Person p1, GradeSheet g2
 WHERE p1.id = g2.sid AND g2.grade <> 'F';
+-------------+
| name        |
+-------------+
| John Chen   |
| Maria Lopez |
| Wei Zhang   |
| Aisha Khan  |
+-------------+

That is the students who passed at least one course. Zhang failed PHYS 121 in 2025 and still appears, on the strength of his C in CS 331; Khan failed in 2026 and appears on the strength of her B. And Haddad, who has never taken anything, is missing. Two kinds of wrong in one query.

Subtract from Student, not from GradeSheet. That is what keeps Haddad in: he has no grade sheet at all, so he is in Student, not in Fail, and therefore in the answer. SELECT sid FROM GradeSheet EXCEPT ... would have lost him, and that error survives casual testing because the result still looks reasonable.

A wrinkle worth reporting. Projecting onto name means a name appears if any student with it qualifies. There are two John Chens — S11 never failed, S13 failed MATH 231 — and the name is in the answer. By id:

+-----+-------------+
| id  | name        |
+-----+-------------+
| S11 | John Chen   |
| S16 | Maria Lopez |
| S17 | Omar Haddad |
+-----+-------------+

Three students, not the three-or-more the name list suggests. The question asked for names, so the first answer is correct — but this is the kind of list somebody would act on, and the id version is the one to hand over.

Find name and rank of the teacher(s) with highest salary. 
Loser   ←  Π[tid1] σ[salary1 < salary2] ( Teacher1 × Teacher2 )
Winner  ←  Π[tid] Teacher  −  Loser
Result  ←  Π[name2, rank3] σ[F] ( Winner1 × Person2 × Teacher3 )
            where   F  ≡  [ tid1 = id2  ∧  tid1 = tid3 ]
SELECT DISTINCT p2.name, t3.rank
  FROM Person p2, Teacher t3
 WHERE t3.tid = p2.id
   AND t3.tid IN ( SELECT tid FROM Teacher
                   EXCEPT
                   SELECT t1.tid                     -- teachers out-earned by somebody
                     FROM Teacher t1, Teacher t2
                    WHERE t1.salary < t2.salary );
+-------------+-----------+
| name        | rank      |
+-------------+-----------+
| Alan Turing | Professor |
+-------------+-----------+

A superlative with no MAX, because the algebra being translated had none. The losers are the teachers somebody out-earns; everyone else is tied for the maximum. Turing at 132,000 is the only teacher nobody out-earns.

In SQL you would of course write:

SELECT p.name, t.rank FROM Person p, Teacher t
 WHERE p.id = t.tid AND t.salary = (SELECT MAX(salary) FROM Teacher);

which returns the same row, is obviously correct, and is the answer to give if the question says “in SQL” without qualification. The long form is here because it is what the algebra can express — and the two agree on an important point: both return every teacher tied for the top salary, not an arbitrary one. The version people reach for instead, ORDER BY salary DESC LIMIT 1, does not; it silently returns one row where the right answer may be three.

Note the strictness. With <= in the loser subquery, every teacher is out-earned by themselves, the difference is empty, and the query returns nothing.

(a) Find department name and amount of each issued paycheck. (b) Find department name and serial number of the paychecks whose amount is below 1,000. 
(a)  Π[dpt, amount] paycheck

(b)  Π[dpt, serNum] σ[F] paycheck
         where   F  ≡  [ amount < 1000 ]
SELECT DISTINCT dpt, amount FROM paycheck;

SELECT DISTINCT dpt, serNum FROM paycheck WHERE amount < 1000;
+-----------------+----------+     +-----------------+--------+
| dpt             | amount   |     | dpt             | serNum |
+-----------------+----------+     +-----------------+--------+
| Divination      |   760.00 |     | Divination      |      1 |
| Divination      |   520.00 |     | Divination      |      2 |
| Herbology       | 12400.00 |     | Herbology       |      2 |
| Herbology       |   410.00 |     | Potions         |      3 |
| Potions         |  1150.00 |     | Potions         |      4 |

(a) Nine rows from ten paychecks. The two Potions cheques of 1,150.00 are different paychecks — serial numbers 1 and 2 — but the projection throws the serial number away, so what remains is one tuple, and DISTINCT is what makes SQL agree with the algebra. Drop it and you get ten rows, which is a correct answer to a question nobody asked.

This is the smallest possible demonstration that Π loses information, and worth keeping in mind for the rest of the page.

Find full name and salary of each professor that serves in the rank of Chief Wizard. 
Π[firstName, lastName, salary] σ[F] professor
    where   F  ≡  [ rank = 'Chief Wizard' ]
SELECT DISTINCT firstName, lastName, salary
  FROM professor
 WHERE rank = 'Chief Wizard';
+-----------+------------+---------+
| firstName | lastName   | salary  |
+-----------+------------+---------+
| Albus     | Dumbledore | 1200.00 |
| Dolores   | Umbridge   |  960.00 |
+-----------+------------+---------+

Two things about the string comparison that are easy to assume wrongly.

It is case-insensitive here — MariaDB's default collation for these columns folds case, so 'chief wizard' matches too. That is a property of the collation, not of SQL, and PostgreSQL would have returned nothing. Never rely on it either way.

And rank is a reserved word in recent MySQL and MariaDB, where it is a window function. It works unquoted in this position, but a schema that uses it is one awkward query away from trouble, and `rank` is the safe spelling.

Find names and phone numbers of those departments whose chair earns less than 1,000 in salary. 
Π[name1, phone1] σ[F] ( department1 × professor2 )
    where   F  ≡  [ chairId1 = socSecNum2  ∧  salary2 < 1000 ]
SELECT DISTINCT d.name, d.phone
  FROM department d, professor p
 WHERE d.chairId = p.socSecNum
   AND p.salary < 1000;
+----------------+--------------+
| name           | phone        |
+----------------+--------------+
| Divination     | 017-555-0103 |
| Muggle Studies | 017-555-0105 |
+----------------+--------------+

One link, one filter — and the link is the thing to check first. Drop d.chairId = p.socSecNum and every department is paired with every underpaid professor, so every department qualifies: five rows instead of two, with the right columns and nothing visibly wrong.

Both departments in the answer are Umbridge's, who earns 960. A professor chairing two departments produces two rows here, correctly.

Find full names (first and last) of all professors who are members of the department named Potions. 
Π[firstName1, lastName1] σ[F] ( professor1 × member2 )
    where   F  ≡  [ socSecNum1 = profId2  ∧  deptName2 = 'Potions' ]
SELECT DISTINCT p.firstName, p.lastName
  FROM professor p, member m
 WHERE p.socSecNum = m.profId
   AND m.deptName = 'Potions';
+-----------+------------+
| firstName | lastName   |
+-----------+------------+
| Albus     | Dumbledore |
| Severus   | Snape      |
| Dean      | Thomas     |
+-----------+------------+

Membership is M : M, so it has its own table and this query goes through it. Compare Exercise 6.3, where chairing — 1 : M — needed no such table because the reference sits in a column of Department. Which of the two a query needs is decided entirely by the mapping you did in Set 4.

Unlike the College database, professor carries its own names, so nothing here needs a second table just to find out what someone is called.

Find the full name of the chairs of those departments that have issued at least one paycheck in the amount higher than 10,000. 
Π[firstName1, lastName1] σ[F] ( professor1 × department2 × paycheck3 )
    where   F  ≡  [ socSecNum1 = chairId2  ∧  name2 = dpt3  ∧  amount3 ≥ 10000 ]
SELECT DISTINCT p.firstName, p.lastName
  FROM professor p, department d, paycheck c
 WHERE p.socSecNum = d.chairId
   AND d.name = c.dpt
   AND c.amount >= 10000;
+-----------+------------+
| firstName | lastName   |
+-----------+------------+
| Minerva   | McGonagall |
| Pomona    | Sprout     |
+-----------+------------+

Three tables, two links, one filter, and the links chain rather than branch: professor to department, department to paycheck.

“At least one” needs no special construct. Existential quantification is what a product plus a condition is: a row appears in the result exactly when some matching row exists. A department that had issued three large cheques would list its chair three times before DISTINCT collapsed them. It is “no” and “every” that cost you a subquery.

Find id, first name, and last name of those professors who have received paychecks from (at least) two different departments. 
Π[socSecNum1, firstName1, lastName1] σ[F] ( professor1 × paycheck2 × paycheck3 )
    where   F  ≡  [ socSecNum1 = prof2  ∧  socSecNum1 = prof3  ∧  dpt2 ≠ dpt3 ]
SELECT DISTINCT p.socSecNum, p.firstName, p.lastName
  FROM professor p, paycheck c2, paycheck c3
 WHERE p.socSecNum = c2.prof
   AND p.socSecNum = c3.prof
   AND c2.dpt <> c3.dpt;
+-----------+-----------+------------+
| socSecNum | firstName | lastName   |
+-----------+-----------+------------+
| 100000001 | Albus     | Dumbledore |
+-----------+-----------+------------+

This is the DISTINCT exercise. Dumbledore was paid by Potions and by Transfiguration, so the pair qualifies in both orders and without DISTINCT he appears twice — the query returns two rows for one professor. Had he been paid by three departments it would be six. The algebra's Π deduplicates silently; SQL does not, and this is the query where you would have noticed.

The idiomatic SQL is different and shorter:

SELECT p.socSecNum, p.firstName, p.lastName
  FROM professor p JOIN paycheck c ON c.prof = p.socSecNum
 GROUP BY p.socSecNum, p.firstName, p.lastName
HAVING COUNT(DISTINCT c.dpt) >= 2;

which returns the same row and has no algebraic counterpart at all.

Find id, first name, and last name of those professors who have received at least two (different) paychecks from the same department on the same amount. 
Π[socSecNum1, firstName1, lastName1] σ[F] ( professor1 × paycheck2 × paycheck3 )
    where   F  ≡  [ socSecNum1 = prof2  ∧  socSecNum1 = prof3  ∧
                    dpt2 = dpt3  ∧  serNum2 ≠ serNum3  ∧  amount2 = amount3 ]
SELECT DISTINCT p.socSecNum, p.firstName, p.lastName
  FROM professor p, paycheck c2, paycheck c3
 WHERE p.socSecNum = c2.prof
   AND p.socSecNum = c3.prof
   AND c2.dpt    =  c3.dpt
   AND c2.serNum <> c3.serNum
   AND c2.amount =  c3.amount;
+-----------+-----------+----------+
| socSecNum | firstName | lastName |
+-----------+-----------+----------+
| 100000003 | Severus   | Snape    |
+-----------+-----------+----------+

The same product as Exercise 6.13 with a different tail. The inequality has moved from the department to the serial number, because the department is now required to be the same and (dpt, serNum) is the key, so serNum is the only thing left that can make the two rows different rows.

Snape's Potions cheques 1 and 2 are both 1,150.00. The condition finds the pair twice, once in each order, and DISTINCT collapses it.

The common error is to omit c2.serNum <> c3.serNum, which lets each paycheck match itself. Run that version and it returns eight professors — everyone who has ever been paid. It is worth running once, because an answer that large is obviously wrong and the same mistake in a bigger query is not.

Writing c2 <> c3 instead is not valid SQL: there is no row-identity comparison, which is precisely why the algebra made you name a key attribute too.

Find first name, last name, and salary of those professors that chair more than one department. 
Π[firstName1, lastName1, salary1] σ[F] ( professor1 × department2 × department3 )
    where   F  ≡  [ socSecNum1 = chairId2  ∧  socSecNum1 = chairId3  ∧  name2 ≠ name3 ]
SELECT DISTINCT p.firstName, p.lastName, p.salary
  FROM professor p, department d2, department d3
 WHERE p.socSecNum = d2.chairId
   AND p.socSecNum = d3.chairId
   AND d2.name <> d3.name;
+-----------+----------+--------+
| firstName | lastName | salary |
+-----------+----------+--------+
| Dolores   | Umbridge | 960.00 |
+-----------+----------+--------+

Exercise 6.3 on the other database, and shorter by one table, because professor holds its own name and salary where the College schema put them on Person. Same shape otherwise: double the relation that holds the repeated fact, and put the inequality on its key.

Umbridge chairs Divination and Muggle Studies. Note that she is not a member of either — she is a member of Herbology — which the schema permits and Exercise 6.18 goes looking for.

Find full names (first and last) of all professors who are members of more than one department. 
Π[firstName3, lastName3] σ[F] ( member1 × member2 × professor3 )
    where   F  ≡  [ profId1 = profId2  ∧  deptName1 ≠ deptName2  ∧  socSecNum3 = profId1 ]
SELECT DISTINCT p.firstName, p.lastName
  FROM member m1, member m2, professor p
 WHERE m1.profId    =  m2.profId
   AND m1.deptName <> m2.deptName
   AND p.socSecNum  =  m1.profId;
+-----------+------------+
| firstName | lastName   |
+-----------+------------+
| Albus     | Dumbledore |
| Cedric    | Diggory    |
+-----------+------------+

The membership counterpart of 6.15, and the relation that gets doubled is member rather than department — because a professor's departments are not recorded anywhere else. Choosing which table to double is the one real decision in this family, and the test is always the same: double whichever relation holds the repeated fact.

Dumbledore is in Potions and Transfiguration; Diggory in Transfiguration and Divination. Umbridge, who chairs two departments, is a member of only one and correctly does not appear — a useful reminder that chairing and membership are independent here.

Find full name and rank of each professor that earns a higher salary than their department chair. 
Π[firstName1, lastName1, rank1] σ[F] ( professor1 × professor2 × member3 × department4 )
    where   F  ≡  [ socSecNum1 = profId3  ∧  deptName3 = name4  ∧
                    chairId4 = socSecNum2  ∧  salary1 > salary2 ]
SELECT DISTINCT p1.firstName, p1.lastName, p1.rank
  FROM professor p1, professor p2, member m3, department d4
 WHERE p1.socSecNum = m3.profId
   AND m3.deptName  = d4.name
   AND d4.chairId   = p2.socSecNum
   AND p1.salary    > p2.salary;
+-----------+------------+--------------+
| firstName | lastName   | rank         |
+-----------+------------+--------------+
| Albus     | Dumbledore | Chief Wizard |
| Cedric    | Diggory    | Wizard       |
+-----------+------------+--------------+

Two copies of professor meaning two different people, and a comparison between them. Comparing a column of one alias with the same column of another is how SQL compares two rows of a table; there is no other way.

Check it against the data. Dumbledore earns 1,200; he is in Potions, chaired by Snape at 1,140, so he qualifies there — and in Transfiguration, chaired by McGonagall at 1,640, where he does not. One qualifying membership is enough, and DISTINCT would have mattered had he out-earned both chairs. Diggory at 1,120 out-earns Umbridge at 960 in Divination.

The word “their” is carried entirely by the three-equality chain. Drop m3.deptName = d4.name and the query becomes “professors who out-earn some chair somewhere”, which returns six rows here and is a different claim.

Find the full name and rank of those department chairs that have never received a paycheck from any department which they chair (though they may have been paid by other departments). 
Loser   ←  Π[prof1] σ[F] ( paycheck1 × department2 )
            where   F  ≡  [ prof1 = chairId2  ∧  dpt1 = name2 ]
Winner  ←  Π[chairId] department  −  Loser
Result  ←  Π[firstName1, lastName1, rank1] σ[G] ( professor1 × Winner2 )
            where   G  ≡  [ socSecNum1 = socSecNum2 ]
SELECT DISTINCT p.firstName, p.lastName, p.rank
  FROM professor p
 WHERE p.socSecNum IN (
         SELECT chairId FROM department        -- all chairs
         EXCEPT
         SELECT c.prof                         -- minus the losers
           FROM paycheck c, department d
          WHERE c.prof = d.chairId
            AND c.dpt  = d.name );
+-----------+----------+--------------+
| firstName | lastName | rank         |
+-----------+----------+--------------+
| Dolores   | Umbridge | Chief Wizard |
+-----------+----------+--------------+

The two conditions inside the loser subquery are both essential. c.prof = d.chairId says the cheque went to a chair; c.dpt = d.name says it came from the department that person chairs. Drop the second and the losers become “chairs who have ever been paid by anyone”, and the query answers a different question. The parenthesis in the English — “though they may have been paid by other departments” — is there precisely to warn you.

By hand: Snape chairs Potions and was paid by Potions; McGonagall chairs Transfiguration and was paid by Transfiguration; Sprout chairs Herbology and was paid by Herbology. All three are losers. Umbridge chairs Divination and Muggle Studies and has never been paid by anybody, so she is the one winner.

(a) Find names of all departments that have no members. (b) Find department name and phone number of those departments that have never issued a paycheck. 
(a)  Π[name] department  −  Π[deptName] member

(b)  Loser   ←  Π[dpt] paycheck
     Winner  ←  Π[name] department  −  Loser
     Result  ←  Π[name1, phone1] σ[F] ( department1 × Winner2 )
                 where   F  ≡  [ name1 = name2 ]
SELECT name FROM department
EXCEPT
SELECT deptName FROM member;

SELECT DISTINCT d.name, d.phone
  FROM department d
 WHERE d.name IN ( SELECT name FROM department
                   EXCEPT
                   SELECT dpt  FROM paycheck );
+----------------+     +----------------+--------------+
| name           |     | name           | phone        |
+----------------+     +----------------+--------------+
| Muggle Studies |     | Muggle Studies | 017-555-0105 |
+----------------+     +----------------+--------------+

(a) is the pattern at its smallest — one line of algebra, one statement of SQL, no step 3, because the question asks only for the names and the difference already holds them. No DISTINCT is needed on either side: EXCEPT removes duplicates by definition, exactly as UNION does.

(b) adds step 3: the difference produces bare names, the question asked for phone numbers as well, so the names are fed back into a query over department. Written directly, and better:

SELECT d.name, d.phone FROM department d
 WHERE NOT EXISTS (SELECT 1 FROM paycheck c WHERE c.dpt = d.name);

One pass, no intermediate set, and the correlation makes the intent obvious. This is the form to reach for in your own code; the EXCEPT version is here because it maps onto the algebra line by line. It is also the single most common shape in practical SQL — customers who never ordered, students with no grade, files with no owner.

The two answers coincide here for a structural reason: Muggle Studies has no members, and by the foreign key on paycheck a department can only pay its own members, so it could not have issued a cheque even if it tried. On a department that had members but had not yet paid them, (a) and (b) would differ.

Find full name and rank of each professor that is not the chair of any department, but earns a higher salary than Professor Albus Dumbledore. 
notChair  ←  Π[socSecNum] professor  −  Π[chairId] department
Result    ←  Π[firstName2, lastName2, rank2] σ[F] ( notChair1 × professor2 × professor3 )
              where   F  ≡  [ socSecNum1 = socSecNum2  ∧
                              firstName3 = 'Albus'  ∧  lastName3 = 'Dumbledore'  ∧
                              salary2 > salary3 ]
SELECT DISTINCT p2.firstName, p2.lastName, p2.rank
  FROM professor p2, professor p3
 WHERE p2.socSecNum IN ( SELECT socSecNum FROM professor
                         EXCEPT
                         SELECT chairId   FROM department )
   AND p3.firstName = 'Albus'
   AND p3.lastName  = 'Dumbledore'
   AND p2.salary    > p3.salary;
+-----------+----------+--------+
| firstName | lastName | rank   |
+-----------+----------+--------+
| Filius    | Flitwick | Wizard |
+-----------+----------+--------+

A negative and a comparison in one query, each with its own mechanism: the difference handles “not a chair”, the second copy of professor handles “than Dumbledore”.

The non-chairs are Dumbledore, Flitwick, Trelawney, Centaur, Thomas and Diggory. Of those, only Flitwick at 1,275 earns more than Dumbledore's 1,200 — and Dumbledore cannot qualify against himself, since > is strict.

The idiomatic version replaces the second copy with a scalar subquery:

SELECT p.firstName, p.lastName, p.rank FROM professor p
 WHERE NOT EXISTS (SELECT 1 FROM department d WHERE d.chairId = p.socSecNum)
   AND p.salary > (SELECT salary FROM professor
                    WHERE firstName = 'Albus' AND lastName = 'Dumbledore');

A scalar subquery must return exactly one value, and the server raises an error if it returns more — a genuine difference from the algebra, where a second Albus Dumbledore would quietly have produced two comparisons and the union of their results. The SQL is stricter, and here that is a feature.

Find first name, last name, and rank of those professors that do not chair any department. 
Loser   ←  Π[chairId] department
Winner  ←  Π[socSecNum] professor  −  Loser
Result  ←  Π[firstName1, lastName1, rank1] σ[F] ( professor1 × Winner2 )
            where   F  ≡  [ socSecNum1 = socSecNum2 ]
SELECT DISTINCT p.firstName, p.lastName, p.rank
  FROM professor p
 WHERE p.socSecNum IN ( SELECT socSecNum FROM professor
                        EXCEPT
                        SELECT chairId   FROM department );
+-----------+------------+--------------+
| firstName | lastName   | rank         |
+-----------+------------+--------------+
| Albus     | Dumbledore | Chief Wizard |
| Filius    | Flitwick   | Wizard       |
| Sybill    | Trelawney  | Wizard       |
| Firenze   | Centaur    | Apprentice   |
| Dean      | Thomas     | Apprentice   |
| Cedric    | Diggory    | Wizard       |
+-----------+------------+--------------+

Six of the ten; the other four are Snape, McGonagall, Sprout and Umbridge, who between them chair the five departments.

And the one you would actually write:

SELECT p.firstName, p.lastName, p.rank FROM professor p
 WHERE NOT EXISTS (SELECT 1 FROM department d WHERE d.chairId = p.socSecNum);

This is also the version to prefer on a real schema, and here is why. chairId happens to be NOT NULL in this database. Had it been nullable — a department between chairs — then a single null in SELECT chairId FROM department would make the NOT IN form of this query return no rows at all, silently, because x NOT IN (..., NULL) is never true. The EXCEPT form survives that, since set difference treats nulls as values rather than comparing them; NOT EXISTS survives it too, and for the clearest reason: it asks whether a matching row exists, which is a question with an answer even when the values are unknown.

That is the last and most practical thing the algebra does not prepare you for. The algebra on these pages has no nulls in it, so every translation here is exact — and the first schema you meet with a nullable foreign key will be the one where the exact translation is wrong. In the College database, the nullable column to watch is Department.chair.

Going further

Nothing on this page uses GROUP BY except in passing, and that is deliberate: every query here is the translation of an algebra expression, and the algebra cannot aggregate. The moment the question becomes “how much did each department pay out”, or “how many courses did this student fail”, you leave the algebra behind entirely and the answer has no counterpart to check against. That is the next topic, and the reason it is taught after this one is that GROUP BY is much easier to understand as a thing SQL adds than as a thing SQL has.

In the other direction, the queries the algebra cannot reach at all are the recursive ones — reporting chains, ancestry, reachability. SQL grew a WITH RECURSIVE for those, and Datalog was designed around them from the start.
