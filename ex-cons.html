Will this operation succeed?

The five schema-based constraints in the order the lectures give them — domain, key, nulls, entity integrity, referential integrity — and then the question the exam actually asks: given a schema and a sequence of operations, does each one succeed, and if not, which constraint does it violate? Fourteen exercises.

Set 3 produced schemas. This set asks what those schemas will and will not hold. Nearly every wrong answer in this topic comes from one of three places: confusing a key violation with a referential one, forgetting that a foreign key may be null, and forgetting that a key attribute may not.

4.1Three categories of constraint

Constraints on a database divide into three kinds, and knowing which kind you are looking at tells you who is responsible for enforcing it.

categoryalso calledwho enforces it
inherent model-basedimplicit constraintsnobody has to — they are built into the data model itself
schema-basedexplicit constraintsthe DBMS, because you wrote them in the DDL
application-basedsemantic constraints, business rulesthe application program, or a human, because the schema cannot say them

An inherent constraint is one the relational model gives you free: a relation is a set, so it cannot contain the same tuple twice; a tuple's attributes are unordered; a relation cannot have two attributes of the same name. You never declare these and you cannot violate them — there is no way to express the violation.

A schema-based constraint is one you declare, and the server then refuses any operation that would break it. These are the five of §4.2, and they are the whole of what this set drills.

An application-based constraint is a true statement about the enterprise that no DDL can carry — “a student may not enroll in more than five courses a term”, “every item must appear on some purchase”. It is not less real for being undeclarable; it is just somebody else's job. §4.5 is about recognising these, because an exam will ask you to, and because in practice they are where the data actually goes wrong.

4.2The five schema-based constraints

In the order the lectures introduce them. The abbreviations are the ones used in class, and they are what an answer should name.

#constraintshortthe test applied to a rowtypical server error
1domain constraintD.C.Is every value atomic, and of the attribute's declared type and range?Incorrect integer value, Data too long
2key constraintK.C.Does some existing tuple already carry this key value?Duplicate entry
3constraint on NULLsN.C.Is an attribute declared NOT NULL being given a null?Column 'x' cannot be null
4entity integrityE.I.C.Is any attribute of the primary key null?Column 'x' cannot be null
5referential integrityR.I.C.For each foreign key: is it null, or does its value occur as a primary key in the referenced relation?a foreign key constraint fails

Domain constraint. Two separate requirements live here. Every value must be atomic — which is why composite and multivalued attributes cannot survive into a table and had to be flattened or given their own relation back in Set 3. And every value must match the type declared for its attribute, including any width or range: a four-digit eid does not accept 'BBBB', and an INT column does not accept 'CD'.

Key constraint. No two tuples may agree on the key. Stated the other way round, which is more useful when you are checking a row: the operation fails if the key value you are inserting is already present.

Constraint on NULLs. Simply whether an attribute was declared NOT NULL. It is listed separately from entity integrity because it is a choice the designer makes about an ordinary attribute, whereas entity integrity is forced.

Entity integrity. No primary-key value may be null — and the word to notice is any. In a composite key, one null component is enough. This is not an arbitrary rule: the primary key is what identifies the tuple, and a tuple with no identity is not a tuple.

Referential integrity. The value of a foreign key either occurs as a primary-key value in the referenced relation, or is null. Two rules come with it: the attributes of the foreign key in R must have the same domains as the primary key of S, and a value of the foreign key either occurs there or is null. R is then the referencing relation and S the referenced one.

The one people get backwards

A duplicate primary key is not a referential-integrity violation, and a dangling foreign key is not a key violation. They are different constraints with different error numbers and different fixes. If you find yourself writing “integrity would be violated” without naming which, you have not answered the question.

Null in a foreign key: allowed. Null in a key: never.

Referential integrity explicitly permits a null foreign key — a tuple that refers to nothing yet. So a total participation constraint from Set 1 does not survive the mapping by itself; it needs an N.C., a NOT NULL written on top of the foreign key by hand, because you knew to. But if that foreign key is also part of the primary key, entity integrity wins and no null is possible. Exercises 4.6 and 4.7 are exactly this pair.

4.3Key, superkey, candidate, primary

A key is a set of attributes that uniquely identifies each tuple in a relation — no two tuples can carry the same value on the key attributes. A key satisfies two properties:

  1. Two tuples cannot have identical values for all the attributes in the key. (This also applies to a superkey.)
  2. It is a minimal superkey — the one with fewest attributes.

A superkey is a subset of attributes that identifies each tuple, i.e. no two tuples share the same combination of values on it. Property 1 holds of every superkey; property 2 is what separates a key from a superkey. Add any attribute to a superkey and you get another superkey, so most relations have a great many — including, always, the set of all attributes.

A candidate key is a minimal superkey. A primary key is a designated candidate key: the one whose values are used to identify tuples in the relation, and the one that gets underlined in the schema.

That last distinction does real work. If a relation has two candidate keys, only the designated one is protected by entity integrity. A null in the other candidate key is perfectly legal; uniqueness on it has to be asked for separately, with UNIQUE.

4.4The three update operations

Which constraints an operation can break depends on the operation, and the asymmetry is worth memorising because it halves the work on an exam question.

operationcan violatewhy
INSERTD.C., K.C., N.C., E.I.C., R.I.C.a new tuple is a new value for every attribute, and a new reference out of the relation
DELETER.I.C. onlyremoving a tuple cannot create a bad value or a duplicate key; it can only strand a foreign key that was pointing at it
UPDATE / MODIFYdepends on the attribute changedchanging an ordinary attribute risks D.C. and N.C.; changing a key risks K.C. and E.I.C., and R.I.C. from anything that referenced it; changing a foreign key risks R.I.C.

So for a DELETE there is only one question to ask: does any foreign key anywhere point at the tuple being removed? If no, it succeeds.

Work down the list keeping track of the actual contents, not the intended ones.

4.5Application-based constraints

Some true statements about the enterprise fit in no DDL. These are the application-based constraints, and the exam question is usually “which constraint from the diagram does your schema fail to enforce?”

the diagram or narrative saysthe DDL can saythe gap

total participation on the 1 sidenothing“every item appears on some purchase” is a claim about the absence of a gap in another table; no column can carry it
a disjoint specializationa type column, if you mapped it that wayoptions (a) and (b) of Set 3 enforce nothing
a 1 : 1 relationshipUNIQUE on the foreign keynone, if you remember the UNIQUE
a range or a list of permitted valuesCHECK, where the server honours itMySQL ignored CHECK until 8.0.16; MariaDB enforces it from 10.2
“at most five per term”, “no two on the same day”nothinga constraint over a set of tuples, not over one

Rows two and six are the ones worth memorising, and they fail for the same reason. Every mechanism in the DDL — NOT NULL, UNIQUE, CHECK, a foreign key — constrains the row being written, using values present in that row. A constraint that depends on which other rows exist is outside what a column can express, and becomes a trigger, an assertion, or application code.

Student: idnameageaddress

This is the Student table of Lecture 6, with the questions written out.

(a) Four superkeys. {id}, {id, name}, {name, age, address}, {id, name, age, address}. Any set containing {id} is a superkey, and the set of all attributes always is.

(b) Which are candidate keys. Only {id} of the four. A candidate key is a minimal superkey, and {id, name} and {id, name, age, address} both properly contain {id}.

{name, age, address} is worth working through rather than dismissing. On this content its five values are all distinct, so it is a superkey — but it is not minimal, because the pair {name, age} inside it is already unique: (A,18), (B,19), (C,18), (D,19), (B,18), no repeats. So on this content the candidate key hiding in there is {name, age}, and {name, age, address} is not one. Whether {name, age} is really a key is a different question, and it is the point of part (c).

(c) The attribute that cannot be a key is name, and it can be ruled out from the content: rows 2 and 5 both carry B, so name fails property 1 outright.

Why the content is not enough in the other direction. Content can disprove a key and can never prove one. {name, age} happens to be unique in these five rows; nothing stops a sixth student called B, aged 18, from enrolling tomorrow. A key is a statement about every state the relation can ever be in, which is a fact about the enterprise, not about today's rows — which is why the designer declares it and the server then enforces it, rather than the server inferring it.

Row 5 of this table is exactly the kind of row that arrives later and invalidates a key someone read off the data.

The database is empty. Will this sequence succeed? If not, which constraint does it violate? 
INSERT <'12345', 'funny', 'Queens',  '1999'> into agency
INSERT <'12345', 'silly', 'College', '1991'> into agency

No — K.C. Primary-key uniqueness would be violated: two distinct tuples of agency would carry '12345' under the primary key agenId.

Note what is not wrong with them. The two tuples differ in three of their four fields; none of their fields is null; neither refers to any other relation. Only the first field matters, because only the first field is the key.

INSERT INTO agency VALUES ('12345','funny','Queens',1999);     -- accepted
INSERT INTO agency VALUES ('12345','silly','College',1991);
ERROR 1062 (23000): Duplicate entry '12345' for key 'PRIMARY'

The first operation succeeds. That is worth saying out loud: the pair does not fail as a unit, it fails on the second operation, and the database is left holding the first one.

Is it possible for the relation fund to contain these two tuples simultaneously? 
'12345', 'funny', 1999
'12345', 'silly', 1991

Yes. The primary key of fund is the pair (aId, pId), and these two tuples carry ('12345','funny') and ('12345','silly') — distinct values. One agency funding two projects is exactly what the relation is for.

+-------+-------+---------+
| aId   | pId   | amount  |
+-------+-------+---------+
| 12345 | funny | 1999.00 |
| 12345 | silly | 1991.00 |
+-------+-------+---------+

Compare this with Exercise 4.2 and you have the whole of the key constraint: the same repeated value '12345' is fatal in one relation and harmless in the other, and nothing about the value decides which. The key does.

The content does of course need an agency with agenId = '12345' and projects 'funny' and 'silly' to exist first, or R.I.C. would stop it. The question asks whether the content is possible, so we supply those and the answer stands.

Is it possible for the relation manage to contain these two tuples simultaneously? 
'12345', 'funny'
'12345', 'silly'

No — K.C. Two distinct tuples of manage would carry '12345' under the primary key pId.

This is Exercise 4.3 with one attribute moved out of the key, and the answer flips. manage is keyed on pId alone because a project has a single manager, so the pair above is precisely what the key was chosen to forbid — one project, two managers.

INSERT INTO manage VALUES ('12345','funny');     -- accepted
INSERT INTO manage VALUES ('12345','silly');
ERROR 1062 (23000): Duplicate entry '12345' for key 'PRIMARY'

If the enterprise later allows co-managers this is not a data problem but a schema problem: the key has to grow to (pId, eId), and manage becomes another assign.

The database is empty. Will this sequence succeed? If not, which constraint does it violate? 
INSERT <'12345', 'funny'> into assign
INSERT <'12346', 'silly'> into assign

No — R.I.C., twice over in each tuple.

assign would hold tuples with the non-null values '12345' and '12346' under pId, which is a foreign key referencing project; but the database is empty, so project has no tuple whose primary key equals '12345' or '12346'. Likewise the two tuples would hold the non-null values 'funny' and 'silly' under eId, a foreign key referencing employee, and employee has no tuple with either of those primary keys.

fails (`assign`, CONSTRAINT `assign_ibfk_1` FOREIGN KEY (`pId`)

The server names only the first constraint it checks. Your answer should name both, because both are violated and the marking is on the reasoning, not the error message.

Note also that the two tuples are fine as a pair: distinct primary keys, no nulls. Nothing is wrong inside assign. Everything is wrong about what it points at.

The database is empty. Will this sequence succeed? If not, which constraint does it violate? 
INSERT <'12344', NULL, NULL> into project
INSERT <'12344', NULL>       into manage

Yes — both operations succeed, and it is worth taking each null separately.

In project, the two nulls land in name and yearDone. Neither belongs to the primary key and neither is declared NOT NULL, so neither N.C. nor E.I.C. has anything to say. The key field projId carries '12344', which is not null and not a duplicate — the relation is empty.

In manage, pId is '12344': not null, unique, and it now has a matching project tuple, so K.C., E.I.C. and R.I.C. all pass. The null lands in eId, which is a foreign key referencing employee but is not part of the primary key of manage. Referential integrity explicitly permits a null foreign key, and nothing declares this one NOT NULL.

+-------+------+
| pId   | eId  |
+-------+------+
| 12344 | NULL |
+-------+------+

Read semantically, the tuple says: project 12344 exists and has no manager recorded. Whether the enterprise should allow that is a design question — if it should not, the schema needs eId CHAR(12) NOT NULL, and no amount of integrity theory will supply it for you.

INSERT <'12333', NULL, NULL> into project
INSERT <'12333', NULL>       into assign

No — E.I.C. assign would hold a tuple with NULL under eId, which is a component of the primary key.

INSERT INTO project VALUES ('12333',NULL,NULL);   -- accepted
INSERT INTO assign  VALUES ('12333',NULL);
ERROR 1048 (23000): Column 'eId' cannot be null

Put this next to Exercise 4.6 and you have the whole of the null rule. The same null, in a field of the same name, referencing the same relation: legal in manage, illegal in assign. The only difference is that assign is keyed on (pId, eId) and manage on pId alone, so in assign the null falls inside the primary key and entity integrity overrides the permission referential integrity would otherwise give it.

Semantically the rejected tuple is nonsense anyway: it would mean “project 12333 is assigned to no employee”, which is not a fact about an assignment but the absence of one.

So the tuple holds the non-null value 'silly' under pId, a foreign key referencing project, but project has no tuple with primary key 'silly'; its only tuple is '12333'. Likewise the tuple holds the non-null value '12333' under aId, a foreign key referencing agency, but agency has no tuple with primary key '12333'; its only tuple is 'silly'.

The tuple has its two identifiers the wrong way round, and the only thing that catches it is reading the schema's field order rather than guessing from the look of the values. '12333' looks like an id and 'silly' looks like a name, and in this schema that intuition is exactly backwards.

The three that are not obvious.

Teacher and Student are subclasses of Person, mapped as one relation each keyed on the superclass key. So tid is simultaneously the primary key of Teacher and a foreign key into Person — the same attribute doing both jobs, which is the signature of this mapping and is why neither subclass repeats name or address.

Write a set of relational schemas for the database of PLANET (Planetary Computer Network), specified by the narrative below. Implement all applicable constraints. Your design must have an adequate level of normalization. For each relational schema, specify the primary key (if any) and the foreign keys (if any).

The firm PLANET owns and operates a large number of computers connected into a world-wide network. PLANET owns a large database where it stores data about all of its computers. Each computer is identified by its NIC (network interface card) identifier, and further characterized by several properties. All of these properties are determined by the model (code) assigned by the manufacturer to the computer. Precisely, the model determines the number of CPUs, clock frequency, core memory size, local disk capacity, and local disk speed. The year when that model appeared on the market is also recorded, and so is the manufacturer.

PLANET identifies computer manufacturers by internal names, and stores about each such manufacturer only one data item: a pointer (lookup key) into a large external database facility where all data about manufacturers (and companies and businesses in general) can be looked up via this lookup key.

PLANET owns very many IP addresses. An IP address is a unique name of a node in the global public INTERNET where a computer can be connected. A computer is connected to the INTERNET by receiving one IP address. An IP address is identified by a string. For each of its IP addresses, PLANET needs to know the name of the GSP (global service provider) which delivers connection to this address, and the approximate geographic location of the IP address. Very much like computer manufacturers, GSPs are also identified by internal name and characterized by a pointer to the same external comprehensive database. Additionally, PLANET rates GSPs based on the quality of service they provide. The rating process is confidential, and only the final internal rating is stored.

The sentence that decides the whole design is “All of these properties are determined by the model”. It is a functional dependency stated in English, and it says the five hardware properties must not live in computer. Put them there and every computer of the same model repeats them, and one careless update makes the database contradict itself. They belong in model, and computer keeps only a reference.

Why model's key is a pair. The model code is assigned by the manufacturer, so two manufacturers may perfectly well use the same code. The key is therefore (code, manufacturerName), and the foreign key in computer is the corresponding pair of fields — a composite foreign key, which is why computer carries manufacturerName even though it looks redundant. It is not redundant; it is half of a key. Compare Section in Exercise 4.9, which carries a department code for exactly the same reason.

connection as its own relation. The narrative says a computer is connected by receiving one IP address, and an IP address names one node, so the relationship is 1 : 1 and could have been a foreign key on either side. Keeping it separate avoids nulls for the computers that are not currently connected and for the addresses PLANET owns but has not used — and the narrative says PLANET owns “very many” addresses, which strongly implies there are such. Mapped this way, computerId alone is a candidate key and so is IpId; whichever you choose as primary, the other wants a UNIQUE, or the 1 : 1 is not enforced.

What the narrative does not let you store. The rating process is confidential and only the final rating is kept, so there is no relation for the process — a single rating column on GSP. Resist the urge to design the thing the narrative explicitly refuses to record.

    name varchar (36),
    address varchar (54),
    primary key (catalognum));

create table phonebook (
    person char (12),
    phonenum varchar (16),
    primary key (person, phonenum),
    foreign key (person) references customer);

create table purchase (
    invoicenum char (14),
    orderdate date,
    shipdate date,
    cardnumber char (16),
    buyer char (12) not null,          -- the double line, in SQL
    primary key (invoicenum),
    foreign key (buyer) references customer);

create table orderfor (
    itemnum char (10),
    invoicenum char (14),
    primary key (itemnum, invoicenum),
    foreign key (itemnum) references item,
    foreign key (invoicenum) references purchase);

Five relations for three entity sets and two relationship sets. phonebook exists because phone # is multivalued; orderfor exists because of is M : M. The by relationship gets no relation at all — it is 1 : M, so it collapses into the buyer column of purchase.

The one line that is easy to leave out is not null on buyer — an N.C., not a consequence of the foreign key. The diagram puts M on the purchase side of by and 1 on the customer side, and a purchase with no buyer is not a thing the enterprise has; the foreign key alone would permit it, because referential integrity allows a null foreign key. Tested:

INSERT INTO purchase VALUES ('INV-0002','2026-09-02',NULL,NULL,NULL);
ERROR 1048 (23000): Column 'buyer' cannot be null

INSERT INTO purchase VALUES ('INV-0003','2026-09-02',NULL,NULL,'C-9999');
ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint
fails (`purchase`, CONSTRAINT `purchase_ibfk_1` FOREIGN KEY (`buyer`)
REFERENCES `customer` (`catalognum`))

Two different refusals, from two different constraints, on the same column: the first is the N.C., because the value is missing; the second is the R.I.C., because it points at nothing. Being able to say which is which is most of this exercise.

On the other columns. orderdate, shipdate and cardnumber are left nullable on purpose: an order placed today has no ship date yet, and the diagram does not say every purchase carries a card. Declaring them not null would be adding a constraint the diagram never made — as much an error as omitting one it did.

Column types are a judgement call the diagram cannot make for you; they are your domain constraints, and any reasonable width passes. What is marked is the keys, the foreign keys and the not null.

Name a constraint expressed by Figure 63 that your answer to Exercise 4.13 does not enforce. Which of the three categories of §4.1 does it fall into, and why can no column carry it?
Not from the problem book

Exercises 4.2–4.13 are the problem book's and the lectures'. This one is ours: the diagram and the DDL are Problem 135's, and only the question asked about them is new.

Figure 63 marks the of relationship M on the item side as well as the purchase side. Read together with the cardinality on the other end, that is a claim that every item appears on some purchase — and the DDL of Exercise 4.13 lets an item sit in the catalogue untouched forever:

INSERT INTO item VALUES ('I-003', 2.25, 10);      -- accepted

SELECT itemnum FROM item
 WHERE itemnum NOT IN (SELECT itemnum FROM orderfor);
+---------+
| itemnum |
+---------+
| I-002   |
| I-003   |
+---------+

The category is application-based — a semantic constraint that is true of the enterprise and undeclarable in the schema. Some program, or some person, has to enforce it.

Why no column can carry it. The reason is structural rather than a limitation of SQL. A constraint of the form “this tuple must be referenced by at least one tuple elsewhere” is a statement about the absence of a gap in another relation. Every mechanism in the DDL constrains the tuple being written, using values present in that tuple. Nothing in a tuple of item can be inspected to decide whether some tuple of orderfor mentions it — and even if it could, the constraint would have to be re-checked every time an unrelated orderfor tuple was deleted. That is the work of a trigger or an assertion, not of a column.

Hence the asymmetry worth memorising, and it is the same one as §4.5: total participation on the M side of a 1 : M relationship becomes an N.C. and is enforced; total participation on the 1 side becomes a comment.

A second answer would also have earned the marks: nothing in the DDL says the quantity of an item cannot be negative, or that shipdate cannot precede orderdate. Those are domain constraints that a check clause can express — so they are schema-based constraints you omitted, not application-based ones. The difference between “undeclarable” and “declarable but not declared” is exactly what §4.1 is asking you to notice.

Going further

Everything on this page is a constraint the server can check one tuple at a time. Nothing here stops you from storing the same fact twice — a schema can satisfy all five schema-based constraints and still let an update leave the database contradicting itself. That is what functional dependencies and normalization are about, and it is the one remaining question the relational model asks of a design.

In the other direction: from here the question stops being “what may the database hold?” and becomes “what can I get out of it?”. Set 5 answers that with the relational algebra, and the keys and foreign keys you have been writing down finally start earning their keep — every selection condition in the next two sets is one of them.
