Disks, file sizes and sorting

Why a database lives on a disk, what a disk costs you every time you touch it, and the three numbers that decide how long any operation on a stored file will take: the length of a record, the number of records, and the size of a block. Twelve exercises from the problem book, all of them arithmetic in powers of two, and most of them answerable in four lines once the three numbers are on the page.

Every set until now has been about what a database means. This one is about what it costs, and the answers are startling: the same file, read the obvious way, takes seven weeks; sorted by the obvious algorithm, takes five centuries. Both numbers come out of the same short calculation.

Notation, as Lectures 18 and 19 write it
SymbolIs
ℓthe length of one record, in bytes — the sum of its field lengths
Tthe number of records in the file
bthe block size, in bytes
Bthe number of blocks the file occupies
tbthe block access time, in seconds

Everything on this page is built from the first five, and the sorting of §11.5 adds the sixth. Write every quantity as a power of two before you do anything with it — that is not a stylistic preference, it is the method: multiplication becomes addition of exponents, division becomes subtraction, and a logarithm is read straight off. The problem book asks you to round sizes and counts up to the nearest power of two for exactly this reason, and 210 ≈ 103 is the only conversion you need to remember.

11.1The memory hierarchy

A database is stored physically as files of records, and those files live on a disk. Lecture 18 begins with why.

Four levels, and the line through the middle
LevelCapacityAccess time
processor cache~1 MB~1 ns
primary memory~10 GB~10 µs
secondary memory~10 TB~1 ms
tertiary memoryunbounded~100 s

Databases are stored permanently on secondary storage, for three reasons Lecture 18 gives in order: they are too large to fit entirely in main memory, permanent loss of stored data arises less frequently there, and the cost of storage is cheaper.

Read the access-time column as the whole of this set. Primary memory is about a hundred times slower than cache, and disk is about a hundred thousand times slower than memory. That last ratio is why, when the cost of a database operation is estimated, only block accesses to secondary storage are counted: everything the processor does in between is several orders of magnitude too small to matter.

(a) In 2000 a disk access took about 10 ms and a memory access about 10 ns, so the disk is 10−2 / 10−8 = 106 times slower. The physical half is that the disk remembers when the power goes off.

Count steps on the ladder, do not multiply anything out. A terabyte is two steps above a megabyte, so 210 × 210 = 220. A petabyte is four steps above a kilobyte, so 240. A millisecond is two steps above a nanosecond and a second is two steps above a microsecond, so both of those are 106.

All four answers are a million, give or take the 2.4% in 210 ≈ 103, because all four questions are “two steps”. Seeing that before computing anything is the skill the rest of this set needs.

(a) Name two parameters that obey Moore's Law.
(b) Name two parameters that do not obey Moore's Law.
(c) Which memory type is called volatile, and why?
(d) Which operations, performed by the disk hardware in the process of fetching a block of data, are responsible for the major part of the access time?

(a) Processor speed and its speed-to-cost ratio; memory chip capacity and its specific cost; disk capacity and its specific cost.

(b) Memory access time, and disk rotation speed. Capacity is a matter of how small a feature can be printed; access time is a matter of how fast a signal or a motor can move, and those improve slowly.

(c) Main memory is volatile, because its content is lost when the power is switched off. So is the cache. Everything below the dashed line in §11.1 — disk and tape — is non-volatile, which is the first of the three reasons a database is stored there.

(d) Seek time and rotational latency. The major part of the disk access time is spent positioning the heads over the required cylinder (seek), and then waiting for the required sector in that cylinder to rotate under the head (latency). §11.2 puts numbers on both.

Why these four questions belong together. Moore's Law improves the two quantities in (a) and leaves the two in (b) alone; the two in (b) are exactly the ones in (d). So the gap between what a disk can hold and how fast it can be reached widens every year, and every technique in the rest of this set exists to work around it.

11.2Inside a disk

The parts, and the two that cost time

Two definitions, and the difference between them is the one students lose marks on:

TermIs
sectorthe smallest addressable unit on the disk device — a property of the hardware
blockthe unit of transfer between disk and CPU — a property of the system, usually several sectors

Everything on this page is counted in blocks, because the block is what crosses the wire. A query that needs one byte pays for a whole block; a query that needs a whole block pays the same.

The four factors, and which two matter
#FactorIsSize
1seek timetime for the read/write head to move from one track to anotherlarge
2latency timetime for the wanted sector to rotate under the headlarge
3processing timethe controller's own work≈ 0, typically ns
4transfer timemoving the bytes once they are under the headsmall, µs or ns

Latency comes straight off the rotation speed. At 6,400 revolutions per minute:

one revolution  =  60 s / 6400  ≈  0.01 s  =  10 ms

average latency =  half a revolution  =  5 ms

Half a revolution, because on average the sector you want is half a turn away — sometimes it has just passed, sometimes it is just arriving.

Factors 1 and 2 dominate; 3 and 4 are noise. That is why tb, the block access time, is treated as a single constant for the whole of this set: whatever the block holds and wherever it goes, the cost is the seek plus the latency, and those do not depend on how much you then read.

Your friend Jim runs a private database business. He is asking you for advice about some decisions he has to make. For each of the following scenarios, state your advice and explain it clearly. (Do not be equivocal.)

(a) Jim is unhappy because his disks are too slow. A vendor is offering a technology break-through: a disk controller whose processor speed, measured in instructions per second, exceeds the speed of the controllers currently in use by over 100. If Jim's typical disk costs x dollars, how much should Jim pay for this new controller?
(b) Jim has acquired exceedingly comprehensive archives containing libraries of old manuscripts, totaling several terabytes of data. A small number of research institutions world-wide are very interested in these archives, and are willing to pay Jim handsomely for providing a reliable access to the data. Typically, an interested researcher accesses one or very few manuscripts at a time, and looks at the manuscript(s) for a long time. The researchers habitually work at all hours of day and night, on holidays, etc. Which storage devices should Jim employ?

(a) Zero. Disk access time is heavily dominated by seek time and rotational latency. The delay caused by the controller while it is processing a transfer is already negligible, so making it a hundred times smaller than negligible changes nothing a user could measure.

This is factor 3 of the table above, and the question is a test of whether you believe the table. A hundredfold improvement in a quantity that is ≈ 0 is still ≈ 0; the two factors that are not ≈ 0 are mechanical and the new controller does not touch them.

(b) Juke-boxes — racks of optical disks with robotic arms, which mount disks on request. That is tertiary storage, the bottom level of §11.1's pyramid, and the scenario has been built so that every one of its drawbacks is harmless here. Only a few researchers are expected to be active at any time, so contention for the drives is unlikely. The expected long contact time — a researcher reads one manuscript for a long while — means the delay of several seconds required for the robot to fetch a disk is acceptable to the client. And excluding human operators renders the solution insensitive to the timing of requests, which matters because the researchers work at all hours.

Read the scenario for the three facts that make tertiary storage work. Several terabytes rules out keeping it in memory; few concurrent users and long sessions make a hundred-second access time tolerable; round-the-clock use rules out anything needing a person. Change any one of the three — make it thousands of users, or short lookups — and the answer changes to disk.

11.3How big is a file, and how long to read it

Four lines, in this order 
ℓ  =  ℓ₁ + ℓ₂ + … + ℓₙ        the length of one record
F  =  ℓ · T                     the length of the file in bytes
B  =  F / b  =  Tℓ / b          the length of the file in blocks
t  =  B · t​b                   the sequential scan time

Lecture 18's worked example. A stored file of fixed-length records with four fields of 16, 16, 32 and 64 bytes; 16 billion records; block size 16 kilobytes; block access time about 1/128 s. Round everything up to a power of two first:

ℓ   =  16 + 16 + 32 + 64  =  128   =  2⁷ B
T   =  16 billion  =  2⁴ · 10⁹  ≈  2⁴ · 2³⁰  =  2³⁴ records
b   =  16 KB  =  2⁴ · 2¹⁰  =  2¹⁴ B
t​b  =  1/128 s  =  2⁻⁷ s

F   =  ℓ · T  =  2⁷ · 2³⁴  =  2⁴¹ B
B   =  F / b  =  2⁴¹ / 2¹⁴  =  2²⁷ blocks

t   =  B · t​b  =  2²⁷ · 2⁻⁷  =  2²⁰ s  ≈  10⁶ s  ≈  12 days

Twelve days to read one file once, and nothing in that calculation is pessimistic: it assumes the records are fixed-length, the file is contiguous, and every block costs the same. A table two terabytes in size cannot be scanned, and that one sentence is the reason indexes exist.

Memorise 220 s ≈ 12 days. It turns up on this page four times, and it lets you read an exponent straight off as a human quantity: 222 s is four times that, about seven weeks.

Two habits worth forming now. Round up, never down — 16 billion becomes 234, not 233, and the answer is an upper bound. And never multiply anything out: every line above is addition and subtraction of exponents, and an answer written as 220 s is more useful than the same answer written as 1,048,576.

Refer to the Research Lab database of Set 3, whose employee table is declared 
employee (empId   VARCHAR(32),
          name    VARCHAR(40),

Assume all tables are stored as files of fixed-length records, so that every character occupies one byte, every numeric item occupies 8 bytes, every date item occupies 8 bytes, and the storage occupied by an entire record is simply the sum of the sizes of the individual items in that record. The block size is 16 kilobytes and the block access time is approximately 1/128 seconds. Eight gigabytes of core memory are available. Assume that the file employee, at its maximum intended size, accommodates about 32 million employees, and that the file is always at this maximum size.

(a) Describe an adequate procedure that the database engine should perform in order to execute the following query, and estimate the worst-case running time of the procedure you propose. 

SELECT * FROM employee;
(b) Do you find the execution time of the query considered in part (a) to be satisfactory? Explain your answer.

(a) Sequential scan, since the entire table must be returned as the query result. There is nothing to look up and nothing to skip; every block has to come across.

ℓ   =  32 + 40 + 40 + 8 + 8  =  128  =  2⁷ B
T   =  32 million  =  2⁵ · 10⁶  ≈  2⁵ · 2²⁰  =  2²⁵ records
b   =  16 KB  =  2¹⁴ B
t​b  =  1/128 s  =  2⁻⁷ s

B   =  ℓ · T / b  =  2⁷⁺²⁵⁻¹⁴  =  2¹⁸ blocks

t   =  B · t​b  =  2¹⁸ · 2⁻⁷  =  2¹¹ s  ≈  34 minutes

(b) Yes — however long it feels. The query cannot be made faster, because it spends its time transferring the required result: the entire table. It is the size of the result, rather than the procedure employed to construct it, that requires such running time.

This is the one case where a half-hour answer is the right answer, and it is worth being able to say why. Every other slow query on this page is slow because of how it was executed, and can be improved by executing it differently. SELECT * on a whole table has no “differently”: four gigabytes have to move, and no index, sort or algorithm changes that. If the execution time is unacceptable, the query is what has to change.

The eight gigabytes of memory are not used, and will not be until §11.5. Being given a number you do not need is normal in these questions — the parts of a problem share one setup.

Refer to the Mail-Order Bookstore database, whose customer table is declared 
customer (emailC VARCHAR(36),

Assume that every character occupies a single byte on disk, while every decimal or date occupies 11 bytes, and that there are no other hidden storage costs in any tuple or table. Block size is equal to 2 kilobytes, and block access time is equal to 1/512 seconds.

(a) Assuming that the Bookstore plans to enlist as customer every person on the planet, and that the population of Earth is estimated at about 8 billion people, calculate the maximum number of blocks that the table customer may occupy. (Assume that no customer will show up more than once under different email addresses.)
(b) Assuming that the Bookstore has reached its goal and has 8 billion customers, calculate the worst-case time to look up customer(s) by name.

(a)

B  =  Tℓ / b  =  2³³⁺⁶⁻¹¹  =  2²⁸ blocks

Which is half a terabyte — 239 bytes — for a table of three short fields, because there are eight billion of them.

(b) Sequential search is required, since there is no index on name and the file is not ordered on it, so in the worst case every block of the data file has to be read:

t​b  =  1/512 s  =  2⁻⁹ s

t   =  B · t​b  =  2²⁸ · 2⁻⁹  =  2¹⁹ s  ≈  6 days

Six days to answer one lookup, and the lookup is the commonest thing a bookstore does. Compare §11.4: the same file, if it were sorted on the field being searched, answers the same question in under a tenth of a second. That ratio — six days against a tenth of a second — is the entire argument for ordering a file, and for the indexes that come after this set.

Worst case means the record is not there, or is in the last block. A sequential search that finds its record early stops early; a sequential search that fails reads everything. When a question says “worst-case” it is asking for the second.

11.4Searching a file

Two procedures, and how to choose

Given a file and a field to search on, there are exactly two procedures available before indexes are introduced, and the schema decides which one you are allowed to propose.

ProcedureAllowed whenWorst-case cost
sequential searchalwaysB · tb
binary searchthe file is sorted on the search field(lg B + 1) · tb

Binary search counts blocks, not records. Lecture 18 first wrote the cost as (lg T + 1) tb and Lecture 19 corrected it: you halve the file by reading a block at a time, so the N in lg N is B, not T. Since T is larger than B — many records fit in a block — the first version overcharges you, by about lg(T/B) block accesses.

On Lecture 19's file, with B = 230 and tb = 2−8 s:

sequential:  B · t​b           =  2³⁰ · 2⁻⁸        =  2²² s  ≈  48 days
binary:      (lg B + 1) · t​b  =  (30 + 1) · 2⁻⁸  <  2⁵ · 2⁻⁸  =  1/8 s

Forty-eight days against an eighth of a second, on the same file, with the same hardware. The only difference is that the second file is sorted on the field being searched — and §11.5 is about what sorting it costs.

A note on the + 1

The lecture writes (lg B + 1) tb and the problem book writes (lg B) tb. The difference is one block access out of twenty or thirty — the final read of the block that holds the record. Either is accepted; this page follows the lecture and reports the book's figure where the two differ, which is never by more than a few milliseconds.

The question is always “is there a route in?”

When a problem says “describe an adequate procedure to search file X for records where field f equals…”, it is testing one decision, and the answer has three possible forms:

11.5Sorting a file that does not fit in memory

§11.4 ended on a promise: a sorted file answers a lookup in milliseconds instead of days. Lecture 19 asks what the sorting costs, and the first answer is: more than the file is worth.

Merge sort, and why it is hopeless here

Merge sort builds sorted runs by repeated pairwise merging:

AfterThere areeach of size
round 0N sorted sequences1
round 1N/2 sorted sequences2
round 2N/4 sorted sequences4
round iN/2i sorted sequences2i
the last round1 sorted sequenceN

How many rounds? Solve N / 2r = 1, so N = 2r and r = lg N. Each round touches every element, so the running time is N lg N — which is optimal for sorting, and irrelevant, because the elements are on a disk. Every element is read once and written once per round:

t  =  N · lg N · t​b · 2

On Lecture 19's file, with N = T = 64 billion = 236 records and tb = 2−8 s:

t  =  2³⁶ · lg 2³⁶ · 2⁻⁸ · 2
   =  2³⁶ · 36 · 2⁻⁸ · 2
   >  2³⁶ · 32 · 2⁻⁸ · 2        since 36 > 32 = 2⁵
   =  2³⁶⁺⁵⁻⁸⁺¹  =  2³⁴ s
   =  2¹² · 2²⁰ s  ≈  4000 × 12 days  ≈  500 years

Five hundred years. The algorithm is asymptotically optimal and the answer is useless, which is the clearest demonstration on this page that counting operations is the wrong model once the data is on a disk. What N lg N fails to notice is that main memory exists and is free: merge sort moves every element across the wire lg N times, when most of that work could have been done in memory.

Multiway merge sort

Two rounds of a different shape. B is the file in blocks, M is memory in blocks.

Round 1 — make sorted runs. Divide the data into partitions that fit into memory, and sort each one with an in-memory sort. That sorting is free, in the sense that counts here: it moves no blocks. What it costs is one read and one write of the whole file.

after round 1:  ⌈B / M⌉ sorted runs, each of M blocks
cost:           2 · B · t​b      (the file in, the file out)

Round 2 and after — merge M runs at once. Hold one block of each run in memory, plus one buffer block for the output. Repeatedly extract the smallest element among the fronts of the runs — a heap does this efficiently — and append it to the buffer. The buffer is flushed to disk only when it is full, and a memory block is replenished from its run only when it is empty, so again the round costs one read and one write of the file.

after round 2:  B / M² sorted runs, each of M² blocks
after round 3:  B / M³ sorted runs, each of M³ blocks
      ⋮
after round R:  1 sorted run of B blocks

How many rounds? Each round multiplies the run size by M, so MR ≥ B and

R  =  ⌈logₛ B⌉  =  ⌈ lg B / lg M ⌉

Every round costs 2 · B · tb — one scan in, one scan out — so:

t  =  2 · B · t​b · R   =   2 × R × (scan time)

On the same file, with B = 230 blocks of 212 bytes and M = 4 GB:

M  =  4 GB / b  =  2² · 2³⁰ / 2¹²  =  2²⁰ blocks
R  =  ⌈ lg B / lg M ⌉  =  ⌈ 30 / 20 ⌉  =  2

t  =  2 · R · (scan time)  =  2 · 2 · 48 days  ≈  192 days

Five hundred years becomes six months, a speedup of about a thousand, and the file and the hardware are unchanged. Everything was bought by noticing that memory holds 220 blocks and that merge sort was using two of them.

The whole cost is in R, and R is tiny. lg M is twenty or more on any real machine, and lg B is rarely above forty, so R is almost always 1, 2 or 3. Which gives the rule worth carrying out of this set: sorting a file costs about two or four scans of it — and if the file fits in memory, R = 1 and it costs exactly two.

(a) A file occupies K blocks of the secondary storage, while the main memory has M blocks. Give an estimate of the cost of sorting the file by an adequate algorithm. Explain your answer briefly.
(b) A file occupies K blocks of the secondary storage, while the main memory has M blocks. A talented administrator has installed a new main memory module, increasing its total size to 2M blocks. Give an estimate of the resulting relative speedup in the cost of sorting the file. Explain your answer briefly.

(a) Multiway merge sort completes in about logM K rounds, in each round transferring the K data blocks once into memory and once out of it. The number of block accesses is therefore

2K · logₛ K

(b) By part (a), the ratio of the old and the new sorting times is

  2K · logₛ K          logₛ K
------------------  =  --------------  =  logₛ 2M  =  1 + 1 / lg M  ≈  1
 2K · log₂ₛ K        log₂ₛ K

The speedup is negligible for practical purposes. For a memory of 1 gigabyte with a block size of 10 kilobytes we have M ≈ 105, so lg M > 15 and the improvement is under 7%.

Why doubling the memory buys almost nothing is worth saying in words, because the result is counter-intuitive. Memory enters the cost only inside a logarithm, and only as the base of one. Doubling M adds 1 to lg M, and lg M is already fifteen or twenty, so the number of rounds hardly moves — and since R is a ceiling, usually it does not move at all. To halve the sorting time you would have to square the memory, not double it.

Note the change of variable. This question writes K where the lecture writes B; the formula 2K logM K is the lecture's 2 · B · tb · R counted in block accesses rather than in seconds, with the tb left off.

Your friend Jim occasionally sorts mailing lists for GLOBAL ALERT, a local advertising company. A typical mailing list is about 50 gigabytes long. Jim's assistant has carefully implemented the quicksort algorithm on the server, which has one gigabyte of main memory. Jim is very unhappy, as the sorting time appears to be much worse than that of his competitor.

(a) What should Jim do? State your advice and explain it clearly.
(b) Which storage devices should Jim employ for this sorting task? Precisely, the lists have to be brought in from GLOBAL ALERT, sorted, and returned to GLOBAL ALERT.

(a) Jim should eliminate quicksort and implement multiway merge sort. Quicksort is an in-memory algorithm: run against a file far larger than memory, its expected running time is Ω(lg N · B) block transfers, where N is the number of items sorted and B the number of blocks in the file. Multiway merge sort completes in 2(logM K · K) block transfers in the worst case, so the expected speedup is at least

  lg N
---------
logₛ K

Put numbers to the denominator. Even for a small block size, say a kilobyte, a 50-gigabyte file is about 5 · 107 blocks and a gigabyte of memory is about 106 blocks, so

logₛ K  ≈  log₁₀⁶ (5 · 10⁷)  <  2

while lg N for a file of tens of millions of records is around 25 or 30. The speedup is about an order of magnitude, and costs nothing but the algorithm.

(b) The lists should be brought in and taken back on a tape — conveniently, even one tape cassette may suffice. The tape should be the source for the first phase of the multiway merge sort, with the intermediate results written to disks. Finally, the second phase of the multiway merge sort should write back to the tape.

Each level of the hierarchy is used for what it is good at. Tape is cheap, portable and sequential — perfect for carrying 50 gigabytes across town and for feeding a sequential first pass, and useless for anything that needs to jump around. The merge phase does jump around, between M runs at once, so it needs disk. And the sorting inside each run happens in memory. One task, three levels, chosen by access pattern rather than by speed.

Why quicksort was the wrong choice and not just a slow one. Quicksort's partitioning step walks the data from both ends inwards, which is the one access pattern a block-oriented device punishes hardest: consecutive comparisons land in blocks far apart, so almost every comparison costs a block access. The right question about an algorithm here is not how many comparisons it does but how many blocks it touches, and merge sort — which reads and writes in long sequential runs — wins that question even though it loses the comparison count.

Refer again to the Professor Payroll database of Exercise 11.8, with the same assumptions: 128 million professors, block size 32 kilobytes, block transfer time 1/256 seconds, 8 gigabytes of primary memory, and the field lengths given there.

Describe an adequate procedure to sort the file professor according to the field wizardID, and estimate the worst-case running time of the procedure you propose.

Multiway merge sort. From Exercise 11.8, B = 218 blocks and tb = 2−8 s.

M  =  8 GB / b  =  2³ · 2³⁰ / 2¹⁵  =  2³³⁻¹⁵  =  2¹⁸ blocks  =  B

R  =  ⌈ lg B / lg M ⌉  =  ⌈ 18 / 18 ⌉  =  1

t  =  2 · R · B · t​b  =  2 · 1 · 2¹⁸ · 2⁻⁸  =  2¹¹ s  ≈  34 minutes

The file fits in primary memory exactly — M = B = 218 blocks — so the multiway merge sort has only one round: the file is read in, sorted in memory, and written out. There is nothing to merge.

Two scans, and no algorithm at all. When R = 1 the “sort” is just the first phase of §11.5's round 1, and the in-memory sorting between the read and the write is free by this page's accounting. So the cost of sorting a file that fits in memory is exactly twice the cost of reading it — 34 minutes against the 17 of Exercise 11.8(a), which is the arithmetic confirming it.

Watch the ceiling. ⌈18/18⌉ is 1, but ⌈19/18⌉ is 2. One more bit of file — a file twice this size — doubles the sort time, because it forces a second round. Nothing in between: R is an integer, so the cost of sorting goes up in steps, not smoothly.
