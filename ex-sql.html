Creating, changing, querying

The commands of Lectures 11 and 12 in the order they were given — data types, CREATE, INSERT, UPDATE, DELETE, then ORDER BY, the aggregate functions, GROUP BY and HAVING — each with the lecture's own query worked through beside it. Then twelve fresh exercises from the problem book, on two databases you have not seen before. No JOIN keyword anywhere.

Set 6 translated the relational algebra into SQL and stopped where the algebra stops. This set is everything SQL has that the algebra does not: a way to create a database, a way to change one, a way to sort the answer, and a way to count, total and average over groups of rows.

How this page is arranged

Sections 7.1 to 7.5 are the lectures: each command, and then the lecture's own query using it, worked through with the rows it returns. Nothing there is an exercise — your notes already have those answers, and they are reproduced here so that the explanation sits next to them.

The exercises are §7.7 and §7.8, and all twelve come from the problem book. They use two databases you have not met: the Company Database of Appendix B.9, whose content the book supplies in full, and the Department Membership Database of Appendix B.19.

The one rule this set works under

No JOIN. Relations go in the FROM clause separated by commas — that comma is the cartesian product — and every condition linking them is written out in the WHERE clause. That is how both lectures write every query, and it is the restriction the problem book imposes on the two sections these exercises come from: your code must not contain union, intersection, except, or any of the join operators. The reason is the one from Set 5: a join decides for itself which columns to match on, so an answer written with one never has to state the condition that links two tables — which is the thing being marked.

These are your domain constraints from Set 4 — the first of the five, and the only one you express by choosing a type rather than by writing a clause. DEC(4,0) for a four-digit id is a domain constraint; so is VARCHAR(40) for a name.

Money is DECIMAL, never FLOAT

DEC(8,2) holds a salary exactly. FLOAT holds it approximately, so two salaries that should be equal can compare unequal and a total can come out a penny short. The lecture's schema uses DEC(8,2) for salary for this reason.

7.2Creating a database and its tables

CREATE DATABASE databasename;     -- creates database
DROP DATABASE databasename;       -- deletes existing database
SHOW DATABASES;                   -- shows all the databases
USE databasename;                 -- selects database

SHOW TABLES;                      -- shows all the tables in the DB

CREATE TABLE table_name (
    column1 datatype,
    column2 datatype,
    column3 datatype NOT NULL,    -- force the column NOT to accept NULL
    ...
    PRIMARY KEY (column_name),    -- defines primary key
    FOREIGN KEY (column_name) REFERENCES referenced_table(referenced_column)
                                  -- defines foreign key
);

DESC table_name;                  -- shows description of created table
DROP TABLE table_name;            -- deletes table

Three of the five schema-based constraints of Set 4 appear in that one statement: the domain constraint in each datatype, the key constraint and entity integrity in PRIMARY KEY, referential integrity in FOREIGN KEY ... REFERENCES. The fourth, NOT NULL, is the constraint on nulls. Only the application-based constraints have nowhere to go.

Example — creating collegeDB

The four schemas of Lecture 11, as a database:

CREATE DATABASE collegeDB;
USE collegeDB;

CREATE TABLE Person (
    id        DEC(4,0),
    name      VARCHAR(40) NOT NULL,
    yearBorn  YEAR,
    PRIMARY KEY (id)
);

CREATE TABLE Teacher (
    tid     DEC(4,0),
    trank   VARCHAR(30),
    salary  DEC(8,2),
    PRIMARY KEY (tid),
    FOREIGN KEY (tid) REFERENCES Person(id)
);

CREATE TABLE Department (
    code   CHAR(4),
    name   VARCHAR(40),
    chair  DEC(4,0),
    PRIMARY KEY (code),
    FOREIGN KEY (chair) REFERENCES Teacher(tid)
);

CREATE TABLE Discipline (
    tid    DEC(4,0),
    dcode  CHAR(4),
    PRIMARY KEY (tid, dcode),
    FOREIGN KEY (tid)   REFERENCES Teacher(tid),
    FOREIGN KEY (dcode) REFERENCES Department(code)
);

The order is forced. Teacher references Person, Department references Teacher, Discipline references both — so any other order fails on the first foreign key that points at a table not yet created:

ERROR 1005 (HY000): Can't create table `collegeDB`.`Teacher`
(errno: 150 "Foreign key constraint is incorrectly formed")

which is an unhelpful way of saying “there is no such table”.

tid does two jobs in Teacher: it is the primary key and a foreign key into Person. That is the signature of a subclass mapped as its own table, and it is why Teacher holds no name — the name is on Person, once.

Discipline's key is the pair. A teacher teaches in several departments and a department has several teachers, so neither column alone is unique. Both being in the primary key also means neither can ever be null, by entity integrity.

The only constraint here that you have to decide rather than read off the schemas is NOT NULL on name.

Dropping goes the other way

DROP TABLE Person is refused while Teacher still references it, so tables are dropped children-first — exactly backwards from the order they were created. The same asymmetry governs the deletion example in §7.3, where it applies to rows rather than tables.

7.3Inserting, updating, deleting

-- insert, two forms
INSERT INTO table_name VALUES (value1, value2, value3, ...);
INSERT INTO table_name (column1, column2, column3, ...)
       VALUES (value1, value2, value3, ...);

-- update
UPDATE table_name
   SET column = new_data
 WHERE condition(s);

-- delete
DELETE FROM table_name
 WHERE condition(s);

The first INSERT form gives a value for every column, in the order the table declares them. The second names the columns, which lets you leave some out — and the ones you leave out get NULL, or their declared default.

Example — two ways to get a null 
INSERT INTO Person VALUES (1001, 'Blue', 1970);
INSERT INTO Person VALUES (1002, 'Red', NULL);
INSERT INTO Person (id, name) VALUES (1003, 'Pink');
INSERT INTO Person VALUES (1004, 'Green', 1980);

Row 1002 names NULL explicitly, which the first form requires since it demands a value for every column. Row 1003 uses the second form and simply does not mention yearBorn. Both leave the same row:

+------+-------+----------+
| id   | name  | yearBorn |
+------+-------+----------+
| 1001 | Blue  |     1970 |
| 1002 | Red   |     NULL |
| 1003 | Pink  |     NULL |
| 1004 | Green |     1980 |
+------+-------+----------+

Neither trick works on name, which is NOT NULL, and the two refusals read differently:

INSERT INTO Person VALUES (1006, NULL, 1990);
ERROR 1048 (23000): Column 'name' cannot be null

INSERT INTO Person (id, yearBorn) VALUES (1005, 1990);
ERROR 1364 (HY000): Field 'name' doesn't have a default value

The first is the constraint on nulls refusing a null you supplied; the second is the server saying it has nothing to put there. Same constraint, two ways of hitting it.

The insert order is forced too, for the same reason the CREATE order was: all four Person rows before any Teacher row, all three Department rows before any Discipline row.

Example — add $1000 to each professor 
UPDATE Teacher
   SET salary = salary + 1000
 WHERE trank = 'Professor';
before:                          after:
+------+-----------+----------+  +------+-----------+----------+
| tid  | trank     | salary   |  | tid  | trank     | salary   |
+------+-----------+----------+  +------+-----------+----------+
| 1001 | Professor | 90000.00 |  | 1001 | Professor | 91000.00 |
| 1002 | Lecturer  | 50000.00 |  | 1002 | Lecturer  | 50000.00 |
| 1003 | Professor | 80000.00 |  | 1003 | Professor | 81000.00 |
+------+-----------+----------+  +------+-----------+----------+

SET salary = salary + 1000 reads the old value and writes the new one, row by row. The = is assignment here, not comparison — the same symbol doing a different job than it does four words later in the WHERE clause.

Example — delete all data for the person named 'Blue'

The obvious statement does not work:

DELETE FROM Person WHERE name = 'Blue';
ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key
constraint fails (`collegeDB`.`Teacher`, CONSTRAINT `Teacher_ibfk_1`
FOREIGN KEY (`tid`) REFERENCES `Person` (`id`))

Blue is referenced from Teacher, and through it from Department and Discipline. Referential integrity refuses — which, from Set 4, is the only constraint a DELETE can violate. So work inwards from the leaves:

UPDATE Department SET chair = NULL
 WHERE chair IN (SELECT id FROM Person WHERE name = 'Blue');

DELETE FROM Discipline
 WHERE tid IN (SELECT id FROM Person WHERE name = 'Blue');

DELETE FROM Teacher
 WHERE tid IN (SELECT id FROM Person WHERE name = 'Blue');

DELETE FROM Person WHERE name = 'Blue';
Person:                        Department:
+------+-------+----------+    +------+------------------+-------+
| id   | name  | yearBorn |    | code | name             | chair |
+------+-------+----------+    +------+------------------+-------+
| 1002 | Red   |     NULL |    | CSCI | Computer Science |  NULL |
| 1003 | Pink  |     NULL |    | MATH | Mathematic       |  NULL |
| 1004 | Green |     1980 |    | PHYS | Physices         |  1003 |
+------+-------+----------+    +------+------------------+-------+

Why the first statement is an UPDATE. CSCI and MATH still exist; only their chair is leaving. Setting chair to null is legal precisely because it is a foreign key that is not part of Department's primary key — referential integrity permits a null foreign key. Had it been NOT NULL there would be no way to do this without deleting the departments.

Why each statement re-reads the subquery. Every one asks Person again for Blue's id, which works because Person is deleted last. Reverse any two and the subquery comes back empty and the delete silently does nothing.

UPDATE and DELETE without WHERE

WHERE is optional and its absence means every row. DELETE FROM Teacher; empties the table; UPDATE Teacher SET salary = 0; pays nobody. Neither asks whether you meant it. Run the matching SELECT first, see which rows come back, then change the word.

7.4Retrieving: the algebra, in SQL

This is Set 6's whole thesis in four lines, and it is where this set starts rather than finishes:

query in relational algebraSQL
Π[A1, ..., An]SELECT A1, ..., An
σ[F] ( R1 × ... × Rk )FROM R1, ..., Rk
F ≡ [ condition(s) ]WHERE condition(s);
SELECT * FROM table_name;                 -- selects the whole table
SELECT DISTINCT ... FROM ... WHERE ...;   -- selects distinct data
Example — and the DISTINCT that is easy to forget 
SELECT trank FROM Teacher WHERE salary > 5000;
+-----------+          with DISTINCT:   +-----------+
| trank     |                           | trank     |
+-----------+                           +-----------+
| Professor |                           | Professor |
| Lecturer  |                           | Lecturer  |
| Professor |                           +-----------+
+-----------+

Three rows for three teachers, two of them the same word. In the algebra, Π[trank] σ[salary > 5000] Teacher gives two — a relation is a set. SQL returns a bag, so the duplicate stays unless you ask. Write DISTINCT wherever you are translating a Π.

Note also that every teacher qualifies: 5,000 is below the lowest salary in the table, so the WHERE removes nothing.

Example — teachers who chair more than one department

The algebra first:

Π[name2, salary1] σ[F] ( Teacher1 × Person2 × Department3 × Department4 )
    where   F  ≡  [ tid1 = id2  ∧  tid1 = chair3  ∧  tid1 = chair4  ∧  code3 ≠ code4 ]
SELECT DISTINCT p.name, t.salary
  FROM Teacher t, Person p, Department d1, Department d2
 WHERE t.tid = p.id
   AND t.tid = d1.chair
   AND t.tid = d2.chair
   AND d1.code != d2.code;
+------+----------+        without DISTINCT:  +------+----------+
| name | salary   |                           | name | salary   |
+------+----------+                           +------+----------+
| Blue | 90000.00 |                           | Blue | 90000.00 |
+------+----------+                           | Blue | 90000.00 |
                                              +------+----------+

Four relations become four tables after FROM; four conjuncts become four lines of WHERE. Two things are not mechanical.

Two aliases for Department. Without them d1.code != d2.code cannot be written at all — there would be one code and nothing to compare it with.

The inequality makes “more than one” mean more than one. Drop it and the two copies may be the same row, so every chair qualifies against themselves. And because Blue chairs CSCI and MATH, the pair qualifies in both orders — which is what the DISTINCT is cleaning up.

Example — professors in Computer Science, not knowing the code 
SELECT DISTINCT p.name, t.salary
  FROM Person p, Teacher t, Discipline di, Department de
 WHERE p.id = t.tid
   AND t.tid = di.tid
   AND di.dcode = de.code
   AND de.name = 'Computer Science'
   AND t.trank = 'Professor';
+------+----------+
| name | salary   |
+------+----------+
| Blue | 90000.00 |
| Pink | 80000.00 |
+------+----------+

The parenthetical is the point. Knowing the code was 'CSCI' you could write di.dcode = 'CSCI' and drop Department entirely — three tables instead of four. Not knowing it, you go in through the name, which costs one extra table and one extra equality. A query is shorter when it can start from a key and longer when it has to start from a name.

Red teaches in CSCI but is a Lecturer, so is excluded. Pink appears via Discipline (1003,'CSCI') even though the department Pink chairs is PHYS — teaching in a department and chairing one are separate facts in separate tables, and this query asks about the first.

Example — the highest salary, without MAX

The losers-and-winners pattern of Set 5, made literal: each step becomes a real table.

CREATE TABLE loser
SELECT t1.tid FROM Teacher t1, Teacher t2 WHERE t1.salary < t2.salary;

CREATE TABLE winner
SELECT tid FROM Teacher WHERE tid NOT IN (SELECT * FROM loser);

SELECT p.name, t.trank
  FROM Person p, Teacher t, winner w
 WHERE p.id = t.tid AND t.tid = w.tid;
loser:              winner:            result:
+------+            +------+           +------+-----------+
| tid  |            | tid  |           | name | trank     |
+------+            +------+           +------+-----------+
| 1002 |            | 1001 |           | Blue | Professor |
| 1003 |            +------+           +------+-----------+
| 1002 |
+------+

Look at loser. Three rows for two teachers — 1002 appears twice, because Red is out-earned by both Blue and Pink, and the SELECT that built the table had no DISTINCT. It does not matter here, since NOT IN only asks whether a value is present; but a table you built yourself is still a bag, and a COUNT over it would have been counting pairs.

As a single statement, the loser query moves bodily into the subquery and winner disappears:

SELECT p.name, t.trank
  FROM Person p, Teacher t
 WHERE p.id = t.tid
   AND t.tid NOT IN ( SELECT t1.tid
                        FROM Teacher t1, Teacher t2
                       WHERE t1.salary < t2.salary );

The comparison must be strict. With <= every teacher is out-earned by themselves, winner is empty, and the query returns nothing. Ties come out right for free: two teachers sharing the top salary do not out-earn each other, so both survive.

7.5Ordering, aggregation, grouping

Ordering. The algebra has no order at all — a relation is a set. SQL will sort the answer for you:

SELECT column1, column2, ...
  FROM table_name
 ORDER BY column1, column2, ... (ASC / DESC);   -- ascending by default

Aggregate functions. Five of them, and not one has an algebraic counterpart:

functionreturns
MIN() / MAX()the smallest / largest value of the selected column
COUNT()the number of tuples in the selected result
AVG()the average value of a numeric column
SUM()the total sum of a numeric column

Grouping. GROUP BY collects the tuples that have the same values into summary rows, and is normally used with the aggregate functions above. Conditions on an aggregate cannot go in WHERE, which is applied to each row before the groups exist; HAVING is the clause that applies after.

So the clauses run in an order quite different from the one you type them in: FROM builds the product, WHERE filters rows, GROUP BY forms the groups, HAVING filters groups, SELECT picks the columns, ORDER BY sorts what is left. That sequence answers most questions about which clause a condition belongs in: if it mentions an aggregate it must be HAVING, and otherwise put it in WHERE, where it removes rows before any counting is done and so costs less.

Example — teachers who teach more than one department, two ways

With two copies of one table, the Set 5 technique:

SELECT DISTINCT p.name
  FROM Person p, Discipline d1, Discipline d2
 WHERE p.id = d1.tid AND p.id = d2.tid AND d1.dcode != d2.dcode;

With grouping, which the algebra cannot express at all:

SELECT p.name
  FROM Person p, Discipline d
 WHERE p.id = d.tid
 GROUP BY p.id
HAVING COUNT(d.dcode) > 1;
+------+
| name |
+------+
| Blue |
+------+

The second is better, and not only because it is shorter. “More than one” generalises: change > 1 to > 2 and you have teachers in three departments. The first would need a third copy and three inequalities, and for four departments a fourth copy and six. That is the practical reason aggregation was added to SQL.

No DISTINCT on the second, because GROUP BY p.id produces exactly one row per teacher. The first needs it because it produces one row per qualifying pair.

Group by the key, select the name. p.name is not in the GROUP BY list, which some servers reject. It is legal here and in standard SQL, because p.id is the primary key and therefore determines name. If your server complains, write GROUP BY p.id, p.name — grouping by both changes nothing, since the key alone already fixes the groups.

Example — min, max and average salary of lecturers 
SELECT MIN(salary), MAX(salary), AVG(salary)
  FROM Teacher
 WHERE trank = 'Lecturer';
+-------------+-------------+--------------+
| MIN(salary) | MAX(salary) | AVG(salary)  |
+-------------+-------------+--------------+
|    50000.00 |    50000.00 | 50000.000000 |
+-------------+-------------+--------------+

One row in, one row out. An aggregate with no GROUP BY treats the whole filtered table as a single group, so this returns exactly one row however many teachers match. Here only Red does, which is why all three answers agree — degenerate, but correct, and the three functions agree precisely when the group has one row.

Note the widths. MIN and MAX return the column's own type, DEC(8,2), so two decimal places. AVG is a division and the server widens the result, which is why it prints six. ROUND(AVG(salary), 2) if you need it formatted.

The useful version asks it of every rank at once:

SELECT trank, MIN(salary), MAX(salary), AVG(salary), COUNT(*)
  FROM Teacher GROUP BY trank;
+-----------+-------------+-------------+--------------+----------+
| trank     | MIN(salary) | MAX(salary) | AVG(salary)  | COUNT(*) |
+-----------+-------------+-------------+--------------+----------+
| Lecturer  |    50000.00 |    50000.00 | 50000.000000 |        1 |
| Professor |    80000.00 |    90000.00 | 85000.000000 |        2 |
+-----------+-------------+-------------+--------------+----------+

Adding COUNT(*) to a grouped query costs nothing and tells you how much each row is based on — which is how you spot that the Lecturer average is one person rather than a hundred.

A warning about nulls. Every aggregate except COUNT(*) skips nulls rather than treating them as zero. So AVG over a column with nulls divides by the number of non-null values, and COUNT(salary) and COUNT(*) can disagree.

Example — the highest salary again, now with MAX 
SELECT p.name, t.trank
  FROM Person p, Teacher t
 WHERE p.id = t.tid
   AND t.salary = (SELECT MAX(salary) FROM Teacher);
+------+-----------+
| name | trank     |
+------+-----------+
| Blue | Professor |
+------+-----------+

Four lines instead of the eleven it took without MAX. (SELECT MAX(salary) FROM Teacher) is a scalar subquery: it returns exactly one value, so it can go anywhere a value can. If one in that position returned more than one row the server would raise an error rather than guess.

It is still =, not ORDER BY ... LIMIT 1. The tempting one-liner returns one row by construction; if two teachers shared the top salary it would pick one, arbitrarily and silently. When a question says “teacher(s)” with the s in brackets, it is telling you the answer may have more than one row.

And the subquery cannot be a WHERE condition on the outer query. WHERE t.salary = MAX(t.salary) is not legal: an aggregate cannot appear in WHERE, because WHERE is evaluated per row, before any group exists.

Example — every teacher and their number of departments, descending 
SELECT p.name, COUNT(d.dcode)
  FROM Person p, Discipline d
 WHERE p.id = d.tid
 GROUP BY p.id
 ORDER BY COUNT(d.dcode) DESC;
+------+----------------+
| name | COUNT(d.dcode) |
+------+----------------+
| Blue |              2 |
| Red  |              1 |
| Pink |              1 |
+------+----------------+

All five clauses in one query, in the order they are typed and not in the order they run.

“Descending” needs DESC, and the sort is on the count, which is why the expression appears again in the ORDER BY. You may repeat it, or name it with AS and sort by that. Either way, Red and Pink tie at one and ORDER BY says nothing about the order of rows that tie — add a second sort key if it matters.

The lecture's answer adds HAVING COUNT(d.dcode) >= 1, which is harmless and does nothing: a group exists only because it has at least one row. Worth noticing rather than copying.

Green is missing, and that is the interesting part. Green is a person, not a teacher, and has no Discipline row, so the WHERE finds no match and Green never reaches a group. “Every person, including zero” cannot be asked on this page at all — the comma product cannot keep a row that matches nothing. That is what an outer join is for, and it is the one thing here that genuinely needs the JOIN keyword.

7.7Exercises: the Company Database

Problems 739–748 of the problem book, in a different order — single-table first, then the ones that need a product. Same rule throughout: no join operators.

Print a list of names and salaries of all analysts, sorted by salary, the greatest first.
SELECT ename, salary FROM emp WHERE job = 'analyst' ORDER BY salary DESC;
+-------+---------+
| ename | salary  |
+-------+---------+
| Scott | 3000.00 |
| Ford  | 3000.00 |
+-------+---------+

One table, one condition, one sort. DESC is needed because ORDER BY is ascending unless told otherwise, and “greatest first” is the only part of the sentence that is about sorting.

Scott and Ford both earn 3,000, so the two rows tie and nothing in the query says which comes first. On this server they come back in that order; on another, or after an index is added, they may not. ORDER BY salary DESC, ename if you want it settled.

Find the total number of salesmen and their average salary.
SELECT COUNT (enumber), AVG (salary) FROM emp WHERE job = 'salesman';
+----------------+-------------+
| COUNT(enumber) | AVG(salary) |
+----------------+-------------+
|              4 | 1400.000000 |
+----------------+-------------+

Two aggregates with no GROUP BY, so the whole filtered table is one group and the answer is one row. Allen 1600, Martin 1250, Turner 1500 and Ward 1250 average 1400 exactly.

COUNT(enumber) rather than COUNT(*). They agree here, because enumber is the primary key and so can never be null. They would differ on a nullable column: COUNT(*) counts rows, COUNT(x) counts rows where x is not null. Counting a key is a safe habit precisely because the two cannot diverge.

And a question this cannot answer: the average salary of each job, all at once. That needs GROUP BY job, and then you get one row per job rather than one row for the single job you filtered to.

Find an alphabetically sorted list of names of all employees whose name begins with letter S.
SELECT ename FROM emp WHERE ename LIKE 'S%' ORDER BY ename;
+-------+
| ename |
+-------+
| Scott |
| Smith |
+-------+

LIKE with a pattern, which is the one string operator SQL has that the algebra does not. % matches any run of characters including none; _ matches exactly one. So 'S%' is “begins with S”, '%s' would be “ends with s”, and '_o%' would be “second letter is o”.

Case. MariaDB's default collation folds case, so 's%' finds the same two rows here. That is a property of the collation, not of SQL — PostgreSQL would return nothing, and ILIKE is its case-insensitive form. Never rely on it either way.

ORDER BY ename with no DESC is ascending, which for a string column means alphabetical — again, by the collation's idea of alphabetical.

Find the highest, lowest, and average salary paid.
SELECT MAX (salary), MIN (salary), AVG (salary) FROM emp;
+-------------+-------------+-------------+
| MAX(salary) | MIN(salary) | AVG(salary) |
+-------------+-------------+-------------+
|     5000.00 |      500.00 | 1968.333333 |
+-------------+-------------+-------------+

No WHERE at all: the group is the whole table, all fifteen employees. King's 5,000 and Boss's 500 are the two ends.

What this cannot tell you is who. Adding ename to the select list does not work — the query returns one row and there are fifteen names, so there is no sensible value to put there. Standard SQL rejects it outright; MySQL and MariaDB may silently pick a name from an arbitrary row, which is worse. Finding the highest-paid employee is a different query, and it is the one worked through twice in §7.4 and §7.5.

The average is not a salary anybody earns, and it is pulled upwards by King: nine of the fifteen employees are below it and only six above. AVG over a whole table says nothing about how the money is spread, which is what GROUP BY is for — Exercise 7.10 asks the same kind of question one group at a time.

Find names and salaries of all employees whose manager is Jones.
SELECT e1.ename, e1.salary FROM emp e1, emp e2
 WHERE e1.manager_num = e2.enumber AND e2.ename = 'Jones';
+-------+---------+
| ename | salary  |
+-------+---------+
| Scott | 3000.00 |
| Ford  | 3000.00 |
+-------+---------+

Two copies of one table, because the question is about a relationship between two rows of emp: e1 is the employee being reported, e2 is their manager. Without the aliases there is no way to say which ename you mean.

The link runs e1.manager_num = e2.enumber — the child's foreign key to the parent's key — and getting it backwards gives you the subordinates of Jones's own manager, which is a different and non-empty answer. Writing the foreign key down in the direction the schema declares it is the check.

Jones is employee 7566 and manages Scott and Ford, the two analysts. You could get the same answer with WHERE manager_num = 7566 and one table — but only by knowing Jones's number, and the question gives a name. That is the same shape as the Computer Science example in §7.4.

Find names and job titles of all employees that are managed by some employee whose job title is not manager.
SELECT e1.ename, e1.job FROM emp e1, emp e2
 WHERE e1.manager_num = e2.enumber AND e2.job != 'manager';
+-------+-----------+
| ename | job       |
+-------+-----------+
| Smith | clerk     |
| Jones | manager   |
| Blake | manager   |
| Clark | manager   |
| Adams | clerk     |
| Boss  | professor |
+-------+-----------+

The same two-copy shape as Exercise 7.5, with the condition moved from the manager's name to the manager's job.

Read the answer and the point becomes clear. Jones, Blake and Clark are managers themselves, and they are in the answer because their manager is King, whose job is president. Smith's manager is Ford, an analyst; Adams's is Scott, also an analyst; Boss reports to King. The condition is about the manager's job, not the employee's.

King is not in the answer, and the reason is the null. King's manager_num is NULL, so e1.manager_num = e2.enumber is unknown for every e2, and WHERE discards unknown. That is three-valued logic doing exactly what you want here — King has no manager, so no manager of King has a job title — but it is worth noticing that nothing in the query says so.

And != is the same null trap in waiting. If some employee had a null job, e2.job != 'manager' would be unknown for them too and they would silently drop out, even though a null job is certainly not 'manager'.

Find names and locations on which they work of all employees managed by the president.
SELECT e1.ename, loc FROM emp e1, emp e2, dept
 WHERE e1.dept_number = dept.dept_number
   AND e1.manager_num = e2.enumber
   AND e2.job = 'president';
+-------+----------+
| ename | loc      |
+-------+----------+
| Clark | New York |
| Jones | Dallas   |
| Blake | Chicago  |
| Boss  | Queens   |
+-------+----------+

Three tables, two links. emp twice for the manager relationship, as in Exercises 7.5 and 7.6, plus dept to turn the employee's department number into a place.

The two links do different jobs and it is worth saying which. e1.manager_num = e2.enumber together with e2.job = 'president' selects the rows — it is the question. e1.dept_number = dept.dept_number selects nothing: it is there only to make loc available, because the answer has to name a location and emp does not hold one.

That is the general pattern for “find X and some attribute of a related thing”: one link per relationship you are asserting, plus one link per table you need only in order to read a column from it. Count them against the tables — three tables want at least two links — and a missing one is obvious before you run anything.

The president is King, and the four people reporting to him are the three managers plus Boss, scattered across four of the five locations. Boston is missing because department 4 has no employees at all.

Find names and salaries of all employees who have a higher salary than some employee who works in research.
SELECT ename, salary FROM emp WHERE
       salary >
            (SELECT MIN(salary) FROM emp, dept WHERE
                    dept_name = 'research' AND
                    emp.dept_number = dept.dept_number);
+--------+---------+     the research salaries:
| ename  | salary  |     +-------+---------+
+--------+---------+     | ename | salary  |
| Allen  | 1600.00 |     +-------+---------+
| Ward   | 1250.00 |     | Smith |  800.00 |
| Jones  | 2975.00 |     | Jones | 2975.00 |
| Martin | 1250.00 |     | Scott | 3000.00 |
| Blake  | 2850.00 |     | Adams | 1100.00 |
| Clark  | 2450.00 |     | Ford  | 3000.00 |
| Scott  | 3000.00 |     +-------+---------+
| King   | 5000.00 |
| Turner | 1500.00 |
| Adams  | 1100.00 |
| James  |  950.00 |
| Ford   | 3000.00 |
| Miller | 1300.00 |
+--------+---------+

“Higher than some employee” is higher than the lowest-paid one. That is the whole translation, and it is worth doing deliberately rather than by feel: to beat at least one member of a set, you need only beat the smallest. The research salaries run from 800 to 3000, so the condition amounts to salary > 800, and thirteen of the fifteen employees qualify — everyone except Smith himself at 800 and Boss at 500.

The same reading turns the other three quantified questions into things you can already write:

the questionwhat to write
greater than some member> (SELECT MIN(...) ...)
greater than every member> (SELECT MAX(...) ...)
equal to some memberIN (SELECT ...)
different from every memberNOT IN (SELECT ...)

The book writes the first two as > ANY and > ALL, which SQL does have. The lectures do not use them, and as the table shows, nothing is lost: an aggregate and a comparison say the same thing, and say it in terms you can already defend.

Notice that the subquery names the same tables as the outer query. emp appears inside and outside, and they are unrelated uses — the inner one lists research salaries, the outer one is the employee being tested. A subquery is evaluated on its own terms unless it refers to a column from the outer query, which this one does not.

The research members themselves are in the answer, except the one who earns least, because a research employee can perfectly well out-earn a colleague. Had the question meant “than every employee in research”, the subquery would read MAX instead of MIN, and only King at 5,000 would qualify.

7.8Exercises: Department Membership

Problems 735–738, against the database of §7.6. The book's own restriction is the one this set works under: your code must not contain union, intersection, except, or any of the join operators.

Write SQL code that creates the tables for the Department Membership Database. A professor has a social security number, a name, a rank and a salary, and exactly one main department; may additionally be a member of any number of other departments; and a department has at most one chair, who chairs at most one department. Provide for all the stated constraints.
CREATE TABLE deprt (
    name VARCHAR (20),
    room VARCHAR (6),
    phone DECIMAL (4,0),
    PRIMARY KEY (name)
);

CREATE TABLE prof (
    pnumber CHAR (9),
    name VARCHAR (20) NOT NULL,
    rank VARCHAR (20),
    salary DECIMAL (8,0),
    main VARCHAR (20) NOT NULL,
    PRIMARY KEY (pnumber),
    FOREIGN KEY (main) REFERENCES deprt,
    CONSTRAINT pnb CHECK (to_number (pnumber) >= 0)
);

CREATE TABLE member (
    pnumber CHAR (9),
    additional VARCHAR (20),
    PRIMARY KEY (pnumber, additional),
    FOREIGN KEY (pnumber) REFERENCES prof,
    FOREIGN KEY (additional) REFERENCES deprt
);

CREATE TABLE chair (
    who CHAR (9) UNIQUE,
    what VARCHAR (20),
    PRIMARY KEY (what),
    FOREIGN KEY (who) REFERENCES prof,
    FOREIGN KEY (what) REFERENCES deprt
);

“Exactly one main department” is two constraints. The foreign key says it must be a real department; the NOT NULL says there must be one. Leave off the NOT NULL and a professor may float unattached — the thing this schema most needs to prevent.

“At most one chair per department” is the primary key on what. chair is keyed on the department, not on the person, which is what stops a department having two chairs.

“Who chairs at most one department” is the UNIQUE on who. This is the one easy to miss. Without it, chair could hold (Snape, Potions) and (Snape, Hiding) — two different primary keys, so the key constraint has no objection. UNIQUE is how you declare a candidate key that is not the primary one, and it is the only way to express a 1 : 1 relationship in SQL.

On the CHECK clause. to_number is Oracle's; MariaDB has no such function, so running the book's DDL as printed fails there. Written CHECK (pnumber >= 0) it does the same job, since MariaDB casts the string for the comparison. This is the standard annoyance with CHECK: it is the least portable thing in the DDL, and MySQL ignored it entirely until 8.0.16.

FOREIGN KEY (main) REFERENCES deprt with no column named is legal shorthand — the reference is taken to be the primary key of deprt. Naming it is clearer.

Write SQL code for the following query, whose purpose is to find how people and earnings are distributed across ranks and departments.

Find a table with columns DEPARTMENT, RANK, COUNTPROFS, AVGSALARY. For each department say d and each rank say r, find as countProfs the number of professors whose rank is equal to r and whose main department is d, and find as avgSalary the average salary of these professors. Do not take into account or consideration any of those professors whose rank is recorded as unranked, and do not report those pairs of a department d and rank r where the average salary of professors of rank r in the department d is less than one dollar.

SELECT    main AS department, rank, COUNT(*) AS countProfs, AVG(salary) AS avgSalary
FROM      prof
WHERE     rank != 'unranked'
GROUP BY  main, rank
HAVING    AVG(salary) >= 1;
+-----------------+---------------------+------------+-------------+
| department      | rank                | countProfs | avgSalary   |
+-----------------+---------------------+------------+-------------+
| Divination      | Lecturer            |          2 |  40000.0000 |
| Potions         | Associate Professor |          1 |  76000.0000 |
| Potions         | Professor           |          2 |  89500.0000 |
| Transfiguration | Assistant Professor |          1 |  52000.0000 |
| Transfiguration | Professor           |          1 | 104000.0000 |
+-----------------+---------------------+------------+-------------+

One table in the FROM. Everything the question asks about — department, rank, salary — is on prof, because main holds the department name itself rather than a code. No second table, no link.

Grouping by two columns makes one group per pair, which is exactly what “for each department and each rank” asks for. A department with professors at three ranks produces three rows.

The two conditions go in different clauses, and the question tells you which. “Do not take into account” is about individual professors, so it is a WHERE — it removes Umbridge before any group is formed, so she affects no count and no average. “Do not report those pairs” is about whole groups and is stated in terms of an average, so it must be a HAVING. Swapping them is not possible: an aggregate cannot appear in WHERE, and rank != 'unranked' in HAVING would let Umbridge into her group's average first.

Both clauses do visible work on this data. With neither:

+-----------------+---------------------+------------+-------------+
| department      | rank                | countProfs | avgSalary   |
+-----------------+---------------------+------------+-------------+
| Divination      | Lecturer            |          2 |  40000.0000 |
| Hiding          | Assistant Professor |          1 |      0.0000 |
| Hiding          | unranked            |          1 | 120000.0000 |
| Potions         | Associate Professor |          1 |  76000.0000 |
| Potions         | Professor           |          2 |  89500.0000 |
| Transfiguration | Assistant Professor |          1 |  52000.0000 |
| Transfiguration | Professor           |          1 | 104000.0000 |
+-----------------+---------------------+------------+-------------+

Two extra rows: Umbridge's, removed by the WHERE, and Filch's, removed by the HAVING because he is paid nothing. That second one is the reason the question bothers to mention a dollar.

COUNT(*) rather than COUNT(salary). They differ when salaries can be null: COUNT(*) counts rows, COUNT(salary) counts non-null salaries, and AVG ignores nulls as well. A professor with a null salary would be counted in countProfs and silently left out of avgSalary — two columns answering slightly different questions.

Professor Severus Snape (whose social security number is 123456789) has served as chair in the department named Potions. However, he is now leaving this department and will have no affiliation with it in future. His new main department is Hiding (though he will not be the chair there). Otherwise, he retains all his current additional affiliations. Write the SQL code that makes this change.

Three things have to happen, in three tables: he stops chairing Potions, he stops being affiliated with Potions, and his main department becomes Hiding.

DELETE FROM chair  WHERE who = '123456789';
DELETE FROM member WHERE pnumber = '123456789' AND additional = 'Potions';
DELETE FROM member WHERE pnumber = '123456789' AND additional = 'Hiding';
UPDATE prof SET main = 'Hiding' WHERE pnumber = '123456789';
chair:                             member, for Snape:
+-----------+-----------------+    +-----------+------------+
| who       | what            |    | pnumber   | additional |
+-----------+-----------------+    +-----------+------------+
| 222222222 | Transfiguration |    | 123456789 | Divination |
| 777777777 | Hiding          |    +-----------+------------+
+-----------+-----------------+

prof, for Snape:
+-----------+---------------+--------+
| pnumber   | name          | main   |
+-----------+---------------+--------+
| 123456789 | Severus Snape | Hiding |
+-----------+---------------+--------+

The order is forced by the foreign keys again. The update to prof.main comes last so that nothing is pointing at a department he is in the middle of leaving.

The third statement is the one to think about. Hiding is currently an additional affiliation and is about to become his main one. Leaving the member row records the same fact twice, in two tables, which is the redundancy the split into main and additional exists to avoid. The schema does not forbid it, so this is a judgement the constraints cannot make for you.

The book's answer does not run, and then does the wrong thing

The printed answer is three statements:

DELETE FROM chair WHERE who = '123456789';
DELETE FROM member WHERE who = '123456789';
UPDATE prof SET main = 'Hiding' WHERE pnumber = '123456789';

The second has no WHERE column to stand on — member's columns are pnumber and additional, and there is no who:

ERROR 1054 (42S22): Unknown column 'who' in 'WHERE'

Correct that to pnumber and it runs, but now it deletes every one of Snape's additional affiliations — including Divination, which the question explicitly says he keeps. Both the chair row and the Potions membership should go; Divination should not.

Worth doing deliberately: run the book's version, look at what is left in member, and compare it with the sentence “otherwise, he retains all his current additional affiliations”.

Implement a database upgrade which will enable the Office to keep track of department secretaries. These are not professors (but rather ordinary wizards and witches). Although identified by social security number and certainly having name, secretaries will never receive any salary, nor bear any special rank. However, secretaries serve in the role known as Keeper of Secrets. Precisely, each department chair may designate one secretary as Keeper of Secrets. Secretaries, in general, may keep secrets for several chairs (or none as yet) and the Office needs to record all the Keeper of Secret assignments.

Write SQL code to create the new table(s) and/or modify definitions (or content) of the existing ones (including dropping), as needed. No part of the existing database content may be lost.

CREATE TABLE secretary (
    snumber CHAR (9),
    name VARCHAR (20) NOT NULL,
    PRIMARY KEY (snumber)
);

CREATE TABLE keeperSecrets (
    pnumber CHAR (9),
    snumber CHAR (9),
    PRIMARY KEY (pnumber),
    FOREIGN KEY (pnumber) REFERENCES prof,
    FOREIGN KEY (snumber) REFERENCES secretary
);

Two new tables, nothing dropped, nothing altered — which is the right answer to “no part of the existing content may be lost”.

Why secretaries do not go in prof. They would fit: social security number, name. But prof also carries rank, salary and a NOT NULL main department, and the narrative says secretaries have none of those. Adding them would mean either relaxing main to nullable — weakening a real constraint on actual professors — or inventing a department for people who have none. A separate table costs one more relation and keeps both groups honestly described.

The cardinality is all in the primary key. “Each chair may designate one secretary” is PRIMARY KEY (pnumber): at most one row per professor. “Secretaries may keep secrets for several chairs” is the absence of any constraint on snumber — it may repeat freely. And “or none as yet” is satisfied by a secretary simply having no row, which is why the relationship is a table of its own rather than a column on secretary.

Checking it after creating:

+----------------------+          DESC keeperSecrets;
| Tables_in_deptmember |          +---------+---------+------+-----+
+----------------------+          | Field   | Type    | Null | Key |
| chair                |          +---------+---------+------+-----+
| deprt                |          | pnumber | char(9) | NO   | PRI |
| keeperSecrets        |          | snumber | char(9) | YES  | MUL |
| member               |          +---------+---------+------+-----+
| prof                 |
| secretary            |
+----------------------+

PRI on pnumber and MUL on snumber is the cardinality, read back out of the catalogue: “unique” and “may repeat”.

One thing the schema does not say. The narrative is about department chairs designating secretaries, but pnumber references prof, not chair. So the DDL permits a professor who chairs nothing to have a Keeper of Secrets. Referencing chair(who) instead would enforce it — who is UNIQUE, so it can be referenced — at the cost that the row would have to be deleted whenever someone stopped being a chair, as in Exercise 7.13. Either is defensible; what matters is noticing that you chose.

Going further

One thing on this page could not be written at all: the last example of §7.5 leaves Green out, because the comma product cannot keep a row that matches nothing. “Every person, with zero where they teach nothing” needs an outer join, which is the one place the JOIN keyword is not avoidable — LEFT JOIN has no comma equivalent and no algebraic counterpart either.

Beyond that: views, which name a query and let you select from it — the problem book's answer to Problem 750 writes the same query both ways, with and without; transactions, which make the four statements of §7.3's deletion succeed or fail as one unit; and indexes, which change nothing about what a query means and a great deal about how long it takes. And the question this set has carefully not asked — whether the schema stores the same fact twice — is normalization.
